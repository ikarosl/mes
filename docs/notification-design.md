# 通用通知跨模块协议

本文维护业务、Notification、事务基础设施和目标模块的分工。发布参数、去重、本人阅读及数据保留由 [Notification](../apps/api/src/modules/notification/README.md)及其[数据库](../apps/api/src/modules/notification/docs/database.md)维护；选择理由见 [ADR-0007](adr/0007-general-notification-boundaries.md)。审批事件映射见[Approval](../apps/api/src/modules/approval/README.md#通知事件)。

## 1. 模块定位与所有权

| 所有者 | 职责 |
| --- | --- |
| 触发业务模块 | 决定事件身份、触发时机、具体收件人、最小摘要与真实来源/目标，核验业务资格 |
| Notification | 不可变消息、固定收件集合、发布去重、本人收件及首次阅读、提交后扩展端口 |
| 最外层事务 executor | 原子提交业务、通知和成功审计，确认提交后调度扩展 |
| 目标模块 | 详情及操作实时鉴权，业务待办和状态 |

通知未读、业务待办、外部投递结果互相独立。Notification 不重算角色或处理业务决定；新增通知场景仍须单独确认范围。

## 4. 同事务落库与提交后钩子

### 4.1 提交边界

业务、消息、收件和成功审计同事务提交，失败整体回滚。站内核心写入不能移入异步钩子。只有实际新消息登记待触发事件；内层 Repository 返回不代表提交成功。最外层 executor 明确提交并释放连接后才调度；回滚、提交未确认和重试废弃尝试不触发。事务内按通知身份合并登记。

### 4.2 通用非阻塞端口

扩展端口属于 Notification，事务基础设施只负责通用调度。事件是轻量不可变数据，不携带连接、请求、凭证或正文；需要读取时另起公开读取。业务响应不等待处理器；调度失败、同步抛错及异步 rejection 分别隔离，不能改变已提交结果、重做业务或尝试回滚。日志只留稳定身份及脱敏分类。

同键复用及 HTTP 成功重放不重新调度。当前默认空实现，不接外部网络、队列或 outbox；未来处理器须异步 I/O，并明确超时、并发、积压与过载处理，不能只去掉 await 后阻塞业务。

### 4.3 可靠性边界

进程内钩子是 best-effort，提交到调度或执行完成之间退出都可能丢失触发，不保证自动补发、严格顺序或可靠送达。需要可靠外部投递时另行设计持久化投递职责、恢复、领取、重试及通知/用户/渠道去重；发送成功但回执丢失仍须渠道幂等或明确重复策略，不能承诺恰好一次。外部副作用遵守[幂等规范](../apps/api/docs/idempotency.md)。
