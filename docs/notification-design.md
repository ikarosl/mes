# 通用通知设计（尚未实施）

长期决策以 [ADR-0007](adr/0007-general-notification-boundaries.md) 为准，审批接入场景见[审批设计](approval-design.md)。Notification 尚未实现；本设计规定后续首期边界，不代表已存在通知表、接口、管理端入口或事务钩子。未完成事项统一见[路线图](roadmap.md#通用通知后续实施)。

## 1. 模块定位与所有权

Notification 是服务各业务模块的通用站内通知模块，Approval 只是首个调用方。后续生产派工、业务异常等场景可复用同一公开能力，但各场景是否接入须由业务所有者明确，不因通用设计提前扩大业务范围。

| 所有者 | 职责 |
| --- | --- |
| 触发业务模块 | 决定何时通知、通知谁、事件身份、最小摘要和目标对象；校验来源、目标及业务资格 |
| Notification | 消息及收件记录、发布去重、本人收件查询与已读状态、提交后通知扩展端口 |
| 最外层事务 executor | 原子提交业务、通知与成功审计，管理事务内待触发事件，提交成功后调度钩子 |
| 目标业务模块 | 详情查询和业务操作的实时鉴权；业务状态及待办事实 |

通知未读、业务待办完成、未来外部渠道投递结果是独立概念，不能相互替代。Notification 不读取审批节点来推断接收人，不执行审批决定，也不拥有生产或库存事实。

其他模块仅通过 Notification 根级 `public.ts` 使用稳定契约，不直接写其表。application 契约不暴露数据库连接、HTTP Request 或渠道 SDK；事务接入遵守[架构规范](architecture.md)，成功审计仍统一经公共 transactional audit writer。

## 2. 公开发布契约

以下是后续接口必须满足的语义，具体方法名、DTO 和错误代码在模块实施时由所有者文档定义。

- 发布输入包含稳定事件键、事件类型、可选的来源类型与 ID、可选的目标类型与 ID、纯文本标题及摘要、具体用户 ID 集合和命令审计上下文。调用方是后端业务用例，不开放允许前端任意指定事件和收件人的通用发送接口。
- `event_type/source_type/target_type` 按业务命名空间登记到共享常量，contracts 使用字符串联合类型；扩展时增加明确场景契约，不在 Notification 中硬编码审批专用分支。`event_type` 表达发生了什么，是否支持跳转由可选目标表达；不再增加重复的“事务/系统”分类列，也不把通知类型解释为处理资格。
- 接收人由业务模块在触发时解析为具体用户；Notification 只规范化、去重并保存该次收件集合，不重新检查角色、业务权限或账号启停，不因操作者也是收件人而排除本人。已存在用户即使停用也不删除其收件历史，认证有效性由 Identity 负责；不存在的用户 ID 仍须拒绝，不能绕过外键和引用完整性。
- 对尚未发布的新事件，空收件集合返回明确的“无收件人，未创建”结果，不写消息和收件表，不登记钩子，不因此抛出业务资格错误。业务动作是否必须有接收人由业务模块校验；空集合不表示全员广播。已有同键事件仍须先按下方一致性规则处理，不通过改为空集合绕过去重冲突。
- 收件集合在发布时固定，前端只拉取本人的收件记录；角色成员变化不补写、删除或转移历史记录。Approval 的发布/送审资格校验及运行中无人可审规则见[审批接入](approval-design.md#3-审批通知接入尚未实施)，通知模块不接管审批资格判断。
- 事件键带业务命名空间，由稳定业务动作或事件身份生成；按场景加入事件类型及目标节点等信息。不得使用每次调用新生成的随机键、当前时间或原始 HTTP 幂等键代替事件身份；无业务来源的纯通知同样由发布用例提供稳定事件键。
- 同键且规范化内容一致时返回已有通知身份，并标明没有新建；一致性比较包含来源、目标、事件类型、标题、摘要和去重后的收件集合。同键不同内容或不同收件集合应拒绝，不覆盖原消息或补写收件人。真正的新动作或更正通知使用新事件键。空收件而未创建的事件不形成持久化去重记录，也不由 Notification 自动重新发布。
- 并发发布由数据库唯一约束保证只有一条消息，唯一键冲突后仍须核对内容。通知级去重独立于 HTTP 幂等；后者仍需逐端点登记及验收，不能因存在 `event_key` 就宣称接口支持 `Idempotency-Key`。

### 2.1 文本与可选跳转

所有通知统一展示纯文本标题和正文。无目标的系统通知直接展示内容；有目标时，前端在正文旁呈现由结构化目标生成的“查看详情”链接。首期每条消息至多一个目标，不在正文持久化 HTML、Markdown 链接或 URL，不建设富文本和多链接编辑器。

前端集中维护 `target_type -> 稳定路由名、参数及详情定位方式` 的映射，`target_id` 只提供目标身份。同一审批申请的待办、通过、驳回等不同事件可以复用 `approval_instance` 的同一映射；页面重命名或路径调整由前端映射维护。缺少目标或尚无对应映射时仍可阅读正文，不执行猜测出的地址。

| 场景示例 | 事件类型 | 来源 | 跳转目标 | 展示 |
| --- | --- | --- | --- | --- |
| 审批节点待处理 | `approval_task_assigned` | 审批动作 | 审批申请 | 文本及“查看详情”链接，进入后由 Approval 判断当前能否处理 |
| 审批结果 | `approval_approved` 等 | 审批动作 | 审批申请 | 文本及同一申请的详情链接，不因有链接而表示仍有待办 |
| 纯系统通知 | 如 `system_notice`，实施时登记 | 可以为空 | 为空 | 直接展示文本 |

`source_type/source_id` 表示“因哪次业务动作产生”，`target_type/target_id` 表示“点开后去哪个对象”，两者可以不同，也可以分别为空。各字段对必须同时有值或同时为空，已登记业务事件仍遵守自己的来源/目标必填契约；例如审批通知继续必须关联真实动作和申请。

纯系统通知是一种内容场景，不等于无人执行的定时任务；首期由有登录身份的发布用例触发并记录 `created_by`。本设计允许无业务来源和无跳转内容，不额外建设公告发布页面；定时提醒和无人系统作业暂不考虑，因此不引入虚构操作者或修改人工审计规则。

## 3. 站内通知候选表

遵守[数据库公共规则](database-conventions.md)：ID/FK 为 `BIGINT UNSIGNED`，API 中以字符串传输；时间为 `DATETIME` 北京时间，接口带 `+08:00`。新外键默认限制删除，不级联删除消息或人员历史。

### 3.1 `notifications`

一次事件产生的一条站内消息，可有多个接收人，所有者 Notification。

| 字段 | 类型及空值 | 含义 |
| --- | --- | --- |
| `id` | `BIGINT UNSIGNED NOT NULL` | 主键 |
| `event_key` | `VARCHAR(150) NOT NULL` | 服务端稳定事件去重键 |
| `event_type` | `VARCHAR(50) NOT NULL` | 代码登记的事件类型；审批首批为 `approval_task_assigned/approval_approved/approval_rejected/approval_withdrawn` |
| `source_type` | `VARCHAR(50) NULL` | 代码登记的来源类型；审批使用 `approval_action`；无业务来源时为空 |
| `source_id` | `BIGINT UNSIGNED NULL` | 触发消息的业务动作或事件 ID，与来源类型成对为空或有值 |
| `target_type` | `VARCHAR(50) NULL` | 代码登记的目标类型；审批使用 `approval_instance`；无跳转时为空 |
| `target_id` | `BIGINT UNSIGNED NULL` | 对应业务目标 ID，与目标类型成对为空或有值 |
| `title` | `VARCHAR(255) NOT NULL` | 服务端生成的纯文本标题 |
| `body` | `TEXT NOT NULL` | 最小通知摘要，不复制完整业务单据或敏感详情 |
| `created_by` | `BIGINT UNSIGNED NOT NULL` | 首期人工作业触发人，引用 users；事务内派生消息沿用触发人 |
| `created_at` | `DATETIME NOT NULL` | 创建时间 |

约束：`UNIQUE(event_key)`。分别以 CHECK 保证 `(source_type IS NULL AND source_id IS NULL) OR (source_type IS NOT NULL AND source_id IS NOT NULL)` 及对应 target 字段的成对空值规则，不允许只有类型或只有 ID。原始消息不可改写、删除；非空来源和目标是跨模块逻辑引用，由发布用例通过所属模块能力验证，不建立通用多态 FK。类型可扩展不等于接受任意字符串，不能用 `0` 或假 ID 代替空值。

### 3.2 `notification_recipients`

各用户自己的通知收件和阅读状态，所有者 Notification。

| 字段 | 类型及空值 | 含义 |
| --- | --- | --- |
| `id` | `BIGINT UNSIGNED NOT NULL` | 主键 |
| `notification_id` | `BIGINT UNSIGNED NOT NULL` | 消息 FK |
| `user_id` | `BIGINT UNSIGNED NOT NULL` | 接收人 FK users |
| `read_at` | `DATETIME NULL` | 为空未读，首次标记后不回写为空 |
| `created_by/created_at/updated_by/updated_at` | 按数据库公共规则 | 收件创建沿用触发人，已读更新记录本人 |
| `version` | `INT NOT NULL DEFAULT 0` | 乐观并发版本，`CHECK(version >= 0)` |

约束：`UNIQUE(notification_id,user_id)`；索引 `(user_id,read_at,created_at,id)` 和 `(user_id,created_at,id)`，分别支持未读及全部收件分页。

只允许本人标记自己的收件记录已读，点击该条通知时调用写接口更新数据库，重复操作保持首次时间，不改变业务状态。并发更新遵守乐观锁规范，不覆盖首次已读时间；具体请求版本与重复成功响应在 API 契约中细化。首期不提供手动“标记已读”按钮、全部已读、消息删除、改回未读或收件人手工增删。

## 4. 同事务落库与提交后钩子

### 4.1 提交边界

1. 业务用例通过公开能力，在同一 MySQL 事务内完成业务写入、通知和收件记录、成功审计。任一核心落库失败整体回滚，不能把站内通知核心写入放进异步钩子。
2. 只有实际新建的通知登记事务内待触发事件；这些事件是事务作用域的临时内存数据，不是第二份持久化事实。Notification 加入已有事务时，不自行提交或提前发送。
3. 最外层事务 executor 确认提交成功、释放本次事务连接后，才把待触发事件交给提交后调度能力。INSERT 执行完成、内部 Repository 返回或内层事务回调返回均不代表最外层已提交。
4. 回滚或提交结果未确认成功时不触发钩子；重试废弃前次尝试的临时事件，只允许最终确认提交的尝试进入调度。同一事务内按通知身份合并重复登记。

### 4.2 通用非阻塞端口

Notification 提供统一的提交后通知扩展端口，首期默认空实现；这是后续实现要求，当前尚无该钩子。端口归 Notification，事务基础设施只负责通用提交后调度，不感知审批事件或外部渠道。

- 钩子接收已提交通知的轻量、不可变数据，例如通知 ID、稳定事件键、事件类型、来源与目标引用、接收用户 ID 和关联 requestId。不得捕获事务连接、请求对象、Token、Cookie 或外部渠道凭证；需要进一步读取时通过公开能力发起新的读取。
- 业务响应不等待钩子或外部请求完成。调度阶段不内联执行外部处理器；未来实现必须使用异步 I/O，不能仅移除 `await` 后同步执行耗时逻辑并宣称非阻塞。
- 调度失败、处理器同步抛错和异步 rejection 都必须独立捕获；钩子失败不改变已提交业务结果、不触发业务重做、不尝试回滚已提交事务。记录通知 ID、事件类型、requestId 和脱敏错误，不记录通知正文或凭证。
- 同键复用已有通知以及 HTTP 成功结果重放都不重新登记钩子。事务提交成功只获得本次进程内触发机会，不承诺外部渠道恰好投递一次。
- 首期不实现外部网络发送、渠道配置、重试任务、消息队列或 outbox。实际接入外部处理器时，必须再定义超时、并发上限、积压上限及过载处理，不能无限堆积异步任务或用同步等待反向阻塞业务请求。

### 4.3 可靠性边界

站内消息以数据库提交结果为准。进程内钩子属于 best-effort：提交成功到调度之间、调度后执行完成之前都可能因进程退出丢失外部触发；提交结果不确定时也不能靠直接重发补救。首期不承诺自动补发、严格顺序或可靠外部送达。

未来若要求可靠外部投递，应另行设计同事务持久化投递记录或 outbox、后台恢复与重试、按通知/接收人/渠道去重、多实例领取和失败处置。发送成功但回执丢失时，仍需渠道幂等或明确重复投递策略；不得把简单钩子升级描述为恰好一次保证。该持久化任务用于记录投递职责，不复制业务事实或引入兼容双写。

外部投递状态独立于站内已读和业务完成。外部副作用的 HTTP 幂等约束继续遵守[现有幂等规范](../apps/api/docs/idempotency.md)，不因事务后运行就自动具备恢复闭环。

## 5. 拉取、点击已读与历史展示

- 首期采用“后端落库，前端主动拉取本人通知列表及未读数”。打开通知入口和当前页面正常刷新时请求服务端；轮询间隔及每页条数在界面实施时确定，不引入 WebSocket/SSE 推送、跨标签页消息或同步机制。断网恢复后通过下一次正常拉取取得数据库状态。
- 拉取列表、展示预览和打开通知入口本身不修改已读。用户点击具体通知或它的详情链接时，发送本人收件记录的已读写请求，数据库保存首次 `read_at`；标记与目标页面能否访问独立，目标路由或接口拒绝访问也不撤销已读。
- 前端收到已读成功后更新当前页面状态和未读数；请求失败时保留原未读状态并按既有 HTTP 规则提示，可在再次点击时重新尝试。GET 不承担写入，不只在本地减未读数后宣称已保存；不为通知实现多标签页同步。
- 通知模块只校验登录身份与本人收件关系：列表、未读数和已读命令都由后端强制限定当前用户，不能读取或修改他人收件记录。Notification 不重建目标业务的权限模型，不因用户后来失去审批或其他业务权限而隐藏其已有通知文本。
- 历史标题和正文按发布时文本继续展示，不作为当前业务状态或处理资格。即使目标结束、停用、删除或已无访问权限，原收件内容和逻辑引用仍保留；业务模块负责确定发布内容，不复制完整业务单据，不因跳转失效改写旧通知。
- 跳转由前端映射和既有路由守卫处理，目标详情及后续操作继续由所属业务模块的后端接口独立鉴权。通知模块不提前查询目标权限以隐藏正文或链接；路由守卫不能代替目标 API 的安全边界。
- 列表采用服务端分页和稳定的 `created_at,id` 排序；未读数来自本人收件记录，审批待办数来自 Approval 的当前活动节点与实时资格。两者独立，点击通知不完成审批或其他业务待办。

## 6. 历史保留

通知及收件记录默认长期保留，不提供用户删除、自动到期清理或定期归档任务。正文保持发布时内容，收件记录只按既定规则更新已读与审计字段；通过索引和分页读取历史。

运维可以单独安排人工备份，年度备份不等于年度清空。将来确需清理时，应另行明确备份恢复验证、按业务关联范围处理、跨期追溯及事件去重身份的保留方式，再维护运维方案；不能仅因已有备份就忽略在线外键和事实历史规则。本次不定义或执行清理操作，开发环境允许重置的约定不等于正式运行数据的定期清空策略。

## 7. 实施与验证边界

实施时建立 Notification 模块所有者 README、数据库与接口文档，登记架构边界、共享代码和权限；本文候选表届时由模块数据库文档统一维护，避免形成两份权威定义。

验收至少覆盖：非审批业务形态及无来源/无跳转文本的公开发布契约、来源/目标成对空值、空收件跳过与本人去重、跨模块同事务提交与回滚、最外层提交前不得触发、提交失败与重试事件丢弃、并发去重及同键不同内容、HTTP 重放不重复调度、钩子慢响应或异常不改变业务响应、本人收件隔离、点击已读及失败保持未读、首次已读并发、权限变化后历史文本仍可见和失效业务链接。非审批契约验证不要求提前新增生产通知等实际功能。

本次仅补设计；后续编码完成先保证可启动，由用户黑盒测试和 UI 确认后再编写测试集，遵守根 AGENTS.md 的阶段安排。

项目目前处于开发阶段，数据库结构可以调整并完全重置，无需保留兼容数据。通知实施只追加 migration，重置后用统一 migration/seed 恢复，不依赖现有数据，不建设兼容双写或影子表。本次不创建表、不追加 migration、不重置数据库。
