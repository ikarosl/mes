# 设计选择与现状差异

状态：结构方向已确定，完整字段与约束见[评审入口](README.md)，代码已接入，待验收见路线图。本文件保留设计时的选择理由与改造前后差异，不再并行维护三套待选DDL。

## 已选方案

复用公共入出库主从，内嵌有类型来源外键；归并生产退料的实际物流单据。需求、分配、采购和产出授权等独立业务事实不归并。公共四表归Inventory所有，各来源模块仍负责自己的资格、额度及履约。

当前轻量模块化单体只有六个明确场景，采用直接来源FK可以复用既有采购／成品字段，减少来源关联主从和联查。接受公共表知道业务来源结构：新增实际场景时按需要新增来源字段和条件约束，不提前建设万能业务ID或插件式业务关联体系。

未选“全部场景各自一套物流主从”，因为会增加其他入出库两套状态及单据查询，同时继续保留独立退料物流字段。未选“公共主从加每场景来源分表”，因为来源引用当前没有独立数量或生命周期，分表收益不足以抵消额外关联和组合约束。未来出现独立业务事实时再建其业务表，不把当前决定解释为永远不能增加关联表。

## 三种数量并不合并

例如原分配10、已确认领料8、本次退3：分配仍记录10；inbound_detail记录3和原分配引用；确认后库存流水记录+3。分配量不是已领量，可退额度从实际已领8扣除退料及损耗计算。旧return_detail不再保存第二份3。需求履约不因退回3而恢复。

单据与流水分别表达待办／执行单据和不可变库存事实。草稿没有流水，确认有一次匹配流水；库存余额只从流水形成。授权数量100、本次入库60、下次40同样是不同事实，不能为了少一个数量字段删除授权。

## 改造边界

这是有限的公共单据归并，仍有实际依赖成本。所有六场景一次接入，必须一起处理成品负流水、草稿新批次、预留并发、领退额度、采购／产出历史已入以及收尾追溯，不称为只改几个字段。

本目录没有业务代码、正式migration、数据库执行或测试验收结论。旧表删除只在正式版本化迁移中执行，开发库使用已允许的重建／初始化，不设计双写或影子表。待完成工作统一在[路线图](../roadmap.md#通用出入库后续阶段)。
