# 管理端前端架构规范

本文是 `apps/admin-web` 的前端代码分层、数据所有权、候选生命周期、刷新和竞态规则的唯一基准。
页面视觉与通用交互以根目录 `design.md` 为准，多标签页、路由弹窗和失效候选的具体接入方式见
`frontCompoentDesgin/DynamicTabSwitching.md`，HTTP 协议以 `api-conventions.md` 为准，通用编码细节以
`coding-standards.md` 为准。

本文解决的核心问题不是“请求应该写在页面还是组件”，而是每类数据必须有唯一、可解释的所有者，并具有明确的
加载、刷新、错误和并发语义。禁止以一个大而全的 `loadData()` 或多个互不相知的局部缓存代替这些设计。

## 1. 设计目标

- 同一份候选数据在同一消费边界内只有一份状态来源，不在多个 composable 中复制原始 `ref` 和请求逻辑。
- 候选所有权采用“composable 实现复用、所有者实例局部化”：跨页面复用 `useXxxOptions` 工厂实现，但每个
  页面/弹窗持有独立实例，不引入跨页面共享缓存，因此不要求缓存页之间实时同步。
- 正式列表、动态候选、关键明细和编辑草稿使用不同生命周期，失败时互不拖累。
- 弹窗打开、页面激活和下拉展开能够获得新鲜候选，但不得覆盖用户尚未提交的草稿。
- 写操作只刷新受影响的数据，不以全页面重载掩盖状态所有权不清。
- 所有异步请求都能抵御重复触发、响应乱序、目标切换、页面失活和会话切换。
- 前端权限行为与后端 `/options` 的跨页面授权契约一致，但不把前端可见性当作安全边界。
- 架构决策可以通过类型、测试和代码评审清单验证，而不是依赖约定俗成。

非目标：

- 不引入通用前端数据请求框架或服务端状态库来替代当前 Vue 和 `src/api`。
- 不为候选数据建立跨页面全局缓存、失效传播、TTL 或实时同步；每个消费方按自身生命周期刷新。
- 不为 ID 绑定明细预建无限缓存；切换目标即重新加载。
- 不把管理端扩展为完整 ERP/MES 前端范围。

## 2. 分层与依赖方向

```text
Vue 页面/业务弹窗
        ↓ 组合用例、保存草稿、处理交互
页面/弹窗 composable（useXxxList / useXxxOptions / useXxxEditor）
        ↓ 业务投影、局部加载、提交编排
src/api
        ↓ HTTP 协议、DTO、错误转换、请求配置
后端 API
```

| 层级              | 应承担                                                       | 不应承担                                    |
| ----------------- | ------------------------------------------------------------ | ------------------------------------------- |
| `src/api`         | URL、method、query/body 类型、`skipErrorHandling` 等协议配置 | 页面 loading、业务筛选、缓存、中文交互提示  |
| 页面级 composable | 正式列表、查询、分页、页面筛选投影、写后刷新                 | 其他页面状态、所有弹窗候选的聚合加载        |
| 弹窗级 composable | 当前编辑目标、关键明细、局部候选、提交前校验和竞态守卫       | 无关弹窗候选、正式列表分页                  |
| Vue 组件          | 展示、输入、事件和调用所属用例 composable                    | 创建 Axios 实例、跨页缓存、散落的多接口编排 |

`src/api` 是唯一 HTTP 入口，但“通过 API 封装调用”不等于组件可以随意编排请求。纯展示组件和通用输入组件
不得发起业务请求；业务弹窗可以调用自身 composable，由 composable 决定本地加载。

## 3. 数据分类与唯一所有者

新增数据状态前必须先归入下表，不允许先写请求再决定放置位置。

| 数据类别     | 示例                                          | 唯一所有者                              | 生命周期                          |
| ------------ | --------------------------------------------- | --------------------------------------- | --------------------------------- |
| 稳定枚举     | 状态码、获取方式、中文映射                    | `packages/constants` / contracts        | 随构建发布，不请求 API            |
| 正式分页列表 | 产品、路线、工单、批次                        | 页面级 `useXxxList`                     | 查询、翻页、写成功后刷新          |
| 页面筛选候选 | 产品筛选中的分类、任务筛选中的负责人          | 页面 composable（`useXxxOptions` 实例） | 首次进入、激活、展开时按需刷新    |
| 弹窗字段候选 | 弹窗表单里的产品、路线、负责人、工序          | 弹窗 composable（`useXxxOptions` 实例） | 打开、激活（仍打开时）、展开刷新  |
| ID 绑定明细  | `materials(productId)`、`routeSteps(routeId)` | 当前业务弹窗 `useXxxEditor`             | 每次切换目标重新加载，不进缓存    |
| 编辑草稿     | 表单字段、BOM 行、路线步骤行                  | 弹窗组件或弹窗 composable               | 随路由 KeepAlive 保留；不跨硬刷新 |

候选源实例的所有权规则（T1）：

1. **谁持有实例，谁负责它的页面激活刷新**。消费者通过 props 接收候选、通过 `refresh-x` 事件触发刷新，
   不得为不持有的源注册 `onActivated`。
2. **同一缓存路由页内，多个消费者使用相同请求契约（同端点、同参数、同有效性口径）时，提升到页面持有一个
   实例**，通过 props 下发给各消费者；投影留在消费侧，允许不同消费者过滤/映射出不同视图。
3. **只有一个消费者时，由最近消费者（页面或弹窗）自持**。跨缓存路由页永远各自实例，最大共享边界是一个
   缓存路由页实例，不得继续提升到 App 或全局 Pinia。
4. **ID 绑定明细不共享**，即使多个调用点存在，也强绑定当前编辑对象，保持局部加载。

## 4. 候选 composable 实例

### 4.1 基础实例 `useRefreshableOptions`

跨页面复用同一套候选加载实现，位置 `src/composables/options/useRefreshableOptions.ts`：

```ts
interface RefreshableOptions<T> {
  options: Readonly<Ref<T[]>>;
  loading: Readonly<Ref<boolean>>;
  status: Readonly<Ref<'idle' | 'loading' | 'ready' | 'error'>>;
  refresh: () => Promise<void>;
}
```

语义：

- 只保存当前实例的候选、`refresh()` 重新请求、last-request-wins、失败保留上次成功快照。
- 无单飞合并：每次 `refresh()` 都重新请求；并发调用由内部 request token 保证最后一次生效（旧响应/旧失败丢弃）。
- 无全局缓存、无失效标记、无 TTL：跨页新鲜度由消费方在页面激活、弹窗打开、下拉展开时调用 `refresh()` 保证。
- 刷新失败保留上次成功结果并弹出局部 warning，`refresh()` 不 reject，调用方无需 catch。
- `status`：`idle` 未请求 / `loading` 请求中 / `ready` 最近一次成功 / `error` 最近一次失败。

### 4.2 资源包装

每个跨页候选端点提供一个薄包装（工厂），复用实现、实例局部持有：

- `useProductOptions()` → `/products/options`；
- `useProductCategoryOptions()`（产品域内，产品页筛选与产品表单、分类页父分类）→ `/categories/options`；
- `useProcessRouteOptions()` → `/process-routes/options`；
- `useUserOptions()` → `/users/options`；
- `useProcessStepOptions()`（产品域内，唯一消费者路线步骤弹窗）→ `/process-steps/options`；
- `useDepartmentOptions()`（System 域内，唯一消费者用户表单弹窗，弹窗自持）→ `/system/departments/options`；
- `useRoleOptions()`（System 域内，用户页岗位筛选、列表角色名、用户表单与分配角色弹窗）→ `/system/roles/options`。

包装只负责绑定请求与失败提示，不含业务投影。业务过滤/映射在消费侧以 `computed` 完成，例如：

```ts
const productSource = useProductOptions();
const finishedProducts = computed(() =>
  productSource.options.value.filter((item) => item.itemKind === 'finished_product'),
);
```

### 4.3 所有权判定

- 候选是否被多个缓存路由页使用？
  - 是：复用同一 composable 工厂，但每个路由页单独创建实例。
- 同一缓存页内是否有多个消费者使用相同请求契约？
  - 是：提升到页面，所有消费者共享一个实例（页面持有并负责激活刷新，弹窗经 props 接收、经 `refresh-x` 触发）。
  - 否：由唯一消费者（页面或弹窗）自持。

### 4.4 刷新与合并

- 最新候选刷新后与当前已选值经 `utils/live-options.ts` 的 `buildLiveOptions` 合并：全量候选刷新成功后，已选值仍存在则正常显示，已消失则显示原始 ID +“已失效”并禁用；`hasUnavailableSelection` 在提交前拦截失效已选值。
- 分页、远程搜索或带数量上限的窗口候选不能根据当前窗口缺失判定失效；调用方必须把当前已选 ID 交给端点补全或显式解析，再以解析结果执行合并与提交守卫。候选端点的完备性和增长迁移规则见 `api-conventions.md` §5.1。
- 合并只保留当前已选失效值，未选中的失效项不残留在下拉列表中。

## 5. 页面、弹窗与 composable 边界

### 5.1 页面正式列表

正式列表使用 `useXxxList` 管理：query、currentPage、pageSize、total、items、loading、服务端分页参数映射、
查询/重置/翻页/刷新，并带列表请求 token（last-request-wins）。列表 composable 不加载弹窗专用候选。

### 5.2 候选 composable

只含候选的 composable 使用 `useXxxOptions` 命名，是共享 `useRefreshableOptions` 工厂的薄消费方：持有实例、
在消费方投影、暴露 `refresh()` 供生命周期接线。不复制原始 `ref`、请求和单飞逻辑。

### 5.3 关键编辑明细

同时管理服务端明细和编辑状态的 composable 使用 `useXxxEditor`。关键明细必须区分三种状态：
“尚未加载 ≠ 服务端返回空集合 ≠ 加载失败”。加载失败不得返回空数组供弹窗继续编辑，也不得覆盖现有草稿；
必须保留错误状态并至少采取一种措施：禁止保存并提供“重新加载”、保持弹窗关闭、明确要求放弃旧草稿后重试。
候选失败可以 best-effort，关键明细失败必须显式失败。

## 6. 生命周期与定向刷新

| 事件         | 正式列表               | 页面筛选候选                        | 弹窗候选             | 关键明细             | 编辑草稿         |
| ------------ | ---------------------- | ----------------------------------- | -------------------- | -------------------- | ---------------- |
| 首次进入页面 | 加载                   | 持有者 `onActivated` 刷新（含首帧） | 未打开不加载         | 未打开不加载         | 初始化           |
| 打开弹窗     | 不刷新                 | 按需                                | 刷新实际依赖         | 按目标 ID 加载       | 明细成功后初始化 |
| 展开某个下拉 | 不刷新                 | 只刷新该筛选资源                    | 只刷新该下拉资源     | 不刷新               | 保留             |
| 页面重新激活 | 按业务需要，不默认重载 | 持有者刷新可见筛选                  | 仍打开的弹窗自持刷新 | 不覆盖正在编辑的明细 | 保留             |
| 写操作成功   | 只刷新受影响列表       | 无需失效（无共享缓存）              | 不连带刷新无关资源   | 按用例关闭或更新     | 成功后清理       |
| 候选刷新失败 | 不受影响               | 保留实例内上次成功                  | 保留实例内上次成功   | 不受影响             | 保留             |

- **M1 首次进入**：`onActivated` 在首次挂载时也会触发，因此页面候选刷新只放在 `onActivated`（同时覆盖首帧
  与再激活），`onMounted` 只加载正式列表与关键明细，避免同一候选首帧双请求。
- **M2 展开刷新**：页面筛选下拉同样在 `@visible-change` 时刷新对应资源，保证同页写操作后下一次展开即可
  自愈，不要求页面间实时同步。
- **M3 失败即严格**：新实例候选首次加载失败时 `options` 为空，已选值经合并显示“已失效”，提交被
  `hasUnavailableSelection` 拦截；实例内没有跨页“上次成功快照”可回退。
- 弹窗打开可以并发刷新其全部必要候选（需要正确显示已有选中值）；展开任意一个下拉只刷新该下拉对应资源，
  不刷新无关资源，也不重新形成“前端聚合端点”语义。

## 7. 异步并发与目标身份守卫

### 7.1 候选 `refresh`（无参共享资源）

同一实例的并发 `refresh()` 由 request token 保证最后一次生效：旧响应写入前检查 token，旧失败不提示。

### 7.2 ID 绑定请求

`materials(productId)`、`routeSteps(routeId)` 等请求必须满足 last-request-wins：请求与目标 ID 一起记录；
新目标不得复用旧目标的在途请求；响应写入前再次确认目标 ID 未变化且请求仍是最新一代；关闭弹窗或切换对象后
到达的旧响应只能丢弃，不能修改草稿或 loading。

### 7.3 列表请求

快速查询、翻页和改变 pageSize 可能响应乱序。列表 composable 使用请求序号确保较旧查询不能覆盖较新查询结果；
loading 的结束只由当前最新请求负责。

### 7.4 写命令的幂等意图（待后端闭环后启用）

只有接口文档明确声明 `Idempotency-Key` 必填且服务端闭环已经完成的命令，前端才建立幂等意图。键状态
由发起写操作的页面/弹窗 composable 局部持有，`src/api` 只接收并转发键，不生成键、不保存状态；不得
放入跨页面 Pinia Store。键绑定“一次尚未确认结果的提交意图”，不绑定点击次数或弹窗 visible 状态；
第一次正式提交才使用 `crypto.randomUUID()`，相同有效载荷的超时、断网、无响应和可重试 5xx 复用原键，
业务有效载荷变化、明确成功或按接口契约明确无副作用的 4xx 后结束旧意图。Axios 自动重试必须沿用请求
配置中的原键，interceptor 禁止生成 UUID。

意图签名的输入不能只取表单 body。每个启用接口必须由契约明确提供稳定 scope、语义 path params、query、
规范化 body 和 version 的字段清单，前端签名覆盖同一组客户端业务输入；任一字段变化都必须作废旧键。
签名只用于前端生命周期判断，不作为安全指纹发送给后端，actorId 等服务端上下文仍由后端计算；用户会话
切换时必须销毁尚未闭环的本地意图。

当前项目没有表单草稿持久化、待提交恢复日志或按幂等键查询结果的接口。局部 composable 只能在自身及
KeepAlive 页面实例存活期间保留 K1；浏览器硬刷新会丢失表单和 K1。只把 key 或 payload hash 写入
`sessionStorage` 不能恢复原请求。若高风险命令要覆盖硬刷新，必须另行实现完整 payload 的安全恢复日志和
恢复 UI，或实现受鉴权的服务端结果查询；当前两者均不存在，不得在文档或测试中宣称已经支持。

幂等键生命周期不能替代弹窗 `submitting` 和行级 pending。完整服务端事务、前端伪代码和启用门槛见
[`http-idempotency-implementation-plan.md`](http-idempotency-implementation-plan.md)。当前尚无业务端点完成
闭环，前端不得提前发送该 header。

## 8. 错误边界

| 请求类型            | 是否 best-effort | 失败后的 UI                                | 是否允许继续保存                         |
| ------------------- | ---------------- | ------------------------------------------ | ---------------------------------------- |
| 正式列表            | 否               | 保留旧列表或显示列表错误                   | 与列表无关的弹窗按自身状态决定           |
| `/options` 动态候选 | 是               | 初次为空；刷新失败保留实例内上次成功并提示 | 已知失效值禁止；高风险用例可要求刷新成功 |
| 关键编辑明细        | 否               | 明确加载失败，不伪装成空数据               | 禁止                                     |
| 写操作              | 否               | 保留草稿，显示业务错误                     | 可修正后重试                             |
| 页面激活后台刷新    | 是               | 不覆盖草稿，不跳转无权限页                 | 依据当前关键数据状态                     |

`/options` API 使用 `skipErrorHandling`，避免一个参考数据 403 触发全局无权限跳转；调用层负责局部提示。

## 9. 权限与跨页面候选契约

- 前端候选实例局部化解决“重复请求、实例隔离、刷新时机”问题；
- 后端 `/options` any-of 权限保证每个合法消费页面的最小角色都能读取需要的候选，契约保持不变。

| 端点                              | 消费页面/弹窗                                      | 页面最小视图权限                                            | 前端原始状态所有者      |
| --------------------------------- | -------------------------------------------------- | ----------------------------------------------------------- | ----------------------- |
| `/products/options`               | 路线表单、产品物料、生产工单、生产任务             | 全部消费页面视图权限的并集                                  | 每消费页面/弹窗独立实例 |
| `/process-routes/options`         | 产品默认路线、生产批次、生产任务                   | 全部消费页面视图权限的并集                                  | 每消费页面/弹窗独立实例 |
| `/users/options`                  | 路线步骤、生产工单/任务页与弹窗                    | 全部消费页面视图权限的并集                                  | 每消费页面/弹窗独立实例 |
| `/process-steps/options`          | 路线步骤                                           | 工序和路线页面约定权限                                      | 路线步骤弹窗实例        |
| `/categories/options`             | 产品页筛选与产品表单、分类页父分类                 | `product:products:view` 与 `product:categories:view` 的并集 | 每消费页面/弹窗独立实例 |
| `/production/work-orders/options` | 生产任务表单已下达且仍有余量的完整候选（本地筛选） | `production:tasks:view`                                     | 任务表单弹窗实例        |
| `/system/departments/options`     | 用户表单弹窗部门下拉                               | `system:user:view`                                          | 用户表单弹窗实例        |
| `/system/roles/options`           | 用户页岗位筛选、列表角色名、用户表单与分配角色弹窗 | `system:user:view`                                          | 用户页实例              |

多个页面消费同一 `/options` 端点只代表复用同一后端契约，不代表前端共享缓存状态。

```text
│     ├─ useProductOptions.ts
│     ├─ useProcessRouteOptions.ts
│     ├─ useUserOptions.ts
│     ├─ useDepartmentOptions.ts
│     └─ useRoleOptions.ts
└─ views/<module>/
   ├─ <Feature>Page.vue
   ├─ components/
   └─ composables/
      ├─ useXxxList.ts        // 正式列表、查询和分页
      ├─ useXxxOptions.ts     // 候选消费方（持有实例 + 消费侧投影）
      └─ useXxxEditor.ts      // 关键明细、编辑状态和提交前校验
```

命名约束：

- `useXxxList`：正式列表、查询和分页；
- `useXxxOptions`：候选消费方或薄包装；
- `useXxxEditor`：关键明细、编辑状态和提交前校验；
- `loadXxx`：加载关键数据或明确允许重复的操作；
- `refreshXxx`：明确重新请求（对应 `useRefreshableOptions.refresh()`）。

不要继续新增含义不清的 `loadData`、`loadOptions`、`refreshOptions`。当函数同时处理多类资源时，其调用点
必须是明确的组合生命周期，内部仍委托给按资源命名的 loader。

## 11. 测试要求

### 11.1 候选实例基础语义

- 每次 `refresh()` 都重新请求；
- 后请求先返回时，旧响应不覆盖（last-request-wins）；
- 旧请求失败不产生错误提示；
- 最新刷新失败保留上一次成功候选并提示；
- 不同页面调用同一 composable 得到独立状态。

### 11.2 页面与弹窗

- 展开一个下拉只调用对应 loader（页面筛选与弹窗字段都是）；
- 弹窗打开并发刷新必要候选，但关键明细失败不会被转换为空草稿；
- 候选刷新不覆盖表单输入和表格行；
- 页面激活时，只由持有者刷新其持有的源；弹窗关闭时不刷新弹窗候选；
- 产品 A/路线 A 的旧响应晚到时不能覆盖产品 B/路线 B；
- 写操作成功只刷新目标列表，不连带刷新无关候选；
- 首次进入不重复请求同一候选（M1）；
- 同页写操作后展开筛选下拉能取到新值（M2）。

### 11.3 权限和契约

- 每个 `/options` 的权限元数据等于全部消费页面视图权限并集；
- 每个最小页面角色都能读取该页面实际请求的全部候选；
- 无任一消费权限的角色仍返回 403；
- 单个候选失败不会导致列表失败或全局 403 跳转。

## 12. 评审清单

新增页面、弹窗或候选端点时逐项确认：

- [ ] 数据已归类为列表、候选、关键明细、草稿或稳定枚举。
- [ ] 同一缓存页内多个同契约消费者共享一个实例（提升到页面），跨页各自实例，无模块级单例或重复 `ref`。
- [ ] 谁持有实例谁负责它的页面激活刷新；消费者只触发刷新，不重复注册生命周期。
- [ ] 业务 filter/map 位于消费侧 computed，不污染原始候选。
- [ ] 页面候选刷新只挂在 `onActivated`（含首帧），`onMounted` 只加载列表与关键明细。
- [ ] 展开一个下拉不会刷新无关资源（含页面筛选下拉）。
- [ ] ID 绑定请求具有目标身份和响应乱序守卫。
- [ ] 写接口只有在服务端闭环和接口契约已启用后才发送幂等键；键由业务意图所有者持有，API wrapper 不生成。
- [ ] 幂等覆盖范围区分 KeepAlive 与浏览器硬刷新；没有待提交恢复机制时不宣称刷新后可复用原键。
- [ ] 关键明细失败不会变成可保存的空数据。
- [ ] 候选刷新不会覆盖 KeepAlive 中的编辑草稿；失效已选值经 `live-options` 合并、可显可拦。
- [ ] 写后只刷新目标列表，不连带刷新无关候选。
- [ ] `/options` 消费权限矩阵、API 文档和最小角色测试保持同步。
- [ ] 已补候选实例、页面生命周期与竞态守卫测试。
