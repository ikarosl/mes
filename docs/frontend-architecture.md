# 管理端前端架构规范

本文是 `apps/admin-web` 的前端代码分层、数据所有权、异步加载、缓存和失效策略的唯一基准。
页面视觉与通用交互以根目录 `design.md` 为准，多标签页、路由弹窗和失效候选的具体接入方式见
`frontCompoentDesgin/DynamicTabSwitching.md`，HTTP 协议以 `api-conventions.md` 为准，通用编码细节以
`coding-standards.md` 为准。

本文解决的核心问题不是“请求应该写在页面还是组件”，而是每类数据必须有唯一、可解释的所有者，
并具有明确的加载、刷新、失效、错误和并发语义。禁止以一个大而全的 `loadData()` 或多个互不相知的
局部缓存代替这些设计。

## 1. 设计目标

- 同一份跨页面参考数据只有一个原始状态来源，不在多个 composable 中复制 `ref` 和请求单飞逻辑。
- 正式列表、动态候选、关键明细和编辑草稿使用不同生命周期，失败时互不拖累。
- 弹窗打开、页面激活和下拉展开能够获得新鲜候选，但不得覆盖用户尚未提交的草稿。
- 写操作只刷新受影响的数据，不以全页面重载掩盖状态所有权不清。
- 所有异步写回都能抵御重复触发、响应乱序、目标切换、页面失活和会话切换。
- 前端权限行为与后端 `/options` 的跨页面授权契约一致，但不把前端可见性当作安全边界。
- 架构决策可以通过类型、测试和代码评审清单验证，而不是依赖约定俗成。

非目标：

- 不引入通用前端数据请求框架或服务端状态库来替代当前 Vue、Pinia 和 `src/api`。
- 不把所有接口响应放进全局 Store；只有真正跨页面共享且语义相同的数据才进入 Pinia。
- 不为 ID 绑定明细预建无限缓存、复杂 TTL、离线同步或跨浏览器标签页一致性。
- 不把管理端扩展为完整 ERP/MES 前端范围。

## 2. 分层与依赖方向

```text
Vue 页面/业务弹窗
        ↓ 组合用例、保存草稿、处理交互
页面/弹窗 composable
        ↓ 业务投影、局部加载、提交编排
Pinia 共享参考数据 Store（仅跨页面共享数据）
        ↓ 原始候选缓存、单飞、失效、会话重置
src/api
        ↓ HTTP 协议、DTO、错误转换、请求配置
后端 API
```

| 层级                 | 应承担                                                       | 不应承担                                           |
| -------------------- | ------------------------------------------------------------ | -------------------------------------------------- |
| `src/api`            | URL、method、query/body 类型、`skipErrorHandling` 等协议配置 | 页面 loading、业务筛选、Pinia 缓存、中文交互提示   |
| Pinia 共享参考 Store | 跨页面原始候选、每资源单飞、缓存状态、失效和会话重置         | 页面专用 DTO、弹窗草稿、按当前行过滤、关键业务明细 |
| 页面级 composable    | 正式列表、查询、分页、页面筛选投影和写后刷新                 | 其他页面状态、所有弹窗候选的聚合加载               |
| 弹窗级 composable    | 当前编辑目标、关键明细、局部候选、提交前校验和竞态守卫       | 无关弹窗候选、正式列表分页                         |
| Vue 组件             | 展示、输入、事件和调用所属用例 composable                    | 创建 Axios 实例、跨页面缓存、散落的多接口编排      |

`src/api` 是唯一 HTTP 入口，但“通过 API 封装调用”不等于组件可以随意编排请求。纯展示组件和通用
输入组件不得发起业务请求；业务弹窗可以调用自身 composable，由 composable 决定本地加载还是委托共享 Store。

## 3. 数据分类与唯一所有者

新增数据状态前必须先归入下表，不允许先写请求再决定放置位置。

| 数据类别       | 示例                                           | 唯一所有者                                | 生命周期                                |
| -------------- | ---------------------------------------------- | ----------------------------------------- | --------------------------------------- |
| 稳定枚举       | 状态码、获取方式、中文映射                     | `packages/constants` / contracts          | 随构建发布，不请求 API                  |
| 正式分页列表   | 产品、路线、工单、批次                         | 页面级 `useXxxList`                       | 查询、翻页、写成功后刷新                |
| 页面筛选投影   | 产品筛选中的分类、任务筛选中的负责人           | 页面 composable；原始数据可来自共享 Store | 首次进入、激活、展开时按需刷新          |
| 跨页面参考候选 | 产品、路线、用户，以及被多个正式页面消费的分类 | Pinia 共享参考 Store                      | cache-first 获取，按资源主动刷新和失效  |
| 单弹窗候选     | 仅路线步骤弹窗使用的工序候选                   | 弹窗 composable                           | 打开、对应下拉展开、页面重新激活        |
| ID 绑定明细    | `materials(productId)`、`routeSteps(routeId)`  | 当前业务弹窗 composable                   | 每次切换目标重新加载，不进入全局缓存    |
| 编辑草稿       | 表单字段、BOM 行、路线步骤行                   | 弹窗组件或弹窗 composable                 | 随路由 KeepAlive 保留，候选刷新不得覆盖 |
| 会话和标签页   | 当前用户、Token 内存态、应用标签               | 既有 Auth/Tabs Pinia Store                | 按认证与路由基础设施管理                |

判断一类候选是否进入共享 Store，必须同时满足：

1. 两个或以上独立页面/业务组件消费同一端点的同一原始响应语义；
2. 刷新后应自动传播到其他消费者；
3. 可以定义可靠的失效和会话重置边界。

仅仅调用了同一个 API 并不足以共享。`materials(productId)` 和 `routeSteps(routeId)` 虽有多个调用点，
但它们强绑定当前编辑对象、失败影响关键业务编辑，默认保持局部加载。若未来要缓存，必须先补充按 ID
上限、失效来源和版本一致性设计。

## 4. 跨页面参考候选 Store

跨页面共享状态必须使用 Pinia。禁止用模块顶层 `ref`、导出可变单例或隐藏在普通 composable 中的
进程级缓存代替 Pinia；这些方式缺少用户切换重置、测试隔离、调试可见性和明确生命周期。

建议在 `apps/admin-web/src/stores/reference-options.ts` 建立共享参考 Store。当前适合收敛的原始资源包括：

- 产品 `productOptions()`；
- 工艺路线 `routeOptions()`；
- 用户 `userOptions()`；
- 产品分类 `categoryOptions()` 在产品页与分类页都正式消费时也应进入共享层。

工序候选目前只有路线步骤弹窗消费，可以保留局部；后续出现第二个独立消费页面时再迁入共享层。

### 4.1 每资源独立状态

每一类共享资源必须独立维护：

```ts
interface OptionResourceState<T> {
  items: T[];
  status: 'idle' | 'loading' | 'ready' | 'refreshing' | 'error';
  error: unknown | null;
  loadedAt: number | null;
  isInvalidated: boolean;
}
```

在途 Promise、请求代次和 AbortController 属于运行时协调状态，可以保留在 setup store 闭包中，不需要
序列化为 Pinia state。产品、路线、用户之间不得共享一个 `optionsRequest` 或一个 `loading`。

### 4.2 标准操作语义

每一类资源提供一致但彼此独立的操作：

```ts
ensureProducts();
refreshProducts();
invalidateProducts();

ensureRoutes();
refreshRoutes();
invalidateRoutes();

ensureUsers();
refreshUsers();
invalidateUsers();
```

- `ensureXxx()`：cache-first。已有未失效的成功快照时直接返回；未加载或已失效时请求。
- `refreshXxx()`：明确请求最新快照；若同资源已有在途请求，则返回同一个 Promise。
- `invalidateXxx()`：只标记陈旧，不立即产生网络请求；下一个合法生命周期再 `ensure`/`refresh`。
- `$reset()`：清空所有快照、错误、失效标记和请求代次；退出登录、切换用户或权限上下文变化时必须执行。

不得提供供所有下拉调用的通用 `refreshAll()`。页面首次启动或弹窗打开确需多类候选时，可以在调用侧
通过 `Promise.allSettled` 并发调用多个独立操作；展开某个下拉时只刷新该下拉对应的资源。

### 4.3 失败与最后成功快照

共享缓存的失败策略与局部候选不同：

- 首次加载失败：保持空数组，状态设为 `error`；当前候选不可用，但不拖累列表或关键明细。
- 已有成功快照后刷新失败：保留最后成功快照，记录 `error` 并标记陈旧；禁止把一次网络失败传播成
  所有已打开页面候选同时清空。
- 成功刷新：原子替换原始 `items`，清除错误和失效标记；业务投影通过 computed 自动更新。
- 交互提示按实际请求最多显示一次；不得由共享请求的多个调用者重复弹出同一错误。

保留最后成功快照不代表它仍然有效。提交前继续使用 `live-options` 检查已知失效项，最终由后端重新校验
权限、状态、版本和业务关系。如果无法确认候选新鲜度且该动作风险较高，业务弹窗可以根据资源错误状态
禁用保存并要求重新刷新。

### 4.4 业务投影留在消费侧

共享 Store 只保存接口返回的原始最小字段，不保存下列页面语义：

- “自制且非原材料产品”；
- “排除当前产品的 BOM 候选”；
- 工单、批次专用的字段重命名；
- “当前产品已启用路线”；
- Element Plus 的 `{ label, value }` 结构。

这些过滤和映射由页面或弹窗 composable 使用 computed 完成。这样多个消费方共享新鲜度和请求状态，
但不会把某个页面的业务规则写进全局缓存。

## 5. 页面、弹窗与 composable 边界

### 5.1 页面正式列表

正式列表使用 `useXxxList` 管理：

- query、currentPage、pageSize、total、items、loading；
- 服务端分页参数映射；
- 查询、重置、翻页和列表刷新；
- 列表请求的响应乱序保护。

列表 composable 不加载弹窗专用候选，不提供“列表 + 全部候选”的 `loadData()`。初次页面组合可以并发
调用 `loadList()` 和必要的页面筛选 `ensureXxx()`，但两者必须有独立错误边界。

### 5.2 候选 composable

只包含候选的 composable 使用 `useXxxOptions` 命名。它可以是共享 Store 的薄业务适配器，例如：

- `useProductFormOptions`：委托共享产品资源，投影为自制半成品/成品；
- `useProductRouteOptions`：委托共享路线资源，按当前产品过滤已启用路线。

薄适配器的价值是保留业务语义和组件依赖边界，不应重新复制原始 `ref`、单飞 Promise 和 HTTP 请求。

### 5.3 关键编辑明细

同时管理服务端明细和编辑状态的 composable 使用 `useXxxEditor`，不要以 `Options` 命名掩盖其关键数据职责。
例如产品 BOM 和路线步骤更适合命名为 `useProductMaterialEditor`、`useRouteStepEditor`。

关键明细必须区分三种状态：

```text
尚未加载 ≠ 服务端返回空集合 ≠ 加载失败
```

加载失败不得返回空数组供弹窗继续编辑，也不得覆盖现有草稿。弹窗必须保留错误状态，并采取至少一种措施：

- 禁止保存并提供“重新加载”；
- 保持弹窗关闭；
- 明确要求用户放弃旧草稿后重试。

候选失败可以 best-effort，关键明细失败必须显式失败。两者即使并发请求，也要分别检查结果，禁止用一个
`catch` 或一次空数组赋值合并语义。

## 6. 生命周期与定向刷新

| 事件         | 正式列表               | 页面筛选候选         | 弹窗候选               | 关键明细             | 编辑草稿         |
| ------------ | ---------------------- | -------------------- | ---------------------- | -------------------- | ---------------- |
| 首次进入页面 | 加载                   | `ensure`             | 未打开不加载           | 未打开不加载         | 初始化           |
| 打开弹窗     | 不刷新                 | 按需                 | 刷新弹窗实际需要的资源 | 按目标 ID 加载       | 明细成功后初始化 |
| 展开某个下拉 | 不刷新                 | 只刷新该筛选资源     | 只刷新该下拉资源       | 不刷新               | 保留             |
| 页面重新激活 | 按业务需要，不默认重载 | 刷新可见筛选         | 只刷新仍打开弹窗的候选 | 不覆盖正在编辑的明细 | 保留             |
| 写操作成功   | 只刷新受影响列表       | 仅标记受影响资源失效 | 不连带刷新无关资源     | 按用例关闭或更新     | 成功后清理       |
| 候选刷新失败 | 不受影响               | 局部错误             | 局部错误               | 不受影响             | 保留             |

弹窗打开时并发加载其全部必要候选是合理的，因为需要正确显示已有选中值；展开任意一个下拉又刷新全部候选
是不合理的。数据来自不同端点，不具有原子快照语义，也不应共享失败域。

主动刷新按钮必须与实际作用域一致：“刷新工序”只能刷新工序；如果确需刷新弹窗全部候选，按钮必须明确
命名为“刷新全部候选”，并且仍通过各资源独立 loader 组合。

## 7. 写操作后的失效矩阵

每个写用例必须在实现前列出“刷新列表”和“失效参考资源”，禁止统一调用全页面 `loadData()`。

| 写操作示例             | 立即网络刷新                | 只失效、不立即请求             | 不应刷新                 |
| ---------------------- | --------------------------- | ------------------------------ | ------------------------ |
| 新增/编辑/启停产品     | 当前产品列表                | 产品 options                   | 分类、路线、用户 options |
| 新增/编辑/启停分类     | 当前分类列表                | 分类 options                   | 产品、路线、用户 options |
| 新增/编辑/状态流转路线 | 当前路线列表                | 路线 options                   | 产品、用户 options       |
| 保存产品 BOM           | 依赖 BOM 摘要的当前产品列表 | 视业务是否影响其他候选，默认无 | 分类、路线、用户 options |
| 保存路线步骤           | 依赖步骤摘要的当前路线列表  | 默认无                         | 产品、路线、用户 options |
| 修改用户启停状态       | 当前用户列表                | 用户 options                   | 产品、路线 options       |

如果写操作发生在另一个页面，共享 Store 的失效标记使下一次 `ensure` 能获取新数据；如果相关弹窗正打开，
页面激活或用户展开下拉时会执行定向 `refresh`。不要求写操作同步等待所有潜在消费者刷新。

## 8. 异步并发与目标身份守卫

### 8.1 无参数共享资源

同一资源并发调用只产生一个请求。`finally` 清理时必须验证当前 Promise 身份，避免旧请求清掉后来请求：

```ts
const current = fetchOptions();
request = current;
try {
  await current;
} finally {
  if (request === current) request = null;
}
```

Store reset 必须增加 generation/epoch。旧会话请求即使随后成功，也不得重新写入新会话 Store。

### 8.2 ID 绑定请求

`materials(productId)`、`routeSteps(routeId)` 等请求必须满足 last-request-wins：

- 请求与目标 ID 一起记录；
- 新目标不得复用旧目标的在途 Promise；
- 能取消时使用 AbortController；不能取消时使用递增序号或 generation；
- 响应写入前再次确认弹窗仍可见、目标 ID 未变化且请求仍是最新一代；
- 关闭弹窗或切换对象后到达的旧响应只能丢弃，不能修改草稿或 loading。

`loading: boolean` 只能代表一个明确请求域。多个独立资源并发时使用独立 loading/status，或使用请求计数，
不得让先完成的请求把另一个仍在执行的 loading 提前置为 false。

### 8.3 列表请求

快速查询、翻页和改变 pageSize 也可能响应乱序。列表 composable 必须使用请求序号或取消机制，确保较旧查询
不能覆盖较新查询结果。loading 的结束同样只由当前最新请求负责。

## 9. 错误边界

| 请求类型            | 是否 best-effort | 失败后的 UI                              | 是否允许继续保存                         |
| ------------------- | ---------------- | ---------------------------------------- | ---------------------------------------- |
| 正式列表            | 否               | 保留旧列表或显示列表错误                 | 与列表无关的弹窗按自身状态决定           |
| `/options` 动态候选 | 是               | 初次为空；刷新失败保留最后成功快照并提示 | 已知失效值禁止；高风险用例可要求刷新成功 |
| 关键编辑明细        | 否               | 明确加载失败，不伪装成空数据             | 禁止                                     |
| 写操作              | 否               | 保留草稿，显示业务错误                   | 可修正后重试                             |
| 页面激活后台刷新    | 是               | 不覆盖草稿，不跳转无权限页               | 依据当前关键数据状态                     |

`/options` API 使用 `skipErrorHandling`，避免一个参考数据 403 触发全局无权限跳转；调用层负责局部提示。
这不会改变认证刷新流程，也不能用于普通正式列表、关键明细或写操作。非 `/options` 的分页接口不得仅因被下拉
复用就设置该标记；应先按 `api-conventions.md` 建立正式候选端点。

## 10. 权限与跨页面候选契约

前端共享 Store 和后端授权解决不同问题：

- Pinia 共享层消除重复请求、统一缓存和刷新语义；
- 后端 `/options` any-of 权限保证每个合法消费页面的最小角色都能读取需要的候选。

新增或迁移共享候选时必须维护消费矩阵：

| 端点                      | 消费页面/弹窗                          | 页面最小视图权限           | 前端原始状态所有者      |
| ------------------------- | -------------------------------------- | -------------------------- | ----------------------- |
| `/products/options`       | 产品 BOM、路线表单、生产工单、生产任务 | 所有这些页面视图权限的并集 | 共享参考 Store          |
| `/process-routes/options` | 产品默认路线、生产工单、生产任务       | 所有这些页面视图权限的并集 | 共享参考 Store          |
| `/users/options`          | 路线步骤、生产工单、生产任务           | 所有这些页面视图权限的并集 | 共享参考 Store          |
| `/process-steps/options`  | 路线步骤                               | 工序和路线页面约定权限     | 路线步骤弹窗 composable |

消费矩阵必须以代码搜索结果为依据，并由后端元数据契约测试覆盖最小权限角色。前端不能通过“严格资源权限 +
吞掉 403”掩盖授权收紧；吞掉错误只负责故障隔离，不负责授予合法能力。

## 11. 推荐目录与命名

```text
apps/admin-web/src/
├─ api/
│  └─ product.ts
├─ stores/
│  ├─ auth.ts
│  ├─ tabs.ts
│  └─ reference-options.ts
└─ views/product/
   ├─ ProductsPage.vue
   ├─ components/
   │  ├─ ProductMaterialDialog.vue
   │  └─ RouteStepDialog.vue
   └─ composables/
      ├─ useProductsList.ts
      ├─ useProductFormOptions.ts
      ├─ useProductMaterialEditor.ts
      └─ useRouteStepEditor.ts
```

命名约束：

- `useXxxList`：正式列表、查询和分页；
- `useXxxOptions`：只管理或投影候选；
- `useXxxEditor`：关键明细、编辑状态和提交前校验；
- `useXxxStore`：跨页面 Pinia 状态；
- `loadXxx`：加载关键数据或明确允许重复的操作；
- `ensureXxx`：cache-first；
- `refreshXxx`：明确重新请求；
- `invalidateXxx`：只标记陈旧。

不要继续新增含义不清的 `loadData`、`loadOptions`、`refreshOptions`。当函数同时处理多类资源时，其调用点
必须是明确的组合生命周期，内部仍委托给按资源命名的 loader。

## 12. 测试要求

### 12.1 共享参考 Store

- `ensure` 并发调用同一资源只请求一次；
- 用户刷新不会请求产品或路线，任一资源失败不修改其他资源；
- `refresh` 在已有缓存时仍会请求；
- 已有成功快照后刷新失败会保留旧值并记录错误；
- `invalidate` 后的 `ensure` 会重新请求；
- logout/reset 后旧会话响应不能回填；
- 多个业务投影共享同一个原始 ref，且各自过滤互不污染。

### 12.2 页面和弹窗 composable

- 展开一个下拉只调用对应 loader；
- 弹窗打开可以并发加载必要候选，但关键明细失败不会被转换为空草稿；
- 候选刷新不覆盖表单输入和表格行；
- 产品 A/路线 A 的旧响应晚到时不能覆盖产品 B/路线 B；
- 写操作成功只刷新目标列表并失效准确的共享资源；
- 写操作失败保留草稿。

### 12.3 权限和契约

- 每个 `/options` 的权限元数据等于全部消费页面视图权限并集；
- 每个最小页面角色都能读取该页面实际请求的全部候选；
- 无任一消费权限的角色仍返回 403；
- 单个候选失败不会导致列表失败或全局 403 跳转。

## 13. 评审清单

新增页面、弹窗或候选端点时逐项确认：

- [ ] 数据已归类为列表、共享候选、局部候选、关键明细、草稿或稳定枚举。
- [ ] 跨页面相同原始候选使用 Pinia，没有新的模块级单例或重复 `ref`。
- [ ] 业务 filter/map 位于消费侧，没有污染共享原始状态。
- [ ] 展开一个下拉不会刷新无关资源。
- [ ] ID 绑定请求具有目标身份和响应乱序守卫。
- [ ] 关键明细失败不会变成可保存的空数据。
- [ ] 候选刷新不会覆盖 KeepAlive 中的编辑草稿。
- [ ] 写后只刷新目标列表，并准确 invalidate 受影响候选。
- [ ] 会话退出/切换会 reset 共享缓存，旧请求不能回填。
- [ ] `/options` 消费权限矩阵、API 文档和最小角色测试已同步。
- [ ] 已补单飞、失败隔离、乱序响应和草稿保留测试。

## 14. 当前整改映射

基于当前正式页面，目标归属如下：

| 数据          | 目标所有者                                | 迁移说明                                                |
| ------------- | ----------------------------------------- | ------------------------------------------------------- |
| 产品 options  | 共享参考 Store                            | Product、Route、Production 消费侧保留各自 computed 投影 |
| 路线 options  | 共享参考 Store                            | 默认路线、工单和任务共用原始快照                        |

| 分类 options  | 共享参考 Store 或迁移期薄适配器           | 产品页和分类页的原始数据应最终单一来源                  |
| 工序 options  | 路线步骤弹窗 composable                   | 当前无跨页面重复，不提前全局化                          |

全仓只有共享层负责其原始候选状态和请求协调，消费方仅持业务投影或当前选中值。
