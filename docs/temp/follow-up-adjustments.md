# 后续调整规划

本文按本次讨论整理已确定方向、后置优化和待决问题，作为后续设计入口；不替代各模块当前有效规范，也不表示尚未实施的能力已上线或验收通过。当前范围与所有者分别见[产品范围](../product-scope.md)和[文档索引](../README.md)。

## 顺序与状态

| 顺序 | 能力 | 当前决定与状态 |
| --- | --- | --- |
| 1 | 来料质检补充表格 | 确定为下一优先项，未实施；与效期分开交付 |
| 后续 | 不合格品线下结果登记 | 一期采用线下审批、线上登记结果；未实施 |
| 后续 | 报废、补产、追加用料解耦 | 方向已确定，未实施；旧流程切换和误确认纠正仍需设计 |
| 后置优化 | 打印、报表、导出及审批共用结构模板 | 确定为后置方向，先完善业务流程；未实施 |
| 待确认后置建议 | 批次效期 | 尚未形成完整实施裁决，不随质检表格接入 |

各阶段沿用[交付顺序](../../AGENTS.md#数据库与交付约定)。当前没有正式测试集及数据集的编写／调整授权；应用类型、构建和启动验证不代表业务验收或正式测试通过。

## 来料质检：补充记录复用 JSON 表格

下一阶段只接来料质检。模板由 [Template](../../apps/api/src/modules/template/docs/template-scenes.md)维护，填写结果归 [Quality](../../apps/api/src/modules/quality/docs/unified-inspection-model.md)，不改变 Procurement 的来源编排及仓库定稿职责。

附件一的检验项目、验收要求、工具、内容描述和结果可作为列，外观、包装、材料证明、数量等可作为预设行。沿用现有 `JsonTableData`、模板选择器和编辑器，将完整表格复制到检验草稿，并随本次检查事实保存；修改或停用模板不联动历史结果。

表格用于补充登记、查看和后续输出。合格／不合格数量、明确结论、检查时间继续使用所属业务字段；自由文本不隐式驱动数量、放行或入库授权。历史未记录内容保持为空，不批量套入默认模板。

这一阶段不包括有效期、文件上传、强制检验方案、数值上下限自动判定或项目级统计；成品和工序检查可在实际接入时复用表格工具，但不为此预先统一提交入口。是否按物料指定默认模板或强制项目，须另行确认。

数据库变更归 Quality，通过追加成对 migration 承接；检查事实的不可变性和历史保留继续遵守[Quality 数据库](../../apps/api/src/modules/quality/docs/database.md)。

## 不合格品：一期登记线下处置结果

已确定一期保留线下分析、审理和审批过程，系统登记其结果及依据。生产异常处置仍由 [Production](../../apps/api/src/modules/production/docs/database/execution-traceability-quality.md)所有，检查事实继续归 Quality。

单据类别与处置结果分开表达：“处理单／审理单”是办理路径，“返工／报废等”是处理结论。两类纸单均可能出现返工，不能用能否返工机械决定单据类别。

结果登记需能够关联真实来源、线下单据和对应数量；最低资料建议为单据类别、单号、处置结果、数量与单位、必要依据，以及系统登记人和时间。线下批准人与日期只能按真实证据填写，不由登记人或登记时间推造。具体必填项、一张纸单对应多项结果的数量守恒及单据分类规则仍需在实施前定案。

现有返工执行和结果事实继续承接实际办理，登记同意返工不等于返工完成。特采、降级、让步、退货等结果的业务效果须分别设计，不能仅增加选项便取得放行或库存资格。完整线上审理、会签及条件分支后置；当前 Approval 的顺序节点不自动等同于多人会签。

## 报废、补产与追加用料：分开决定

后续已确定将三项决定分开：确认报废形成报废事实；管理人员另行确认是否补产、补产数量及适用范围；需要额外物料时独立提需，复用既有需求、分配和领料能力。

新方案中，补料齐套不再作为补产授权生效门禁。补产授权单只采用以下生命周期：

| 状态 | 允许行为与影响 |
| --- | --- |
| 草稿 | 可编辑、确认或取消；不产生有效补产额度 |
| 已确认 | 授权生效；不提供普通修改或取消入口 |
| 已取消 | 保留历史，不产生有效额度 |

仅允许草稿取消。已确认授权误登记的纠正另行设计，不通过直接回改授权或数据库解决。补料需求的分配、领料及履约状态仍独立存在，不能压缩成授权单的三个状态；补产授权也不替代任务、工序及权限校验。

此方向尚未实施。当前[需求与履约](../../apps/api/src/modules/production/docs/database/demand-allocation-and-outbound.md)和[生产执行](../../apps/api/src/modules/production/docs/database/execution-traceability-quality.md)仍描述旧的补料齐套激活链路。实施前须明确补产数量上限、起始及适用工序、重复授权保护，以及旧草稿、在途补料和已生效授权的切换规则；保留已有报废、需求、领料与授权事实，不自动将旧记录追认为新语义。

## 打印、报表、导出与审批：共用可保存的结构模板

本项确定为后置优化，业务流程完善后再推进。目标是统一维护受控数据源引用、字段绑定和可拖拽编辑并保存的表格结构，让打印、报表、数据导出及审批内容展示复用。

共同结构可以表达标题、分组、行列、合并单元格和明细循环；屏幕与纸面采用各自的渲染适配，纸张、分页、重复表头等作为输出配置，不要求两套重复表格定义。修改已有字段的标题、顺序、布局或展示列，目标是不再修改各业务页面组件。

业务模块仍拥有数据来源、权限和计算口径，模板选择已公开字段，不接任意 SQL、接口地址或脚本；新增业务数据、计算口径及审批规则仍需所属模块支持。审批使用送审证据并固定采用的模板版本，不用当前可变单据替代受审内容；关键数量、结论和处理记录保持必显边界。既有证据职责见[审批场景接入](../../apps/api/src/modules/approval/docs/subject-integration.md)。

现有 Template 是“复制后独立保存”的录入表格，尚不是拖拽输出引擎，其编辑并发版本也不是模板发布版本。后续可以复用结构工具或管理入口，但不能直接套用现有版本语义。渲染引擎、字段目录、发布与历史版本保存、各输出格式能力及具体模块所有权仍待专项设计；先以真实复杂纸单验证，再逐步替换内置展示与打印。

## 批次效期：后置建议，尚待完整裁决

效期与质检补充表格是两项能力。建议区分主数据的默认保质期限、检验确认的实物生产日期／实际到期日，以及库存批次采用的效期；这些字段参与查询和归批，应结构化，不只写入自由 JSON。

建议的职责分配为 Product 提供默认配置、Quality 保存确认依据、Procurement／Production 沿正式授权传递依据、Inventory 管理实际批次属性和预警。成品与物料均可支持管理，但默认值落基础物料还是精确版本、无须管理与历史未知的区分仍需定案。

当前[库存批次](../../apps/api/src/modules/inventory/docs/database/inventory-ledger-and-inbound.md#6-item_batch)允许多个来源共批，不能据来源集合推算每份来源剩余量。推荐一期同身份、同单位且生产日期和到期日一致才共批，不同日期另批；这是待确认方案，不预先引入批内分层消耗模型。

实施前还需裁定：

- 一条来料或一份成品产出包含多个实物日期时的登记粒度；来料可评估利用现有到货拆行能力，成品不能默认一个任务只有一个日期。
- 其他入库的登记主体和依据、生产退料是否沿用原批次效期，以及历史未知效期的受控补录。
- 复检是否只更正误登记、是否允许重新评定期限；不得隐式延长已入库批次。
- 临期阈值、到期当日的含义，以及仅预警还是进一步阻止分配／领料的范围。

历史日期不能从创建时间、收货时间或当前默认期限推造；主数据修改不重算旧库存。数据转换与无法无损转换的处置按[数据库与交付约定](../../AGENTS.md#数据库与交付约定)执行。

## 抽离与实施边界

继续保持[模块化单体](../architecture.md#1-架构风格与当前范围)。优先在现有所有者内部拆清报废、补产授权和需求用例；打印专项再建立数据与渲染契约；效期实施时再集中 Inventory 的归批校验和日期计算。现有 JSON 表格工具直接复用，不为这些方向预建通用表单平台、统一质量案件平台、微服务或第二套需求／库存事实。

正式落地时，将新增长期规则维护到对应所有者文档，并修订被明确取代的旧边界；本文保留剩余规划和待决问题，不积累实现经过、命令输出或已完成修改清单。
