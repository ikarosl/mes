# ADR-0008：单节点待办与角色或指定用户审批

状态：Accepted

## 背景

原 Approval 在节点激活时按角色成员创建多条个人任务，处理资格要求同时拥有当前轮任务并满足实时角色权限。新增角色成员无法自动处理已激活的节点，必须人工重新分派；这一成本不符合“同级任意一人决定”的业务需求。

本决策取代 [ADR-0006](0006-approval-workflow-boundaries.md) 中角色生成个人任务及人工重新分派的语义，并增加节点指定单个用户的配置方式。

## 决策

1. 每个申请的每个节点只有一项共同待办；多级流程仍有多个顺序节点，不把整张申请的全部级别合并为一项任务。节点执行记录是唯一待办事实，移除按候选用户生成任务及分派轮次的设计。
2. 每个流程节点在“一个角色”与“一个指定用户”之间二选一。角色和用户是两种资格规则，不是同时满足的条件；首期不包含多个角色、多名指定用户、会签、认领、代理或转交。
3. 申请固定已发布流程版本、节点顺序、分配类型和对应角色 ID 或用户 ID。角色节点按该角色当前的有效成员判断资格；指定用户节点按固定用户 ID 判断资格。两者均实时校验账号及 `approval:decide` 权限，不因被配置为审批人而自动授予权限。
4. 待办查询和审批命令都由后端按登录身份校验当前申请、当前活动节点和上述资格。前端只传分页、scope、状态及业务筛选；命令传目标节点、申请版本和意见。前端提交的角色、用户或可处理标志不能成为授权依据。
5. 角色新增合格成员后，该成员可查询并处理尚未完成的活动节点；成员移除或资格失效后不能处理。没有合格人时保留活动节点并派生阻塞提示，人员恢复后自然可处理，不因读取而更新表，也不需要重新分派才能解锁。
6. 指定用户节点不会随角色成员变化转给其他人。指定用户停用或失去权限时保持待处理并提示阻塞，恢复其资格后继续；发布新流程不改变在途申请。首期不自动替换指定人，申请人仍可按现有规则撤回后使用新流程重新提交。
7. 任意一名合格人员明确决定后完成本节点；通过申请/节点锁及版本校验保证并发只接受一次有效决定，节点、业务生效、处理人记录和成功审计同事务。历史真实处理人、时间、意见及受审证据保持不变，允许自审与同人逐级处理的既有规则不变。
8. 后续接入 Notification 时，当前节点激活在同事务内解析当时合格人员；有接收人时发布一条节点通知并为各接收用户保存收件记录。发布及送审时无合格人员仍由 Approval 拒绝；在途节点无人可审时按第 5 条保留节点并提示，空收件跳过通知创建，不因收件集合为空而回滚前级有效决定。尚未激活节点不提前发送；角色新成员不补写旧收件记录，也不以收到通知作为查看或审批资格。结果通知继续发申请人，外部扩展遵守 [ADR-0007](0007-general-notification-boundaries.md)。

## 查询与历史可见性

当前活动节点的合格人员必须能够查看并处理申请，即使没有历史任务或通知。申请人和实际作出过审批决定的人员保留历史访问资格；明确的全局管理权限继续按接口入口控制。

仅“曾经是候选人”或“曾经收到通知”不单独保留历史全文查看权；不得沿用个人任务表的存在性判断，也不能因为后来加入角色就授予该角色所有已结束申请的历史权限。全局读取限 `approval:configure`；`approval:view` 仅授予接口入口能力。列表与详情遵守同一规则，真实处理人的访问仍须满足接口入口权限及有效账号要求。

## 实施边界

具体结构与审批接入见[审批设计](../approval-design.md)，规则验证见[测试策略](../testing-strategy.md)。流程配置、待办查询、决定命令、历史可见性及前端展示必须使用同一规则；不能只替换待办列表查询而保留个人 taskId 授权。

开发环境允许通过统一 migration/seed 完全重置数据库，不保留兼容数据或建设双写、影子表；变更只能追加 migration。先保证程序可启动并由用户黑盒及 UI 确认，再进入测试集编写阶段。
