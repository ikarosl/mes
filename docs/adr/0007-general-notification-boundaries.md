# ADR-0007：通用通知与事务提交后扩展边界

状态：Accepted（后续通知设计；Notification 与提交后钩子尚未实施）

## 背景

[ADR-0006](0006-approval-workflow-boundaries.md) 约定未来站内通知与审批动作同事务落库，首期不接外部渠道。通知还将服务其他业务模块，不能将公开发布能力和事件模型绑定到 Approval；同时需要为将来的外部通知保留事务提交后的非阻塞扩展入口。

本决策补充通用模块和钩子边界，保留首期站内通知范围，不扩大当前 BOM 审批实现范围。

## 决策

1. Notification 是独立的通用业务模块，拥有消息、收件和阅读状态，Approval 只是首个调用方。各业务模块确定触发条件、具体收件人、事件身份及最小摘要，通过 Notification 的 `public.ts` 发布；业务详情与操作资格仍归业务所有者。
2. 站内通知、收件人、业务写入及成功审计在同一 MySQL 事务中提交，核心落库失败整体回滚。成功审计使用统一公共 writer，跨模块不直接写对方表。
3. 预留 Notification 的统一提交后通知端口，首期默认空实现。只在最外层事务确认提交成功并释放连接后异步调度；SQL 完成或内部回调返回不得提前触发。回滚和未确认成功的提交不触发，失败事务尝试的待触发事件必须丢弃。
4. 业务响应不等待钩子完成；调度和处理失败独立捕获，不改变已提交的业务结果。钩子只接收轻量已提交数据，不持有事务连接、请求对象或渠道凭证，不承担核心业务落库。
5. 事件键跨业务命名空间稳定唯一。同键同内容复用原通知，同键不同内容或收件集合拒绝；并发去重以数据库唯一约束为准。只有实际新建并成功提交的通知登记钩子；同键复用和 HTTP 成功重放不重复调度。
6. 通知已读、业务待办完成、外部投递状态分别管理。本人历史通知直接展示，不随目标业务权限变化隐藏；Notification 只保证登录身份及本人收件隔离。跳转使用既有路由守卫，目标详情和操作由业务后端独立鉴权，通知历史与链接不授予业务权限。
7. 进程内钩子仅为 best-effort，不保证宕机补发、外部恰好一次或严格顺序。首期不接外部渠道，不预建队列、outbox 或投递任务；可靠外部投递需要另行设计持久化任务、幂等、恢复与失败处置后才能启用。
8. `event_type` 表达事件类型，来源与跳转目标分别可选，每组类型/ID 必须成对为空或有值。正文统一为纯文本，有目标时由前端集中维护 `target_type` 到路由和详情定位方式的映射，呈现“查看详情”链接；无目标直接展示，不持久化正文内的 URL 或富文本链接。首期纯系统通知仍保留真实人工操作者，不建设定时提醒或无人系统作业。
9. 具体收件人与业务资格由业务模块确定，Notification 不重查角色、业务权限和账号启停，也不排除操作者本人。新事件空收件时明确跳过创建，不写表、不触发钩子；已有同键仍遵守一致性检查。历史收件集合固定，停用或角色变化不改写；无收件不代表全员广播。
10. 首期后端落库、前端主动拉取；点击具体通知即提交已读写请求，数据库保留首次已读时间。拉取列表不写状态，目标访问失败不撤销已读，标记请求失败不能只在前端宣称成功。暂不提供手动标记、全部已读、推送或多标签页同步。
11. 通知与收件记录默认长期保留，不做删除、到期清理或定期归档功能。人工备份与数据清理分别管理，年度备份不自动授权年度清空；未来清理须另行维护关联数据、追溯和去重身份的运维方案。

## 影响与实施边界

继续采用模块化单体、端口适配器和同库事务，不创建独立通知微服务。数据库基础设施仅提供通用事务生命周期能力，不承载通知或审批业务语义；application 契约不暴露数据库或 SDK 类型。

通用候选结构与钩子细节由[通知设计](../notification-design.md)统一维护，审批文档仅描述审批触发规则。当前通知表、接口和钩子均未实现；新增模块时再登记所有者文档、权限、共享代码并追加 migration，测试安排遵守用户黑盒与 UI 确认后的阶段约定。

首期实施细节与外部渠道待办记录于[路线图](../roadmap.md#通用通知后续实施)，不因本 ADR 预先创建对应表或功能。
