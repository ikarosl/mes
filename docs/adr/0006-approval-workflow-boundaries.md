# ADR-0006：工单、BOM 与顺序多级审批的业务边界

状态：Accepted（BOM 审批纳入本次试探；工单审批和通知仍为后续设计）

节点分配与人员变更规则由 [ADR-0008](0008-approval-node-assignees.md) 取代：每级一个角色或一个指定用户，节点共享待办按实时资格查询，移除个人任务与人工重新分派。本 ADR 下方对应段落保留原决策背景，以 ADR-0008 及模块所有者文档为当前规则。

## 背景

销售取得外部下单通知后，研发先建立成品资料、占用成品编码，再逐步完善 BOM。销售需要在 BOM 尚未完整时正式下达研发或批量工单；采购则必须等待 BOM 完整且审核通过。系统需要分别审核任务承诺与技术定义，避免把成品存在、工单下达和允许生产混为同一资格。

当前工单创建、下达不要求完整 BOM，但仍校验成品可用性和工单必填项。引入审批前，BOM 永久锁定发生在首次成功创建生产任务时，并非创建工单时。本次试探将 BOM 锁定前移到最终批准，并同步生产任务使用门禁；工单审批不在本次范围。现状以 [Product 数据库设计](../../apps/api/src/modules/product/docs/database.md) 和 [Production 工单设计](../../apps/api/src/modules/production/docs/database/work-orders-and-batches.md) 为准；本 ADR 同时定义后续工单审批目标，不能据此宣称工单接口已经具备审批门禁。

## 决策

### 业务流程与审批关注点

1. 销售部门收到外部下单通知；系统不记录该外部动作。
2. 研发部门创建成品编码信息，关联基础物料并逐步配置 BOM。至少先有真实的成品记录占住编码，BOM 此时可以尚未完整。
3. 销售基于该成品编码提交现有研发或批量工单，经过工单审批后正式下达；沿用 `work_orders`，不为此增加前置委托单。
4. 研发完善 BOM，提交独立的 BOM 技术审批。
5. BOM 全部审批节点通过后永久锁定，采购才可据此下达物料采购订单。
6. 已下达工单满足已批准 BOM 及其他生产准备条件后，才可创建生产任务，进入后续生产执行。

工单审批与 BOM 审批审查不同内容，可以分别推进。上述顺序不要求每次都等工单审批结束才开始 BOM 编制或审批；已批准 BOM 的成品也不因新增工单而重新进行同一份 BOM 的审批。

| 审批 | 核心关注点 |
| --- | --- |
| 工单审批 | 是否接受这项研发或批量任务；将要做的成品是否选对，成品编码及其对应产品是否与外部订单要求一致；数量、交期等任务要求是否合理 |
| BOM 审批 | 技术定义是否正确、完整；投入基础物料、单件用量、单位及其他 BOM 规则是否足以作为采购和生产依据 |

工单审批中的产品核对是关键责任，不能只看数量和交期。研发审批人员必须核对销售选择的成品，避免销售选错产品而审批未发现，最终生产结果与外部订单要求不一致。审核对象包含稳定 `product_id` 和可辨识的成品编码及资料；从提交到最终下达，不能悄悄替换被审核产品。外部下单动作不入系统，不代表省略人工对照外部要求的责任，也不表示系统已经自动验证外部订单。

工单批准不代表 BOM 批准；BOM 批准也不代表某张工单获准下达。研发任务和批量工单都遵守这两个独立条件。

### BOM 锁定与使用资格

- 将永久锁定触发点从“首次创建生产任务”前移至“BOM 审批最后一级通过”。这里指 BOM 审批，不是工单审批，也不是某一级审批通过。
- 最终 BOM 批准与 Product 写入永久锁定事实必须同事务完成；任一失败时整体回滚。生产任务创建改为验证已批准、已锁定 BOM，不能继续通过创建任务绕过审批并首次锁定。
- 保留单一 BOM、锁定后不解锁的原则；原则性用料变更仍需新建成品和编码，再复核 BOM。不引入 BOM 版本头、版本行或兼容双写。
- 成品编码存在且资料可用即可供工单使用；BOM 未完整或未批准时，不允许据此正式下达采购订单或创建生产任务。审批通过也不免除后续命令对物料启用状态等当前业务资格的校验。
- 同一成品的 BOM 是成品级定义。多张工单引用同一成品时共用其已批准 BOM，不能把 BOM 批准和锁定误建成每张工单各自一份的事实。

### 顺序多级审批

- 首期必须支持多个顺序节点，例如“研发审批 → 管理审批”；不包含条件分支。
- 节点数量由流程定义表达，不硬编码为两级，也不在业务主表增加 `first_approver`、`second_approver` 等固定级数字段。
- 当前节点满足通过条件后才能进入下一节点；只有全部节点通过，才执行最终业务动作。工单最终动作是下达，BOM 最终动作是批准并永久锁定。
- 工单审批和 BOM 审批使用各自流程定义；示例中的研发、管理两级不代表所有审批动作必须使用相同节点。
- 每一级按配置的角色确定候选人员，候选中任意一名合格人员通过即完成该级；不要求该角色所有人会签。同级多名候选同时操作时只能接受一次有效决定，其他候选的该级待办随之结束。

### 申请人与审批人员

- 首期固定允许申请人审批自己的申请，前提是该申请人满足当前节点的角色、账号有效性及业务审批权限。申请人身份本身不授予审批资格。
- 允许自审不等于提交即自动通过；申请人仍须在当前节点明确作出审批决定，逐笔保留处理人、时间与意见。
- 自审资格规则统一在 Approval 的人员资格判断中处理，业务模块不各自实现自审开关。未来调整该规则时，还须统一处理候选待办生成、实际处理校验以及在途申请适用规则，不能仅修改某个业务接口的判断。
- 允许同一人在一张申请中处理不同审批级，但每一级都须具备该级资格，分别明确操作并记录；不能因前级由本人通过而自动通过后级。
- 此处角色表示授权职责分组，可命名为研发审批员、管理审批员；现有 Identity 角色没有职级高低或上下级关系，不根据角色名称自动推断上级审批人。

### 人员空缺与重新分派

- 发布流程和提交申请时，检查每一级当前均有合格人员；不完整的流程可以保存草稿，但不得发布或开始新申请。
- 运行中因角色成员、账号或权限变化导致无人可审时，保留申请及已完成节点，显示阻塞原因；不得自动跳过或批准。
- 补齐角色人员后显式重新分派当前节点，记录调整及实际人员；不改写已完成决定，不将重新分派解释为撤回，也不赋予管理员代撤回能力。

### 驳回、撤回与重新提交

- 只有申请人本人可以撤回尚未结束的申请，管理员不因管理权限获得代撤回能力。已通过、已驳回或已撤回的申请不能再次撤回。
- 任一级驳回即结束本次申请，不退回上一级继续。
- 申请人修改后新建申请，从第一级重新审批；旧申请和各级意见保留，不能覆盖成一条新的申请历史。
- 审批期间要修改受审内容，必须先撤回，修改后从第一级重新提交；不能让前级审核旧内容、后级审核新内容。
- 撤回与最终批准并发时只能有一个合法结果；最终批准已经提交后，不再将其作为待审申请撤回。BOM 已批准后的永久锁定原则仍然有效。

## 架构影响

继续遵守现有模块化单体、端口适配器和同库事务规范。Product 保有 BOM 及锁定事实所有权，Production 保有工单及生产任务所有权；审批的加入不授权其他模块直接更新这些表。Approval 拥有流程与运行记录；具体公开契约及表结构见模块所有者文档。

审批进度与业务状态应分别表达：最终批准前不得执行目标业务动作；是否在工单业务状态中新增 `submitted` 尚待状态机设计，不因支持多级而增加一级、二级审批等工单状态。采购订单与通知仍是未来能力，本流程不表示已经建设完整采购模块。

### 后续通知首期范围

本次最小审批试探排除 Notification，仅有 Approval 待办；以下是日后接入通知模块时的范围。

- Notification 是服务各业务模块的通用通知模块，Approval 只是首个调用方；后续通用边界由 [ADR-0007](0007-general-notification-boundaries.md) 补充。通知首期只做站内消息，审批待办继续归 Approval，不接入企业微信、钉钉、邮件等外部渠道。
- 通知已读与审批完成独立；待办以 Approval 数据为准。按 ADR-0008，节点保留共享待办，当前可处理人实时解析；通知收件记录落实到具体用户，历史审批保留实际处理人。
- 站内通知通过 Notification 公开能力与审批动作同事务落库；预留最外层事务提交成功后的非阻塞钩子，首期为空实现，失败不改变业务结果。首期不为外部发送预建投递任务、消息队列或事务发件箱，不承诺钩子的宕机补发。

## 实施衔接

本决策涉及 Product 锁定触发点和 Production 任务资格的变更。实施时同步所有者文档、公开契约、后端全部相关命令及管理端交互；数据库结构变更只追加 migration，不能修改已执行的锁定事实迁移，也不能将旧的任务锁定事实伪造为历史人工审批记录。开发环境允许统一重置并通过迁移、种子恢复，不建设兼容双写。

审批接入细化见[审批设计](../approval-design.md)，通用通知候选表、去重及提交后钩子见[通知设计](../notification-design.md)。这些文档区分本次 BOM 试探与未实施扩展，不将代码落地等同于用户黑盒验收。采购衔接及实施事项统一见 [roadmap](../roadmap.md)。
