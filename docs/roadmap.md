# 路线图

## 盘点模块待细化

### F7：盘点明细 CHECK 与唯一键文档对齐

- 随后续盘点模块细化一并处理，当前暂缓修正文档与实现；所有者文档见[退料、报废与盘点](../apps/api/src/modules/production/docs/database/return-scrap-and-stocktake.md)。
- 核对 `stock_check_detail.system_quantity`：本次审计发现文档写 `>= 0`，实际 CHECK 为 `> 0`，候选流程也要求正库存。后续按确认的盘点范围统一候选查询、写入校验、数据库约束和文档，不因文档差异直接扩大为零库存盘点。
- 核对唯一键：本次审计记录的实际 `uk_stock_check_detail_target` 为 `(stock_check_id,item_id,batch_id,stock_status)`，文档多列了 `material_variant_id`。同步说明批次与精确版本的外键关联；该差异不代表已有重复盘点漏洞或缺少版本约束。
- 核对 `result`：实际为 `STORED` 生成列，应准确列出生成表达式，并与显式 CHECK 分开描述，不把表达式保证的结果取值写成独立物理约束。
- 完成标准：按细化后的最终代码及数据库结构复核字段、生成列、唯一键、外键与 CHECK，同步所有者文档；若需改表则追加 migration。黑盒与 UI 确认后再补齐相关测试。

## 库存查询待办

### 日常库存数量查询改用余额投影

- 将分配候选、分配/出库锁内校验、盘点候选、创建和确认中的现存量流水聚合，改为读取现有 `inventory_batch_balance` 或 `inventory_material_variant_balance`。基础物料合计从版本余额按 `material_id` 汇总；物料库存页已读取余额投影，不再列入历史流水增长专项评估。
- 替换须保留精确版本、库存批次和库存状态条件，并验证批次状态过滤、缺行按零处理、流水与投影同事务维护、并发锁序、当前读及数量一致性。不得仅替换 SQL 而削弱写事务中的库存不足和并发校验。
- 完成标准：日常现存量查询与写入校验不再依赖历史流水求和，相关事务和数量验证通过。完成后移除“日常库存查询随历史流水增长”的专项评估事项；剩余容量工作按实际查询和并发瓶颈安排。

### 预留量查询性能检查

- 单独检查库存批次列表、分配和领料候选中的预留汇总。预留来自分配及出库明细，不等于账面库存余额，不能直接用现有余额投影替代。
- 按批次数、历史分配与出库量及并发量逐级增加数据规模，记录执行计划、扫描行数、耗时和锁等待，优先优化重复聚合与组合索引；分页返回少量结果不代表聚合只处理少量历史。
- 是否新增预留数量投影，待容量证据明确后决定，不预建影子表或第二套库存账本。测试集按黑盒确认后的测试阶段安排。

### 流水查询与事实来源边界

- `inventory_transaction` 始终是唯一库存事实来源，余额是同事务维护、可重建的派生结果。日常数量读取改用余额，只改变查询路径，不改变数据所有权或事实来源。
- 历史追溯按业务条件分页读取流水；对账和重建按各自范围聚合流水，不要求每次业务操作重新计算历史。相应查询按用途检查索引和执行成本，不与日常现存量查询混为一个性能评估项。
- `item_id` 是基础物料身份而非流水唯一键；精确库存使用 `material_variant_id`，批次操作还保留 `batch_id` 和库存状态。跨版本合计只能表示基础物料总量，不能用于替代版本或判断齐套；BOM 版本不代替库存精确版本身份。

## 已识别方向（尚未立项）

以下方向不属于当前正式范围。它们表示已经识别的业务缺口，不表示范围、所有权和实施方案已经批准；前置决策完成前不得直接进入开发。

### 通用 Inventory

- 当前基础：`inventory_transaction` 是物料库存数量的唯一事实来源；`inventory_batch_balance` 与 `inventory_material_variant_balance` 是可从流水重建的查询投影。Production 已实现外购物料窄入库、生产领料出库、生产退料、现有库存批次盘点和已领到产线后的物料损耗。
- 待补场景：自产半成品/成品入库、委外完成入库、销售发货出库、仓库内库存报废，以及可用、待检、冻结和不良品之间的状态转换。
- 产出查询需求：在自产半成品/成品入库获批后，支持按生产批次追溯产出库存批次，区分累计入库量与当前库存量。先确定产出身份和来源关系，再设计查询；当前不预定数据库视图或字段结构。
- 实施前提：出现 Production 之外的真实库存消费者后，先确定统一库存能力的代码所有权和公开命令边界，再决定是否从 Production 抽出 Inventory application/module。该决定只涉及模块所有权，不得拆出第二套库存流水或复制库存余额事实。
- 验收边界：业务单据确认、库存流水、余额投影和成功审计必须同事务；新增场景完成契约、追加 migration、并发/幂等约束及真实 MySQL 验证。当前设计见 [Production 数据库设计](../apps/api/src/modules/production/docs/database/README.md)。

### Quality

- 当前基础：仓库只有 `needInspection`、`qualityLevel`、`qualifiedQuantity` 和待检库存状态等预留语义；尚无检验事实表、Quality application/module、HTTP 接口或管理页面。当前工序正常数量不是质量合格数量，异常返工和报废补料也不等于完整 Quality。
- 待定义场景：来料检验、过程检验、最终检验，以及检验结论如何驱动放行、待检/不良库存、返工、报废或让步接收。
- 实施前提：先批准首期业务范围，并确定检验批、检验项、抽样、结论、质量放行和 `qualifiedQuantity` 的唯一写入口径。
- 验收边界：完成模块所有权、契约、追加 migration、权限、事务审计和测试前，不开放质量状态或以预留字段宣称能力已实现。当前范围以[产品范围](product-scope.md)为准。

### 全链路 Traceability

- 当前基础：Production 局部追溯已经可按工单、生产批次、物料和库存批次查询需求、分配、领料出库、库存流水、原料入库来源及工序执行事实；它不代表质量放行，也不包含完整返工、报废、退料、成品入库和销售流向。
- 目标场景：从成品批次或销售交付向后定位生产、质量、原料批次和供应商，也能从原料批次向前定位受影响的生产批次、成品和交付对象。
- 实施顺序：先稳定通用 Inventory、Quality、成品入库和销售出库的数据模型，同时持续保留不可变事实、来源 ID、业务引用和历史快照；再建设跨模块追溯读模型，避免对未定稿表结构反复返工。
- 验收边界：先批准查询范围、数据所有权、关联键和权限；追溯只能聚合既有事实，不得创建第二库存、生产需求或质量事实来源。
