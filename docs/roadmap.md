# 路线图

## 采购到入库：黑盒与 UI 验收

供应商、两种采购入口、到货与实收修订、来料检验及复检、退回与独立补单、采购逐行关闭及仓管分次入库已经接入。当前规则和实现分别见 [ADR-0013](adr/0013-procurement-source-and-stock-boundaries.md)、[业务设计](procurement-inbound-design.md)、[技术设计](procurement-inbound-technical-design.md)及 [Procurement](../apps/api/src/modules/procurement/README.md)、[Quality](../apps/api/src/modules/quality/README.md)、[Inventory](../apps/api/src/modules/inventory/README.md) 所有者文档。本节只保留尚未完成的验收与后置事项，不把类型、构建和启动检查等同于用户验收。

- [ ] 用户联合黑盒与 UI 验收：供应商名称维护 → 按需求／独立备料采购 → 多次到货 → 全检／抽检 → 分次入库 → 生产分配及领料；核对分页、跨页选择、历史来源与权限失败交互。
- [ ] 验收同供应商跨工单合单、需求逐条映射及独立采购量；需求更正／关闭不改写采购，采购和入库不直接减少需求，补单不回写原单。核对免费超量与额外购买、质量退回补发两种补单原因及真实追溯。
- [ ] 验收部分范围主动复检、实收修订及零量复核：选定范围立即暂停，未影响范围继续办理；已有入库／退回及批次身份不变；原实收少录可补录经核实的剩余实物，不能登记新来货或掩盖损耗。
- [ ] 验收采购逐行关闭与仓库待办分离：按真实依据关闭，关闭后原到货仍可检验、更正、入库和退回；更正到零不等于从未到货。终止待退范围不得经复核重新放行，每个退回范围一次完整交接。
- [ ] 验收首次确认自动生成原 item_batch.batch_code、同到货后续分次沿用批次、历史经 inbound_detail 追溯；核对并发、同键重放、旧页面失效、无采购来源旧写入口关闭和事务回滚。
- [ ] 回归 Inventory 提取后的生产需求、预留、领料、退料、盘点和批准成品入库；停用物料版本允许采购入库，但不得生产领用或计入可领齐套量，历史库存总量仍保留。
- [ ] 按用户反馈修正业务和 UI，完成受影响代码的类型检查、构建及 API／管理端启动验证。

### 正式测试阶段

- [ ] 用户完成黑盒及 UI 验收，明确确认设计无问题并通知进入测试阶段后，再编写／调整正式单元、组件、接口及 MySQL 集成测试集；此前不新增正式测试集。
- [ ] 届时使用 Luna MAX 子代理全量验证并修复至通过，覆盖权限、状态、来源／选版、数量、复检／更正、库存联动、并发／幂等／回滚、migration up/down/up 及现有生产回归，按[测试策略](testing-strategy.md)执行；不使用 --passWithNoTests。

### 后置采购扩展

工单提前采购、按需与备料混合来源单、跨到货合并检验、供应商打印、门口拒收登记及抽样分档配置仍待另行安排。一期继续使用独立备料、分入口下单、按到货明细检验及实际抽检数量录入，不扩大为完整 ERP／MES、财务、供应商评审或生产在线质量。

开发库允许完全重置，结构变化只追加 migration，重置后由统一 migration／seed 恢复；不建立兼容双写或影子表。

## 库存查询待办

### 日常库存数量查询改用余额投影

- 将分配候选、分配/出库锁内校验、盘点候选、创建和确认中的现存量流水聚合，改为读取现有 `inventory_batch_balance` 或 `inventory_material_variant_balance`。基础物料合计从版本余额按 `material_id` 汇总；物料库存页已读取余额投影，不再列入历史流水增长专项评估。
- 替换须保留精确版本、库存批次和库存状态条件，并验证批次状态过滤、缺行按零处理、流水与投影同事务维护、并发锁序、当前读及数量一致性。不得仅替换 SQL 而削弱写事务中的库存不足和并发校验。
- 完成标准：日常现存量查询与写入校验不再依赖历史流水求和，相关事务和数量验证通过。完成后移除“日常库存查询随历史流水增长”的专项评估事项；剩余容量工作按实际查询和并发瓶颈安排。

### 预留量查询性能检查

- 单独检查库存批次列表、分配和领料候选中的预留汇总。预留来自分配及出库明细，不等于账面库存余额，不能直接用现有余额投影替代。
- 按批次数、历史分配与出库量及并发量逐级增加数据规模，记录执行计划、扫描行数、耗时和锁等待，优先优化重复聚合与组合索引；分页返回少量结果不代表聚合只处理少量历史。
- 是否新增预留数量投影，待容量证据明确后决定，不预建影子表或第二套库存账本。测试集按黑盒确认后的测试阶段安排。

### 流水查询与事实来源边界

- `inventory_transaction` 始终是唯一库存事实来源，余额是同事务维护、可重建的派生结果。日常数量读取改用余额，只改变查询路径，不改变数据所有权或事实来源。
- 历史追溯按业务条件分页读取流水；对账和重建按各自范围聚合流水，不要求每次业务操作重新计算历史。相应查询按用途检查索引和执行成本，不与日常现存量查询混为一个性能评估项。
- `item_id` 是基础物料身份而非流水唯一键；精确库存使用 `material_variant_id`，批次操作还保留 `batch_id` 和库存状态。跨版本合计只能表示基础物料总量，不能用于替代版本或判断齐套；BOM 版本不代替库存精确版本身份。

## 已识别方向（尚未立项）

采购到入库的一期验收见上方。本节记录更广范围的业务缺口；这些场景仍未立项，不表示其范围、所有权和实施方案已经批准。

### 通用 Inventory

- 当前基础：`inventory_transaction` 是物料与成品库存数量的唯一事实来源；`inventory_batch_balance` 与 `inventory_material_variant_balance` 是可从流水重建的查询投影。Inventory 已拥有库存及入库／盘点能力；Procurement 编排外购检验后入库，Production 编排领料、退料、批准成品入库及领后物料损耗。
- 待补场景：上述 Production 已确认的成品手动入库之外，自产半成品入库、委外完成入库、销售发货出库、仓库内库存报废，以及可用、待检、冻结和不良品之间的状态转换仍须另行明确范围。
- 实施前提：新通用场景须单独确定来源身份、业务所有权及公开命令边界，复用已有 Inventory，不拆出第二套流水或复制库存事实。
- 验收边界：业务单据确认、库存流水、余额投影和成功审计必须同事务；新增场景完成契约、追加 migration、并发/幂等约束及真实 MySQL 验证。当前设计见 [Inventory](../apps/api/src/modules/inventory/README.md) 与 [Production 数据库设计](../apps/api/src/modules/production/docs/database/README.md)。

### Quality

- 当前基础：独立 Quality 已提供外购来料初检、复核办理和不可变结论；Procurement 按其明确批准编排仓管入库。Production 结案线下质检仍由 Production 所有，用于核对管理员产出清单，不改变产出处置。工序正常数量不等于质量合格数量，不预留批次数量列作为未来质量写入口。
- 待定义场景：过程检验、完整最终检验、返工、报废或让步接收等更广场景不自动纳入现有窄 Quality。
- 后续抽样配置：按来料数量区间配置样本数量或比例，允许业务调整，不将档位和比例写死在代码中。检验保留实际覆盖量、样本数和采用的规则版本或参数，后续配置变化不改历史记录或已确认入库额度；配置能力另行安排，不因当前支持手工抽检就宣称已经实现。
- 实施前提：新增质量场景先批准范围，再确定检验批、检验项、抽样、结论及放行的事实来源，不将工序报工或已有批准产出复制为第二套质量事实。
- 验收边界：完成模块所有权、契约、追加 migration、权限、事务审计和测试前，不开放质量状态或以预留字段宣称能力已实现。当前范围以[产品范围](product-scope.md)为准。

### 全链路 Traceability

- 当前基础：Production 局部追溯已经可按工单、生产批次、物料和库存批次查询需求、分配、领料出库、库存流水、原料入库来源及工序执行事实，成品库存查询可追溯入库清单、任务和工单；这些局部入口不等于跨模块质量放行、全部报废或销售流向追溯。
- 目标场景：从成品批次或销售交付向后定位生产、质量、原料批次和供应商，也能从原料批次向前定位受影响的生产批次、成品和交付对象。
- 实施顺序：先稳定通用 Inventory、Quality、成品入库和销售出库的数据模型，同时持续保留不可变事实、来源 ID、业务引用和历史快照；再建设跨模块追溯读模型，避免对未定稿表结构反复返工。
- 验收边界：先批准查询范围、数据所有权、关联键和权限；追溯只能聚合既有事实，不得创建第二库存、生产需求或质量事实来源。

## 审批试探验收与后续扩展

- 当前接入 BOM、生产需求更正和批次收尾场景，按角色、指定用户或场景业务来源配置顺序多级审批；当前使用入口、表结构和事务职责见 [Approval](../apps/api/src/modules/approval/README.md)。长期业务决策见 [ADR-0006](adr/0006-approval-workflow-boundaries.md) 和 [ADR-0008](adr/0008-approval-node-assignees.md)，未实施扩展见[审批与通知设计](approval-design.md)。
- 工单审批后续接入：沿用现有研发/批量工单，核对所选产品与外部订单要求、数量和交期；BOM 审批与工单审批独立。工单审批关联字段仍是所有者文档中的未来结构，本次不改工单下达状态机。
- Notification 独立提供站内通知，Approval 是首个调用方；同事务落库、非阻塞空钩子及当前验收项见下方“通用通知验收”，不在审批模块内建设专用外部发送能力。
- 通用审批决定的 HTTP 幂等重放仍待单独设计；目前决定使用版本、锁与唯一约束防重，不自动重试。Production 新增业务送审已纳入其幂等命令，与申请和绑定共事务。
- 新增审批场景时扩展明确的对象/证据契约、详情展示和接口权限入口，复用通用提交引擎；当前详情契约明确覆盖 BOM、需求更正和批次收尾。列表已经在分页前过滤实时资格，但仍逐申请读取节点并解析候选人，后续按实际查询量评估批量读取，须保留实时资格与实际处理历史可见性的区别。
- 采购衔接保持既定边界：按需求采购沿用需求精确版本，备料采购自行选版，两者的实际供应商和订购数量均由采购确定。一期采购不接在线审批，正式下单锁定与错误重建遵守 ADR-0013；外部订单核对是否需要附件或引用信息仍待另行明确，不提前增加审批流程或第二套生产需求事实。

### 实际接入外部渠道时再设计

- 可靠投递：是否要求宕机补发、可接受延迟与重复；据此定义同事务持久化投递记录或 outbox、幂等、重试退避、失败人工处置、多实例领取和顺序要求。不能只依赖提交后的内存钩子承诺送达。
- 渠道与账号：渠道适配端口、用户与外部账号绑定、凭证配置及脱敏、渠道停用或账号解绑后的处理、送达回执的含义；外部送达不自动变成站内已读。
- 消息量与打扰：超时、并发和积压上限、速率限制、过载策略、去重合并；按实际需求决定优先级、订阅偏好、免打扰、摘要和催办，不能让可关闭提醒影响业务待办本身。
- 运维与内容：失败/积压指标和关联追踪、重发权限及审计；渠道文案和模板版本仅在实际需要时设计，不复制完整业务单据，不预建通用模板平台。
