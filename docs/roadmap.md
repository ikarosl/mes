# 路线图

## 成品入库前置：中间态收尾整改、需求纠错与收尾审批

需求纠错采用 [ADR-0010](adr/0010-demand-correction-by-replacement.md) 的关闭与替代方案，正式数量和中间快照不原位修改。下列为待实施调整；现有批次结束命令仍是一次确认后批量处理，尚不具备逐项收尾及结案审批。

- [ ] 实施需求 `closed` 终态，明确区分“更正替代关闭”和“随批次终止关闭”等原因，`cancelled` 保留给未执行任务取消。送审只冻结旧需求，以在审更正关联显示审批中，履约状态仍为 `active`；操作候选排除它，齐套和完工仍须阻断。替代关系在新需求上指向旧需求，不能把所有关闭需求都要求为有替代需求；同时处理驳回/撤回、混合出库单及终止与在途审批互斥。
- [ ] 将批次提前结束改为“生产中 → 开始收尾 → 管理员逐项处理需求、工序及相关单据 → 登记实际产出 → 提交短产/提前结束审批 → 审批通过 → 批次正式结束”。审批环节必须实际接入通用 Approval 的流程、节点、证据和最终生效，不以管理员确认弹窗代替审批。补充工序 `terminated` 状态和批次收尾操作边界，保留原状态、报工及实际领退料；审批人查看各中间态的处理结果，驳回回收尾阶段且不自动撤销既有事实。
- [ ] 工单聚合展示各任务已审定可用产出、报废量、产出合计、差额和收尾进度；未审定量单独标识，正常任务也明确最终产出确认口径，不累计各道工序报工量作为成品产出。成品入库接入后再增加已入/待入量。
- [ ] 实施单条需求更正申请、审批和替代关系：原 `parent_demand_id` 继续表示补料原始需求，另行保存直接替代及逐次审批关联；保留补料单与来源类型，不把补料替代转成无关联普通人工追加。首期范围及数量下限遵守需求所有者文档，来源损耗错误、身份/版本更换另行设计。
- [ ] 统一更正后的有效需求、缺口、补料齐套与追溯口径，更正最终批准和出库确认复用同一履约判定与状态推进能力，工序消费补料单结果。覆盖原需求 10 已领 4、批准目标 7、新剩余需求 3，连续更正累计历史履约，纯关闭不生成零需求；按生效更正链接续履约，替代需求未领齐仍阻断对应补产额度，普通取消及整单零领料空集合不能误激活补产授权。
- [ ] 追加 migration 调整补料来源唯一键及更正约束，更新需求生成分组/幂等策略、统一 Writer、后端资格与版本校验、权限、审批场景/证据和前端纠错表单。最终批准与关闭旧需求、生成新需求、计划版本推进及审计同事务；原事实/快照、库存流水不改写。
- [ ] 收紧短批任务“关闭全部剩余需求”的独立入口：短批只允许缺料继续生产；整批停止走收尾审批，个别错误需求走单条关闭/更正审批。验证送审期间的操作限制、混合出库单处理、预留释放、重复/并发批准及补料齐套副作用；先黑盒与 UI 验收，确认后再编写测试集并由 Luna MAX 全量验证。

## 中间态收尾整改后：成品入库、研发轮次与工单编号

执行前置：先完成上节中间态收尾、需求关闭/替代、冻结及短产/提前结束审批整改，再推进本节任务。已有批次结束能力及其不变量见[批次结束设计](../apps/api/src/modules/production/docs/database/production-termination.md)，长期决策见 [ADR-0009](adr/0009-research-round-close-and-output-disposition.md)。

- [ ] 对齐成品库存身份及来源追溯：当前库存使用物料精确版本，先定义成品身份、来源工单/生产批次、库存批次及流水关联，再追加 migration；不能直接写入产品 ID 绕过现有外键，也不另建账本或双写。
- [ ] 在当前入库管理页分别提供“生产流转入库”和“额外产出入库”按钮及数量弹窗，选择正常完成或提前关闭的来源工单；有多生产批次时明确归属，展示实际产出处置。库存仅在用户确认入库后变化，结束生产和关闭工单不自动完成入库。
- [ ] 正常入库按实际数量记录少于、等于或多于计划的差异，不固定为计划量；与已登记可用产出核对，报废及未产出差额不入库，零可用产出不产生零数量流水，不反写报工或质量合格量。额外产出经独立入口记录，不能在两条链路重复计入。
- [ ] 支持分次入库、累计已入/待入量及重复/并发确认防重；待入量按产出处置与累计已确认入库量核算，不按当前库存余额推算，避免库存被领用后重复办理入库。
- [ ] 额外产出以 `production_extra` 独立入库，不要求先完成正常入库，不自动生成补料/补产；同一工单正常产出与额外产出形成两笔记录、两个库存批次。例如计划 10，正常 10 入 A，额外 2 入 B。增加对应来源及累计入库查询、后端资格/幂等与并发校验。
- [ ] 新一轮沿用新建成品、新研发工单及新 BOM 审批入口；保留本轮拼版多物料版本配置。新增新旧研发轮次关联、追溯及资料带出交互，不复制旧需求、库存或批准事实；已有手动新建入口不等于轮次关联已经完成。
- [ ] 细化终止时损坏物料的结构化“不补料”登记：当前通过管理员核对说明保留现场情况，未新增损坏数量占用事实。若需自动限制损坏部分可退额度，须先明确与既有 `item_scrap` 损耗补料链路的边界，不按成品差额或 BOM 推算，不借用会触发补料的损耗确认。
- [ ] 工单号改为日期加当日序号，后端生成、编辑不改号；按 `yyyy-MM-dd-1`、`-2` 和业务时区设计，实施时核对原文 `yyy-mmm-ddd` 的格式意图。创建幂等、同日并发不重号，取消/关闭号不复用。
- [ ] 用户黑盒与 UI 验收：以整改后的逐项收尾及结案审批流程登记可用、新增报废、原因和物料安排，查看产出处置并关闭旧工单。覆盖计划 10、可用 3、报废 5、未产出 2；历史报废不重复填写；全部报废；已领料但零产出；异常/返工/补料结束；待确认损耗或异常分配阻断；并发报工使证据失效；重复点击；结束后禁止执行但可沿原分配退料。后续再覆盖正常/额外入库、分次防重、研发轮次关联及并发工单编号。
- [ ] 每阶段 UI 与设计明确确认后再编写对应测试集，并由 Luna MAX 子代理全量验证。覆盖独立终止报废不补料补产、不改变库存或报工、收尾/纠错审批、同事务回滚、权限/幂等/并发、全部批次终态后结案及本节新功能；已有类型检查、构建和启动检查不能代替黑盒验收或正式测试集。

## 盘点模块待细化

### F7：盘点明细 CHECK 与唯一键文档对齐

- 随后续盘点模块细化一并处理，当前暂缓修正文档与实现；所有者文档见[退料、报废与盘点](../apps/api/src/modules/production/docs/database/return-scrap-and-stocktake.md)。
- 核对 `stock_check_detail.system_quantity`：本次审计发现文档写 `>= 0`，实际 CHECK 为 `> 0`，候选流程也要求正库存。后续按确认的盘点范围统一候选查询、写入校验、数据库约束和文档，不因文档差异直接扩大为零库存盘点。
- 核对唯一键：本次审计记录的实际 `uk_stock_check_detail_target` 为 `(stock_check_id,item_id,batch_id,stock_status)`，文档多列了 `material_variant_id`。同步说明批次与精确版本的外键关联；该差异不代表已有重复盘点漏洞或缺少版本约束。
- 核对 `result`：实际为 `STORED` 生成列，应准确列出生成表达式，并与显式 CHECK 分开描述，不把表达式保证的结果取值写成独立物理约束。
- 完成标准：按细化后的最终代码及数据库结构复核字段、生成列、唯一键、外键与 CHECK，同步所有者文档；若需改表则追加 migration。黑盒与 UI 确认后再补齐相关测试。

## 库存查询待办

### 日常库存数量查询改用余额投影

- 将分配候选、分配/出库锁内校验、盘点候选、创建和确认中的现存量流水聚合，改为读取现有 `inventory_batch_balance` 或 `inventory_material_variant_balance`。基础物料合计从版本余额按 `material_id` 汇总；物料库存页已读取余额投影，不再列入历史流水增长专项评估。
- 替换须保留精确版本、库存批次和库存状态条件，并验证批次状态过滤、缺行按零处理、流水与投影同事务维护、并发锁序、当前读及数量一致性。不得仅替换 SQL 而削弱写事务中的库存不足和并发校验。
- 完成标准：日常现存量查询与写入校验不再依赖历史流水求和，相关事务和数量验证通过。完成后移除“日常库存查询随历史流水增长”的专项评估事项；剩余容量工作按实际查询和并发瓶颈安排。

### 预留量查询性能检查

- 单独检查库存批次列表、分配和领料候选中的预留汇总。预留来自分配及出库明细，不等于账面库存余额，不能直接用现有余额投影替代。
- 按批次数、历史分配与出库量及并发量逐级增加数据规模，记录执行计划、扫描行数、耗时和锁等待，优先优化重复聚合与组合索引；分页返回少量结果不代表聚合只处理少量历史。
- 是否新增预留数量投影，待容量证据明确后决定，不预建影子表或第二套库存账本。测试集按黑盒确认后的测试阶段安排。

### 流水查询与事实来源边界

- `inventory_transaction` 始终是唯一库存事实来源，余额是同事务维护、可重建的派生结果。日常数量读取改用余额，只改变查询路径，不改变数据所有权或事实来源。
- 历史追溯按业务条件分页读取流水；对账和重建按各自范围聚合流水，不要求每次业务操作重新计算历史。相应查询按用途检查索引和执行成本，不与日常现存量查询混为一个性能评估项。
- `item_id` 是基础物料身份而非流水唯一键；精确库存使用 `material_variant_id`，批次操作还保留 `batch_id` 和库存状态。跨版本合计只能表示基础物料总量，不能用于替代版本或判断齐套；BOM 版本不代替库存精确版本身份。

## 已识别方向（尚未立项）

以下方向不属于当前正式范围。它们表示已经识别的业务缺口，不表示范围、所有权和实施方案已经批准；前置决策完成前不得直接进入开发。

### 通用 Inventory

- 当前基础：`inventory_transaction` 是物料库存数量的唯一事实来源；`inventory_batch_balance` 与 `inventory_material_variant_balance` 是可从流水重建的查询投影。Production 已实现外购物料窄入库、生产领料出库、生产退料、现有库存批次盘点和已领到产线后的物料损耗。
- 待补场景：上述 Production 已确认的成品手动入库之外，自产半成品入库、委外完成入库、销售发货出库、仓库内库存报废，以及可用、待检、冻结和不良品之间的状态转换仍须另行明确范围。
- 产出查询需求：随成品手动入库支持按生产批次追溯产出库存批次，区分累计入库量与当前库存量。先确定产出身份和来源关系，再设计查询；当前不预定数据库视图或字段结构。
- 实施前提：出现 Production 之外的真实库存消费者后，先确定统一库存能力的代码所有权和公开命令边界，再决定是否从 Production 抽出 Inventory application/module。该决定只涉及模块所有权，不得拆出第二套库存流水或复制库存余额事实。
- 验收边界：业务单据确认、库存流水、余额投影和成功审计必须同事务；新增场景完成契约、追加 migration、并发/幂等约束及真实 MySQL 验证。当前设计见 [Production 数据库设计](../apps/api/src/modules/production/docs/database/README.md)。

### Quality

- 当前基础：仓库只有 `needInspection`、`qualityLevel`、`qualifiedQuantity` 和待检库存状态等预留语义；尚无检验事实表、Quality application/module、HTTP 接口或管理页面。当前工序正常数量不是质量合格数量，异常返工和报废补料也不等于完整 Quality。
- 待定义场景：来料检验、过程检验、最终检验，以及检验结论如何驱动放行、待检/不良库存、返工、报废或让步接收。
- 实施前提：先批准首期业务范围，并确定检验批、检验项、抽样、结论、质量放行和 `qualifiedQuantity` 的唯一写入口径。
- 验收边界：完成模块所有权、契约、追加 migration、权限、事务审计和测试前，不开放质量状态或以预留字段宣称能力已实现。当前范围以[产品范围](product-scope.md)为准。

### 全链路 Traceability

- 当前基础：Production 局部追溯已经可按工单、生产批次、物料和库存批次查询需求、分配、领料出库、库存流水、原料入库来源及工序执行事实；它不代表质量放行，也不包含完整返工、报废、退料、成品入库和销售流向。
- 目标场景：从成品批次或销售交付向后定位生产、质量、原料批次和供应商，也能从原料批次向前定位受影响的生产批次、成品和交付对象。
- 实施顺序：先稳定通用 Inventory、Quality、成品入库和销售出库的数据模型，同时持续保留不可变事实、来源 ID、业务引用和历史快照；再建设跨模块追溯读模型，避免对未定稿表结构反复返工。
- 验收边界：先批准查询范围、数据所有权、关联键和权限；追溯只能聚合既有事实，不得创建第二库存、生产需求或质量事实来源。

## 审批试探验收与后续扩展

- 本次试探限定 BOM 场景，按角色或指定用户配置顺序多级审批；当前使用入口、表结构和事务职责见 [Approval](../apps/api/src/modules/approval/README.md)。长期业务决策见 [ADR-0006](adr/0006-approval-workflow-boundaries.md) 和 [ADR-0008](adr/0008-approval-node-assignees.md)，未实施扩展见[审批与通知设计](approval-design.md)。
- 工单审批后续接入：沿用现有研发/批量工单，核对所选产品与外部订单要求、数量和交期；BOM 审批与工单审批独立。工单审批关联字段仍是所有者文档中的未来结构，本次不改工单下达状态机。
- Notification 独立提供站内通知，Approval 是首个调用方；同事务落库、非阻塞空钩子及当前验收项见下方“通用通知验收”，不在审批模块内建设专用外部发送能力。
- HTTP 幂等命令重放仍需单独接入与验收；本次审批使用版本、锁与唯一约束防止重复决定，不声明支持 Idempotency-Key 或自动写重试。
- 新增审批场景时扩展明确的对象/证据契约、详情展示和接口权限入口，复用通用提交引擎；当前详情契约仅覆盖 BOM。列表已经在分页前过滤实时资格，但仍逐申请读取节点并解析候选人，后续按实际查询量评估批量读取，须保留实时资格与实际处理历史可见性的区别。
- 待确定采购衔接：采购单精确物料版本由谁选择、数量依据及与工单/生产需求的关系、外部订单核对是否需要附件或引用信息。不得引入第二套生产需求事实或提前实现完整采购模块。

### 实际接入外部渠道时再设计

- 可靠投递：是否要求宕机补发、可接受延迟与重复；据此定义同事务持久化投递记录或 outbox、幂等、重试退避、失败人工处置、多实例领取和顺序要求。不能只依赖提交后的内存钩子承诺送达。
- 渠道与账号：渠道适配端口、用户与外部账号绑定、凭证配置及脱敏、渠道停用或账号解绑后的处理、送达回执的含义；外部送达不自动变成站内已读。
- 消息量与打扰：超时、并发和积压上限、速率限制、过载策略、去重合并；按实际需求决定优先级、订阅偏好、免打扰、摘要和催办，不能让可关闭提醒影响业务待办本身。
- 运维与内容：失败/积压指标和关联追踪、重发权限及审计；渠道文案和模板版本仅在实际需要时设计，不复制完整业务单据，不预建通用模板平台。
