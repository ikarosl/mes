# 路线图

## 后续主线：采购、入库质检与模块划分

本节是后续任务的执行顺序，不表示采购、独立 Inventory 或 Quality 已实现。当前已落地边界仍以[产品范围](product-scope.md)、[架构规范](architecture.md)及 [Production 内部职责](../apps/api/src/modules/production/docs/module-boundaries.md)为准；进入各阶段时同步对应所有者文档。现有 Production 黑盒与 UI 反馈继续处理，不因正式测试集暂缓而阻断本节设计准备。

| 顺序 | 任务 | 阶段完成标准 |
| --- | --- | --- |
| 1 | 明确采购与入库质检业务流 | 确定单据关系、数量口径、检验前后库存归属及异常处理 |
| 2 | 划分代码架构与数据所有权 | 明确 Production、Procurement、Inventory、Quality 的职责、公开接口及原子事务 |
| 3 | 提取现有库存能力 | Inventory 成为唯一库存所有者，现有生产链路可启动并可手工验证 |
| 4 | 增加最简单供应商配置 | 一个稳定路由页，仅填写供应商名称，采购可按稳定 ID 选择 |
| 5 | 增加采购模块和两种下单入口 | 按需求采购与备料采购可办理，数量、版本、供应商和来源关系清晰 |
| 6 | 接通采购到货、入库质检及库存放行 | 按阶段 1 的规则形成可实际操作的完整业务流 |
| 7 | 联合黑盒与 UI 验收 | 用户手工验证并反馈修改，确认业务与页面设计无问题 |
| 8 | 编写正式测试集并全量验证 | 用户明确进入测试阶段后，由 Luna MAX 子代理验证并修复至通过 |

### 1. 明确采购与入库质检业务流

- [ ] 按一期外购物料规划入库质检，覆盖按需求采购和备料采购；明确是否存在免检。成品现有线下质检、批准清单及每类收齐一次入库继续按原所有者规则执行，如需纳入新质检流程，另行明确，不自动迁移或改写。
- [ ] 明确“到货登记 → 检验 → 放行至可用库存”的单据关联、办理角色和确认时点。首先确定是收货时进入待检库存，还是检验后才形成库存；在此决定前不提前实现记账或放行状态机。
- [ ] 明确采购单是否允许多次到货／分次入库、超收与少收、部分合格、全部不合格和未到货余量的结束方式。采购数量、到货数量、送检数量、合格／不合格数量、实际入库数量分别定义，不能互相代填。
- [ ] 确定检验所需最小资料、提交与确认资格，以及拒收、退回供应商、复检、结果纠错需要覆盖的最小处理路径。首期不能留下无法处理的不合格到货，也不借此建设完整质量体系、通用退货或库存报废。
- [ ] 明确采购单的数量锁定时点及已下单后的变更／取消规则；讨论同一需求多次下单、分别选择不同供应商，以及一张采购单的供应商数量、跨需求／跨任务合单边界。
- [ ] 明确原需求关闭、更正、换版或任务结束后，在途采购如何提示与处理；已订购事实保留原来源，不能随生产需求变化自动改写、删除或改绑。
- [ ] 将上述规则整理为业务流程、状态转换和数量示例；落地前更新相关 ADR 和所有者设计。尤其应细化 [ADR-0006](adr/0006-approval-workflow-boundaries.md) 的采购门槛：按需求采购须在任务形成精确版本需求后办理，备料采购不依赖工单或 BOM。

### 2. 划分代码架构与数据所有权

以下是目标职责，实际表清单、编排入口和公开契约在本阶段确定；不直接把现有单据按名称整体搬走。

| 目标模块／职责 | 所有的业务 | 跨模块边界 |
| --- | --- | --- |
| Production | 工单任务、执行、需求及更正、分配／领料履约、补料放行、结案产出 | 通过公开能力提供可采购需求；生产命令编排库存操作，保有生产资格判断 |
| Procurement | 采购单、来源需求关联、订购数量、实际供应商及采购履约；一期供应商名称目录 | 通过 Production／Product 校验需求或备料选版；不直接修改生产需求或库存表 |
| Inventory | 库存批次、唯一库存流水、余额投影及库存增减／状态转移规则 | 接收经所属业务校验的记账命令，不反向决定采购、检验或生产业务结果 |
| Quality | 本期入库检验记录、结论及检验结果更正 | 通过公开能力提供放行依据，不直接修改库存或采购表；不接管完整生产质检 |

- [ ] 盘点现有 Production 的 Service、Repository、Controller 及装配职责，补齐真实用例边界；已经独立的入口继续复用，不为目录整齐重复重构或预建空模块。
- [ ] 逐表确定库存、入出库单据、分配、生产退料和盘点的所有者；明确业务单据与库存流水的引用，不让生产语义随库存账本迁移而丢失。供应商一期仅名称配置，先作为 Procurement 内部独立用例与页面，不仅因一张表建立独立 SupplierModule。
- [ ] 设计 `public.ts` 的窄命令／查询能力及跨模块编排方向，保留 `presentation → application → domain`，infrastructure 实现 ports；端口不暴露数据库连接或 SDK 类型，不形成循环调用。
- [ ] 明确生产领料与需求履约／补料放行、采购收货与库存、检验放行与库存状态变化各自的事务和锁序；需要原子生效的操作沿用同池事务上下文，不能拆成多个提交或异步通知。
- [ ] 同步 `docs/architecture.md`、`docs/product-scope.md`、执行规则中的当前范围、模块 README／数据库文档及 `scripts/api-data-ownership.mjs`；新增模块的权限、DTO、常量、契约及幂等范围随实际用例登记。仍为一个 API 和一个数据库的模块化单体。

### 3. 提取现有库存能力

- [ ] 按阶段 2 的所有权清单迁移现有批次、账本、余额查询及库存写入能力。此次提取服务于已明确的采购接入，不必等采购全部开发完成；迁移的是现有可用能力，不建立第二套账本或通用空框架。
- [ ] 将 Production 现有外购入库、成品入库、领料、退料、盘点等用例切换到公开库存能力；移除旧的直接库存写入口，同步所有权登记与必要的只读展示依赖。
- [ ] 保留生产需求唯一事实、精确物料版本、成品身份、批准清单资格及出库／履约联动事务。库存事实只写 `inventory_transaction`，余额仍为可重建的派生结果。
- [ ] 完成受影响模块类型检查、构建和启动检查，手工核对现有入库、分配、领料、补料放行、退料、盘点及成品入库；问题修复后再接新增业务，不把检查结果表述为正式全量测试。

### 4. 增加最简单供应商配置

- [ ] 提供一个稳定路由与组件名的供应商配置页，支持名称的新增、查看与修改；用户填写项只有供应商名称。
- [ ] 保存稳定供应商 ID，采购单按 ID 引用；按公共规范补齐系统审计、并发和软删除字段，具体名称去重及已有引用处理规则写入所有者文档。
- [ ] 提供采购需要的供应商选择接口和页面权限，后端接口独立鉴权。供应商不绑定产品或物料；不建设产品供应商关系、评审准入或研发指定供应商限制。
- [ ] 承认日期、评审人、备注、主要产品、联系人、附件、年度复评及提醒全部不在一期；不预建这些资料的空字段或评审表。

### 5. 增加采购模块和两种下单入口

- [ ] 一套采购单以来源区分“按需求采购”和“备料采购”，分别提供清晰入口，共用已明确的下单生命周期；不复制生产需求作为第二套需求账本。
- [ ] 按需求采购：从工单／生产任务进入，按初始需求、人工追加、工序报废补料、领料损耗补料分组展示具体需求行；也支持从需求页带入来源。持久化关联具体需求 ID，不只关联工单、物料或需求组。
- [ ] 按需求带入物料及已确定的精确版本，采购不能自行换版；正式下单时重新校验需求当前资格、在审更正、物料版本及任务状态。生产侧供应商期望只作备注提示，研发与批量工单规则相同；实际供应商与实际采购数量由采购确定，数量遵守正整数口径。
- [ ] 备料采购：采购自行选择可采购物料、有效精确版本、供应商与数量，不要求工单、任务或生产需求。
- [ ] 实现阶段 1 确定的数量锁定、重复采购提示、分次下单与合单规则；分别展示已下单、到货及入库进度，不能把这些量当作生产已领数量。采购量不必等于需求量，生产需求的剩余量仍由实际确认领料减少。
- [ ] 按需求下单不自动预留库存；按需求采购与备料采购均经后续库存分配办理生产领用。采购来源用于追溯，不自行增加需求专属库存隔离。

### 6. 接通采购到货、入库质检及库存放行

- [ ] 建立采购单行、到货明细、检验记录和库存批次的可追溯关联，支持阶段 1 确定的到货与入库次数、数量差异和余量结束规则。
- [ ] 提供到货办理、入库检验待办、检验结果与入库／放行操作页面；实施既定的角色权限、数量校验、不可变检验事实及独立纠错方式。
- [ ] 按确定的记账时点写库存；采用待检库存时，放行必须通过可追溯的库存状态转移事实完成，不能直接覆盖余额，也不能在收货和放行时重复增加总库存。
- [ ] 实现本期拒收、不合格、部分合格及纠错路径，待检和不合格数量不得当作可用量参与生产分配／领料；不得通过旧外购入库入口绕过已确定的质检门槛。旧手工入口保留、限制或替换方式随业务设计落实。
- [ ] 完成采购履约、检验结果、库存事实及成功审计的一致性，校验重复确认、并发放行、权限与事务回滚；到货、检验或入库均不直接满足生产需求。
- [ ] 新质检只实现本期外购物料入库场景；过程检验、成品完整在线质量、供应商评审、销售、委外、财务结算与通用库存报废另行安排。

### 7. 联合黑盒与 UI 验收

- [ ] 每个编码阶段完成类型检查、构建及启动检查后交给用户手工验证，按反馈修改业务与 UI；不要等全部页面写完才展示。
- [ ] 联合验证“供应商名称配置 → 按需求／备料采购 → 到货 → 检验 → 可用库存 → 生产分配领料”，以及阶段 1 确定的异常路径；检查采购来源、物料版本和数量沿途可追溯。
- [ ] 验证供应商仅作采购选择、研发期望无锁定效果；需求更正／关闭不静默改写在途采购，采购入库不直接清零生产需求。复核拆分前的生产链路和成品入库仍可用。

### 8. 编写正式测试集并全量验证

- [ ] 用户完成黑盒与 UI 验收、明确告知设计无问题并进入测试阶段后，再编写／调整正式单元、组件、接口及 MySQL 集成测试集；此前不新增测试集。
- [ ] 届时使用 Luna MAX 子代理执行全量验证并修复至通过，覆盖架构所有权、权限、状态机、采购来源／选版、数量、质检与库存联动、并发／幂等／回滚、迁移和现有生产回归，按[测试策略](testing-strategy.md)执行实际可运行检查；不使用 `--passWithNoTests`。

各阶段数据库约定：本项目目前处于开发阶段，允许任何时候完全重置数据库，无需保留兼容性数据。结构变化只在 `packages/database/migrations` 追加 migration，不修改已执行文件；重置后由统一 migration／seed 恢复，不建立双写或影子表。每阶段交付说明文件、模块、数据库／migration 影响及所有者文档符合性。

## 库存查询待办

### 日常库存数量查询改用余额投影

- 将分配候选、分配/出库锁内校验、盘点候选、创建和确认中的现存量流水聚合，改为读取现有 `inventory_batch_balance` 或 `inventory_material_variant_balance`。基础物料合计从版本余额按 `material_id` 汇总；物料库存页已读取余额投影，不再列入历史流水增长专项评估。
- 替换须保留精确版本、库存批次和库存状态条件，并验证批次状态过滤、缺行按零处理、流水与投影同事务维护、并发锁序、当前读及数量一致性。不得仅替换 SQL 而削弱写事务中的库存不足和并发校验。
- 完成标准：日常现存量查询与写入校验不再依赖历史流水求和，相关事务和数量验证通过。完成后移除“日常库存查询随历史流水增长”的专项评估事项；剩余容量工作按实际查询和并发瓶颈安排。

### 预留量查询性能检查

- 单独检查库存批次列表、分配和领料候选中的预留汇总。预留来自分配及出库明细，不等于账面库存余额，不能直接用现有余额投影替代。
- 按批次数、历史分配与出库量及并发量逐级增加数据规模，记录执行计划、扫描行数、耗时和锁等待，优先优化重复聚合与组合索引；分页返回少量结果不代表聚合只处理少量历史。
- 是否新增预留数量投影，待容量证据明确后决定，不预建影子表或第二套库存账本。测试集按黑盒确认后的测试阶段安排。

### 流水查询与事实来源边界

- `inventory_transaction` 始终是唯一库存事实来源，余额是同事务维护、可重建的派生结果。日常数量读取改用余额，只改变查询路径，不改变数据所有权或事实来源。
- 历史追溯按业务条件分页读取流水；对账和重建按各自范围聚合流水，不要求每次业务操作重新计算历史。相应查询按用途检查索引和执行成本，不与日常现存量查询混为一个性能评估项。
- `item_id` 是基础物料身份而非流水唯一键；精确库存使用 `material_variant_id`，批次操作还保留 `batch_id` 和库存状态。跨版本合计只能表示基础物料总量，不能用于替代版本或判断齐套；BOM 版本不代替库存精确版本身份。

### 全链路 Traceability

- 当前基础：Production 局部追溯已经可按工单、生产批次、物料和库存批次查询需求、分配、领料出库、库存流水、原料入库来源及工序执行事实，成品库存查询可追溯入库清单、任务和工单；这些局部入口不等于跨模块质量放行、全部报废或销售流向追溯。
- 目标场景：从成品批次或销售交付向后定位生产、质量、原料批次和供应商，也能从原料批次向前定位受影响的生产批次、成品和交付对象。
- 实施顺序：先稳定通用 Inventory、Quality、成品入库和销售出库的数据模型，同时持续保留不可变事实、来源 ID、业务引用和历史快照；再建设跨模块追溯读模型，避免对未定稿表结构反复返工。
- 验收边界：先批准查询范围、数据所有权、关联键和权限；追溯只能聚合既有事实，不得创建第二库存、生产需求或质量事实来源。
