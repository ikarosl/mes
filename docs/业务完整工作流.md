# 生产业务完整工作流

本流程不包含管理员、角色和权限控制，仅描述产品、工艺、生产、质量和库存业务。

文中数据库字段值统一使用小写英文 `snake_case` 稳定代码，中文只用于业务说明和前端标签。数据库继续使用 `VARCHAR + CHECK`，不使用 MySQL `ENUM`；状态值域由数据库约束，合法状态转换由后端领域层控制。

## 一、基础资料准备

### 1. 配置产品分类

进入产品分类管理，配置物料、半成品和成品分类。

分类信息保存至 `product_categories`，通过 `item_kind` 区分：

- `material`：物料；
- `semi_finished`：半成品；
- `finished_product`：成品。

物料、半成品和成品统一保存在 `products` 表中，通过 `products.category_id` 关联分类。这里不是单独的“产品与物料映射表”，而是产品表直接关联分类表。

### 2. 添加物料或产品资料

在 `products` 中添加库存对象，并根据所选分类确定其属于物料、半成品还是成品。

本次添加为物料时，只维护物料编码、名称、单位、获取方式和规格等基础资料，不配置 BOM 和工艺路线。产品、物料和半成品统一使用 `item_code` 作为唯一业务编码，不单独维护型号字段。

对于自产半成品或成品，可以继续配置：

- 产品物料清单；
- 产品工艺路线；
- 默认工艺路线。

系统应根据分类和获取方式进行业务校验，例如采购物料原则上不能配置生产工艺路线，自产半成品和自产成品可以配置 BOM 和工艺路线。

### 3. 物料入库

物料每次入库都应按库存批次管理。

入库时：

1. 在 `item_batch` 中建立物料库存批次；
2. 创建 `inbound_order` 入库单；
3. 创建 `inbound_detail` 入库明细；
4. 生成正数的 `inventory_transaction` 库存流水。

库存现存数量以 `inventory_transaction` 的汇总结果为准，不直接在物料或批次表中维护可修改的库存余额。

### 4. 添加标准工序

在 `process_steps` 中维护标准工序，例如装配、焊接、调试、检验和包装。

工序可以关联默认 SOP 文件。文件信息统一保存在 `technical_files` 中，工序通过 `default_sop_file_id` 关联默认 SOP。

### 5. 配置工艺路线

创建 `process_routes` 工艺路线，并通过 `process_route_steps` 按顺序组合多个工序。

每个路线步骤可以配置：

- 工序顺序；
- 默认负责人；
- 本步骤使用的 SOP 文件；
- 是否需要报工；
- 是否需要检验。

工艺路线必须绑定具体产品。路线启用后不得直接修改原版本，如需调整工序顺序或 SOP，应创建新的路线版本。

### 6. 配置成品或半成品

再次添加产品，本次选择成品或自产半成品，并完成以下配置：

1. 在 `product_materials` 中配置产品 BOM；
2. 为每种投入物料配置单位用量和用量单位；
3. 选择该产品使用的工艺路线；
4. 将默认路线保存至 `products.default_route_id`。

产品 BOM 是后续生成生产物料需求的唯一数据来源。修改 BOM 不得影响已经生成的历史生产需求。

## 二、生产计划与派工

### 7. 创建生产工单

创建 `work_orders` 工单，选择需要生产的产品，并填写工单计划生产数量。

工单下达时，应保存产品编码、产品名称和单位快照，后续修改产品资料不得影响历史工单。

工单初始状态为 `draft`，确认下达后变为 `released`。

一个工单表示整体生产计划，可以拆分成多个生产批次执行。

工单可以关联一个可空的外部订单号，支持同一个外部订单拆分为多个生产工单。外部订单号不作为 MES 工单自身的唯一标识；`work_order_no` 仍保持唯一。

### 8. 创建生产任务

系统中的“生产任务”对应 `production_batches` 生产批次，不需要再建立一张独立任务表。

创建生产批次时：

1. 绑定一个工单；
2. 自动带出工单产品；
3. 填写本批次计划生产数量；
4. 选择该产品的工艺路线（未指定时读取产品默认路线，指定路线时允许使用同产品的非默认路线）；
5. 指定本批次总体负责人；
6. 冻结路线编号和路线版本快照。

一个工单可以拆成多个生产批次，不要求一个批次完成工单的全部生产数量。

创建批次时，后端必须执行以下校验（同一应用事务内）：

- 该工单下未取消生产批次的计划数量合计不得超过工单计划数量。
- 所选路线必须属于工单产品，且路线状态为 `enabled`。
- 批次工序由后端按路线步骤顺序自动生成，不接受前端提交任意 `route_step_id` 集合。
- 路线中的必须报工和必须检验标志同时冻结为快照。

### 9. 生成工序执行记录并等待派工

生产批次创建后，系统根据所选工艺路线自动生成 `batch_step_records`。

每个路线步骤生成一条工序执行记录，并复制：

- 工序顺序；
- 工序编码和名称；
- SOP 文件信息；
- 默认负责人；
- 报工单位；
- 必须报工标志快照；
- 必须检验标志快照。

路线中的默认负责人只作为派工表单的默认建议值。生产批次创建时，所有工序记录以 `pending` 创建，`responsible_user_id` 保持为空；不能因为存在默认负责人就把工序解释为已经派工。

创建完成后，管理员端按待派工工序提醒管理员确认负责人。管理员可以在一个界面批量确认，但每道工序都必须独立校验和保存；确认后将所选用户写入 `batch_step_records.responsible_user_id`，并把该工序从 `pending` 转为 `assigned`。开工前允许撤回派工或改派，开工后不得使用普通派工接口修改负责人。

后续调整路线、工序默认负责人或 SOP 文件，不得回写已经生成的生产批次工序记录。

当前数据库没有生产批次级的统一“工艺参考文件”字段，因此工艺文件应按工序保存在 `batch_step_records` 的 SOP 快照字段中。

## 三、物料需求、预留与领料

### 10. 生成物料需求

生产批次创建后，可以手动点击或由系统自动生成物料需求。

系统根据以下数据计算需求：

```text
需求数量 = BOM 单位用量 × 生产批次计划数量
```

每种物料生成一条 `production_item_demand`，并保存：

- BOM 明细 ID；
- 物料 ID；
- 单位用量快照；
- 单位快照；
- 批次追溯要求快照；
- 生产批次计划数量快照；
- 最终需求数量；
- 幂等键，防止重复点击或重试重复创建需求。

幂等键生成规则：

- 正常需求：`NORMAL:{production_batch_id}:{product_material_id}`
- 工序报废补料：`SCRAPSUP:{supplement_id}:{parent_demand_id}`
- 人工追加：`ADDITIONAL:{production_batch_id}:{business_action_no}:{product_material_id}`

同一个幂等键重复提交时返回既有结果，不再插入新需求。

需求生成后作为历史事实保存。后续修改 BOM 或生产批次计划数量，不得自动覆盖原有需求；如需调整，应取消原需求或新增追加需求。

此时生产批次可进入 `material_pending` 状态。

### 11. 分配物料并形成库存预留

仓库根据物料需求进行物料分配，分配结果保存至 `production_item_allocation`。

同一种物料可以从多个 `item_batch` 库存批次中分配，例如：

```text
需求 100 个
库存批次 A 分配 60 个
库存批次 B 分配 40 个
```

每条分配记录必须关联：

- 生产物料需求；
- 生产批次；
- 物料；
- 库存批次；
- 分配数量。

创建物料分配记录即表示完成库存预留。物料需求本身只表示计划，不会占用库存。

系统分配时必须查询可分配库存，不能只查询账面库存：

```text
可分配库存 = 账面可用库存 - 其他生产批次已预留但未释放的数量
```

分配必须使用 `item_batch` 行锁防止并发超额预留。分配事务执行顺序：

1. 锁定目标 `item_batch` 行（多批次按 ID 升序加锁）；
2. 在锁内重新汇总账面可用库存；
3. 在锁内汇总有效、未释放、未取消的分配占用；
4. 计算最新可分配数量并校验；
5. 写入 `production_item_allocation`；
6. 更新业务状态并写操作日志；
7. 提交事务后再返回成功。

物料全部分配完成后，生产批次进入 `material_assigned` 状态。

### 12. 生产领料出库

物料分配完成后，仓库进行实际领料出库。

领料时：

1. 创建 `outbound_order`；
2. 按分配记录创建 `outbound_detail`；
3. 为每条出库明细生成负数的 `inventory_transaction`；
4. 库存流水关联具体的 `outbound_detail.id`；
5. 生产批次进入 `material_outbound` 状态。

物料分配只表示预留，不会减少账面库存；只有领料出库才会实际扣减库存。

因此，标准流程应为：

```text
生成需求 → 分配预留 → 领料出库 → 生产开工
```

不能把“物料已分配”直接等同于“物料已出库”。

## 四、生产执行与质量闭环

### 13. 生产开工

领料完成后，生产批次进入 `material_outbound` 状态；物料分配和出库不会直接修改任何工序的执行状态。第一道已派工工序实际开始时，生产批次才进入 `doing` 并记录批次 `started_at`。

每道工序开始时，更新对应 `batch_step_records`：

- 校验当前状态为 `assigned`，未派工的 `pending` 工序不得直接开工或报工；
- 状态修改为 `doing`；
- 记录 `started_at`；
- 使用派工阶段已经确认的实际负责人；
- 展示该工序冻结的 SOP 文件。

员工端必须提供明确的“开始工序”按钮。只有被派工员工可以发起普通开工；后端以乐观锁校验工序仍为 `assigned`，在同一事务完成 `assigned -> doing`、写入 `started_at` 和成功审计。普通报工不得代替开工，也不得补写或覆盖 `started_at`。

系统原则上按照 `step_order_snapshot` 顺序执行工序。前一道必报工工序未完成时，后一道工序是否允许开工，由后端业务规则校验。

### 14. 工序报工

报工允许分批多次发生，且只允许已显式开工的 `doing` 工序提交。员工任务页提供相互独立的“正常报工”和“异常报工”入口，不允许在一次普通报工中同时填写正常与异常数量；同一批加工结果若包含正常与异常，应依次形成两条事实。`batch_step_records` 只保存工序执行节点和状态；每次报工向 `batch_step_reports` 插入一条不可变正向 `normal` 事实，填写：

- 报工总数；
- 工序正常数量；
- 异常数量；
- 异常来源：异常大于 `0` 时必须区分当前工序异常或接手时发现的前置异常；
- 单位快照；
- 本次备注。

工序正常数量不是质检合格数量，异常数量也不自动等同于报废或返工。单次事实必须满足：

```text
工序正常数量 + 异常数量 = 报工总数
```

员工普通报工还必须满足正常数量与异常数量恰好只有一个大于 `0`。这里的 `report_type = 'normal'` 表示“正向报工事实”，不是“正常品报工”；返工整单完成和管理员对历史事实的更正继续按各自规则处理，不套用员工普通报工的互斥限制。

未发生报废补产时，所有必须报工工序的最终要求正常数量均为批次计划量，后续工序的投入放行量取前道当前有效正常量。后续工序发生报废并完成补料领用后，系统不是给来源工序直接增加可报量，而是从路线首工序增加同量投入，并提高来源工序之前各上游工序的正常目标；新增正常产出按原路线逐道放行到来源工序。若后道上手时发现前置异常，管理员另选实际重制与补料的截止工序；这只改变物料候选范围，不改变额度仍需传播到异常上报工序。完整公式和 A→B、A→B→C 示例以数据库权威章节 §4.2.3 为准。

上述为当前实施基线。对于工序数量少且管理员可以逐项复核的现场，[数据库权威章节](database/40-production-traceability-quality.md#412-工序完工的两版方案)另行保留“数量达标后仍保持 `doing`，由管理员确认完工”的备用方案。两版不得同时启用；当前未完成正式方案切换前，管理端不得提前增加备用完工入口。

错误报工不得更新或删除。普通冲销以一条等量 `reversal` 事实指向原事实；管理员更正必须在同一命令、同一事务中同时写入“原事实冲销 + 带 `replaces_report_id` 的新普通事实”。若更正后上游 `effective_normal` 小于下游已经报工的 `effective_normal`，后端必须拒绝并返回冲突工序和报工依赖摘要，提示管理员先从最下游开始冲销冲突报工，再重试上游更正。已完成工序在无下游冲突且更正后数量不足时自动重开为 `doing` 并清空 `completed_at`；数量仍达标时保持 `completed`。

创建报工和管理员更正必须先接入 HTTP 幂等闭环；报工事实、工序状态/时间、成功操作日志和幂等结果同事务提交。详细规则以 [`database/40-production-traceability-quality.md`](database/40-production-traceability-quality.md) §4.2 为准。

### 15. 工序检验与返工

当前未落地过程检验；最小返工已经按异常报工整笔闭环。管理员批准返工后生成唯一 `rework_records`，原工序负责人开工并一次性完成返工，返工正常与异常数量合计必须等于来源异常数量；返工完成报工仍异常时生成新的待处置单。

在这些问题定稿前：

- 不创建 `inspection_records`，过程抽检、复检和质量放行仍待定稿；
- `batch_step_reports.normal_quantity` 只作为操作员自检正常量，当前临时作为下工序正常放行量，但不得解释为过程质检或最终质量合格量；
- `need_inspection_snapshot` 继续保留为路线快照，当前不创建检验任务，也不阻塞下工序流转；页面不得展示并不存在的“质检已通过”结论；
- 生产执行完工不校验尚不存在的“有效检验结论”；最终质量确认和 `qualified_quantity` 写入仍不得开放。

### 16. 工序异常、报废和补料

工序异常、确认损失、库存报废、补产和物料补料是不同事实，不能由一条异常报工越过审批自动联动：

- `abnormal_quantity` 只记录本次工序报告的异常数量；
- 有效普通报工的 `abnormal_quantity > 0` 时，在同一报工事务自动创建一条 `batch_step_abnormal_dispositions` 待审批处置单；它不改变 `batch_step_records.status`；
- 批准为返工或报废必须在同一审批事务创建相应下游业务事实；当前最小返工与报废补料均已落地；
- 库存是否扣减仍只能由 `inventory_transaction` 表达；
- 是否需要补产、需要哪些物料以及是否生成追加需求，必须经过独立规则或人工确认。

半自动补料采用“候选物料 + 管理员人工填量 + 新增需求”，不得回写原始需求的 `need_number`。补料物料数量与产品补产数量分开：批准报废时即生成不可变的工序报废补产授权；全部补料需求完成确认领料后，最后一笔确认事务把补料单持久化为 `fulfilled`，授权才进入可执行额度。异常若属实只能批准返工或报废；管理员认定来源报工填写错误时使用“驳回并更正”，以冲销和替代事实修正有效数量，不得物理删除报工。当前不记录某次补报逐笔消费哪张补料单。

报废补料在管理端采用二次复核：管理员先编辑并“暂存需求”，进入只读复核页后可以“重新编辑”或“确定报废并生成”。暂存保存为 `production_scrap_supplement_plan/_line` 服务端草稿，不写正式 `production_item_demand`，也不提前批准异常，因此不能被分配或出库；重新打开页面会恢复未确认方案。最终确定时才一次性提交报废事实、补产授权、补料单和正式补料需求，并把方案转为 `confirmed`。

管理端在“报废并补产”确认前必须展示：异常来源类型与上报工序、异常数量、固定补产起点、物料计算截止工序、额度受影响路径和预计增加的各工序正常目标，以及“授权立即记录、全部补料确认领用后才可执行”的提示。补料物流未完成时只显示待补料/待领料，不出现可补报按钮；补料齐套后，生产执行页在受影响工序旁展示“批次计划量 + 下游报废补产量”、当前正常量和剩余量，并将需要再次执行的已完成上游工序标记为“补产重开”。来源工序必须等前道形成新增正常产出后才显示新的可报量。

### 16.1 生产领料损耗补料

生产批次处于 `material_outbound/doing` 时，现场可以从该批次已确认领料的分配行申报生产领料损耗。损耗记录保存生产批次、需求、分配行、物料、库存批次、数量、单位和原因；创建与管理员确认时都必须校验数量不超过累计确认领料扣除退料占用和既有待确认/已确认损耗占用后的余额。

管理员确认损耗时不提供“不补料”或修改补料数量的选项。确认事务固定完成：

1. `item_scrap(production_consumed)` 转为 `confirmed`；
2. 创建 `production_material_supplement(source_type = 'material_loss')`；
3. 创建一条 `production_item_demand(demand_type = 'material_loss_supplement')`；
4. 需求物料、单位和 BOM 关系取来源分配行，数量严格等于损耗数量；
5. 成功审计和 HTTP 幂等结果同事务提交。

损耗补料继续复用需求分配、领料出库和补料齐套流程。它只补实物，不生成产品补产授权、不增加工序可报上限、不重复扣减库存，也不改变生产批次计划量。普通退料、退料后报废及库存直接报废不属于该入口，仍按各自能力边界处理。

### 17. 生产退料

生产过程中或生产结束后，如存在未使用物料，可以办理退料。

退料时：

1. 创建 `return_order`；
2. 创建 `return_detail`；
3. 记录原需求、原分配记录、物料批次和退料数量；
4. 生成正数的 `inventory_transaction` 退料入库流水。

退料时需要明确是否释放给公共库存：

- `release_after_return = 0`：仍属于原生产批次，后续可以再次领用；
- `release_after_return = 1`：释放给公共库存，其他生产批次可以重新分配。

退料退回的库存状态只允许 `available`（可用）、`pending_inspection`（待检）、`frozen`（冻结）、`defective`（不良），不含“报废”。不能继续使用的退料按以下顺序处理：

1. `return_detail` 记录退料，退回状态使用 `defective`（不良）。
2. 退料确认生成 `stock_status = defective` 的正数退料入库流水。
3. 创建并确认 `item_scrap`，场景使用 `return_after_outbound`，并通过 `return_detail_id` 精确关联来源退料明细。
4. 报废确认生成 `stock_status = defective` 的负数报废出库流水。

`return_detail` 只记录退料事实，`item_scrap` 只记录报废事实，两者不得合并或互相替代。

## 五、完工与入库

### 18. 生产批次执行完工与最终质量边界

当前 `production_batches.completed` 只表示生产执行已经完成，不代表最终质量结论。生产执行完工命令保存：

- `completed_quantity` — 由服务端取最后一道必报工工序的 `effective_normal` 自动形成，客户端不得填写
- `completed_at` — 完工确认时间
- `completed_by` — 完工确认人

`qualified_quantity` 不由生产执行完工命令填写或从末道工序的 `effective_normal` 复制；它只允许由未来的最终质量结论写入。

使用 `production_batches.version` 乐观锁防止重复或并发完工确认。

当前临时自检阶段的生产执行完工边界为：

- 所有必须报工（`need_record_snapshot = 1`）的工序均已完成；
- `need_inspection_snapshot` 不创建检验任务，也不作为生产执行完工阻断条件；
- 最小 `rework_records` 已落地；返工完成报工计入工序有效数量，未完成返工和待处理异常由各自业务记录独立展示，不复用工序或批次执行状态；
- 至少存在一道必报工工序；服务端在事务内重新聚合最后一道必报工工序的 `effective_normal`，且不允许人工覆盖该结果。

批次生产执行完工按 `todo.md` 4.2-D 实施。当前不支持最后一道必报工工序正常数量不足时的短批完工；确需按不足数量结束时，未来必须通过独立的生产损失/短批完工命令记录差额、原因、确认人和审计，不得让管理员直接填写 `completed_quantity`。最终质量确认是另一条命令，需要独立质量事实、权限、事务和审计，不能改变本节生产执行完工的含义。

生产批次完成不等于成品已经入库。生产完成和库存入库是两个独立业务动作。

批次完工不自动创建入库单、库存批次或库存流水。

当工单下所有有效生产批次均已完成，且完成数量达到工单计划数量后，工单可以修改为 `completed`；后续业务全部结束后可修改为 `closed`。

### 19. 半成品或成品入库（待后续阶段）

生产完成后，对合格半成品或成品办理生产入库。

入库时：

1. 在 `item_batch` 中创建新的库存批次；
2. 设置 `source_type = self_made`；
3. 关联来源工单和来源生产批次；
4. 创建 `inbound_order`；
5. 创建 `inbound_detail`；
6. 生成正数的 `inventory_transaction`；
7. 是否需要独立流转里程碑表，在质量放行边界定稿后决定；当前不得创建 `finished_flow_records`。

一个生产批次可以生成多个库存批次，例如：

- 不同生产日期的库存批次；
- 不同质量状态的库存批次；
- 半成品库存批次；
- 成品库存批次。

如果产品入库后仍需等待最终检验，可以先按 `pending_inspection`（待检）状态入库。

质量放行时，不修改原库存流水，而是在同一事务内创建两条库存状态转换流水：

1. `stock_status = pending_inspection`，数量为负数的状态转出流水；
2. `stock_status = available`，数量相同为正数的状态转入流水。

两条流水共享相同 `transaction_group_key`，使用不同且分别唯一的内部键；其来源引用必须指向未来定稿的质量放行事实，当前不得预设为尚不存在的检验表。

质量结论、检验人员和报告只保存在未来的质量模型。库存流水只记录库存数量和状态维度。

库存数量只能由 `inventory_transaction` 汇总得出；未来即使增加流转里程碑，也不得直接改变库存数量。

## 六、库存盘点与修正

### 20. 创建库存盘点

创建 `stock_check_order` 盘点单，并选择需要盘点的库存对象、库存批次和库存状态。

系统生成 `stock_check_detail`，记录盘点时的：

- 物料或产品；
- 库存批次；
- 库存状态；
- 系统账面数量；
- 实际盘点数量；
- 差异数量；
- 盘盈、盘亏或一致结果。

### 21. 确认盘点差异

盘点确认后，根据差异生成 `inventory_transaction`：

- 盘盈生成正数的“盘点调整”流水；
- 盘亏生成负数的“盘点调整”流水；
- 无差异时不生成库存流水。

生成调整流水后，将 `stock_check_detail.adjusted` 标记为 `1`，避免重复调整。

盘点修正不得直接修改库存余额，也不得修改或删除原库存流水。错误的库存流水必须通过数量相反的冲销流水修正。一期只支持一次整笔全额冲销；该冲销是 MES 库存流水纠错，与财务报销单或财务凭证无关。

## 七、核心状态流转

生产工单状态：

```text
draft → cancelled
  └─→ released → doing → completed → closed
          └──────────────→ closed（无未终态批次的提前结案）
```

工单只有在草稿、未下达时可以取消。下达后提前终止统一使用关闭：没有生产批次时可在二次确认后直接关闭；存在批次时必须先完成或取消所有未结束批次，后端拒绝自动级联取消。所有非取消批次均已完成且完成量合计达到工单计划量时，由管理员在汇总确认弹窗中显式确认工单完工，不由批次自动回写；`completed -> closed` 表达成功完工后的行政归档。提前关闭必须填写原因并区分未生产结案与不足量结案。

生产批次状态：

```text
pending
→ material_pending
→ material_assigned
→ material_outbound
→ doing
→ completed

pending / material_pending / material_assigned → cancelled
```

第一版“取消任务”只允许尚未开工且物料尚未实际出库的批次。取消确认弹窗必须展示将联动取消的待确认出库单、有效预留和活动需求，并要求填写原因；后端在同一事务取消这些未形成库存事实的业务状态。`material_outbound`、`doing` 和 `completed` 均禁止取消，不提供强制入口。工单处于 `released` 或 `doing` 且仍有未分配计划量时，可以继续创建后续生产批次。

工序执行状态：

```text
pending → assigned → doing → completed
```

其中 `pending -> assigned` 只由管理员确认派工触发；`assigned -> pending` 只用于开工前撤回派工，改派保持 `assigned`；`assigned -> doing` 只由已派工员工明确点击“开始工序”触发；必报工工序在报工后正常数量达到当前要求时自动 `doing -> completed`，非必报工工序通过显式完工命令转换。已完成工序在合法更正导致数量不足，或下游报废补产提高当前目标时可以 `completed -> doing`。`material_assigned` 属于生产批次的普通物料状态，不得触发工序派工；只有补料全部确认领用形成路线补产授权时，才按权威公式重新打开受影响工序。异常报工和审批由独立事实及处置单表达，工序执行状态不再使用 `abnormal`。

取消的工单、生产批次、入库单或出库单通过取消状态表达，不物理删除已经产生的业务事实。已经确认的库存变动必须通过冲销流水处理；因此生产批次一旦实际领料或开工，第一版不得取消。

## 八、设计边界说明

以下为数据库设计中明确的业务边界：

1. 系统不引入项目模型，不提供项目级数据隔离。“进入生产管理”不表示系统已具备多项目权限或库存隔离能力。
2. 工单关联的外部订单号 `external_order_no` 只用于查询，不保证唯一。同一个外部订单可拆分为多个工单。
3. 路线与产品归属由后端应用事务校验，不依赖数据库组合外键。批次可使用同产品的非默认路线。
4. 工序规则（必须报工、必须检验）在批次创建时冻结为快照；后续路线调整不影响历史批次。
5. 生产需求由幂等键保证不重复生成，正常需求、报废补料和人工追加使用不同键前缀。
6. 工序报废补料支持一条补料单直接生成多种 BOM 物料需求，并由 `supplement_id + parent_demand_id` 防止重复。
7. 分配并发安全由 `item_batch` 行锁保证，不依赖 Redis。
8. 库存状态转换使用同事务内一正一负双流水，`transaction_group_key` 保证两条流水属于同一动作。
9. 批次完工保存最终完成数量和合格数量，完工不自动创建入库单或库存流水。
10. 复检通过 `source_rework_id` 追溯具体返工记录，一个返工可多次复检。
11. 退料库存状态不含“报废”，不能继续使用的退料独立走报废流程。
12. MES 主数据编码永久唯一，软删除后通过恢复原记录处理，不创建同编码新记录。

除上述边界外，完整业务主线为：

```text
配置分类
→ 添加物料和产品
→ 物料入库
→ 配置工序、工艺路线和 BOM
→ 创建工单
→ 创建生产批次并生成工序任务
→ 生成物料需求
→ 分配物料并形成预留
→ 领料出库
→ 工序开工和报工
→ 检验、返工、报废及补料
→ 生产完工
→ 半成品或成品入库
→ 退料及库存盘点修正
→ 生产与库存追溯查询
```
