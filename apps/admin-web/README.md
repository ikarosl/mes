# apps/admin-web

Vue 3 管理端主线。视觉与交互遵守[视觉设计](docs/visual-design.md)：左侧菜单 + 顶部栏 + 内容区；列表优先；新增、编辑、分配、确认使用 Modal，不使用 Drawer。前端分层、候选数据所有权、竞态守卫和刷新时机遵守[管理端架构](docs/architecture.md)。

```text
src/
  app/
  api/
  components/
    data-table/
    query-form/
    modal-form/
    status-tag/
  composables/
  layouts/
  router/
  stores/
  styles/
  views/<module>/<feature>/
    components/
    composables/
    schemas/
    index.vue
```

页面负责组合，Modal 表单、查询模型、状态字典和 API schema 分离。当前共享组件仍由 admin-web 的
`src/components` 所有；只有出现第二个独立前端消费者且组件 API 已稳定时，才评审提取 workspace UI 包。

## 审批试探手工验收路径

审批业务接入产品 BOM、生产需求更正和批次收尾，工单下达审批不在范围内。需求总览提供更正与追溯；收尾页逐项处理并登记产出后再送审。两个 Production 场景须分别配置并发布流程。站内通知使用顶部铃铛，每页 10 条、每 30 秒拉取未读角标；打开入口和显式刷新拉取列表，点击正文保存已读，点击“查看详情”保存后进入审批申请。后端完成迁移并准备至少一个启用角色后，可按以下路径验收：

1. 以具有 `approval:configure` 的账号进入“审批中心 → 审批流程配置”，打开“BOM 审批”，添加两个节点，第一级选角色，第二级选指定用户；切换类型时确认清空另一种选择。保存草稿后修改指定人，直接点击“发布流程”，确认发布的是刚修改的节点；指定用户必须具备审批权限。
2. 以具有产品 BOM 管理权限的账号进入“成品与物料”，为一个未送审成品配置并保存 BOM；重新打开 BOM，确认未保存修改时不能提交审批，保存后“提交 BOM 审批”可用。
3. 提交后确认 BOM 显示“审批中”且编辑控件被锁定；在“审批待办”打开该申请，核对成品编码、规格、BOM 明细、节点角色/指定用户、当前可处理人员和实际处理记录，候选人不再各自生成任务条目。
4. 使用节点角色下的合格账号明确点击“通过当前节点”，确认申请进入下一级；同一账号可继续处理下一级，但每一级都有独立记录。点击“驳回申请”必须填写原因。
5. 申请人从“我发起的”打开申请并撤回，确认申请结束、BOM 恢复可编辑；再次提交应生成新的申请并从第一级开始。全部节点通过后确认 BOM 显示“已批准”并永久锁定。
   驳回或撤回后返回已缓存的“成品与物料”标签，确认列表和此前打开的 BOM 弹窗都恢复草稿状态，无需浏览器刷新。审批通过后返回同一标签，确认弹窗同步为永久锁定。若本地仍有未保存修改且产品版本发生变化，应保留草稿并阻止保存，只有确认“重新加载 BOM”后才丢弃修改。
6. 在第一级尚未处理时加入新的合格角色成员，使用新成员账号刷新“待我处理”，应能看到并处理该旧申请，无需重新分派或历史通知；移除成员后刷新待办应消失，旧详情的迟到提交也应被拒绝。全部成员失效时申请人/管理员详情显示“暂无合格审批人”，补齐后自动恢复；指定用户节点不会因为角色新增其他成员而转给其他人。角色无人或指定用户失效时，发布、提交均应被拒绝。
7. 审批中心默认显示全部状态：普通用户范围为“与我相关”，配置管理员为“全部申请”。通过、驳回或撤回后，申请人和实际作出过通过/驳回决定的人可查看完整处理记录；仅曾是候选人、后加入角色或收到通知均不授予历史访问。“待我处理”只显示当前待办，不提供已结束状态筛选。从产品进入审批中心时也使用全部状态，不限定为本人发起。
8. 两个合格人员同时处理同一节点，只允许一次成功。保留旧详情后由另一人推进节点，旧页面再次提交不得误批下一节点。发布新流程后，已送审申请仍显示原节点配置。指定用户失效时恢复该账号资格即可继续，也可由申请人撤回后按新流程重新送审。

前端页面通过 `src/api/approval.ts` 使用审批公开契约，详情页以服务端返回的 `canApprove` 和 `canWithdraw` 决定操作入口，审批提交 `currentStepId + version`；页面按钮可见性不替代后端鉴权。组件及 API 测试覆盖角色/指定用户切换、候选刷新与失效、保存当前草稿后发布、节点命令和详情请求竞态。完整类型检查同时检查这些测试，单独 Vite 打包不能替代；验证边界见[测试策略](../../docs/testing-strategy.md)。

流程配置支持第三种分派方式“业务关联人员”，具体来源与最终节点要求均由场景接口返回。批次收尾最终节点必须选择“业务关联人员 → 工单负责人”；页面提示最终放行要求，排序或删除导致要求不满足时阻止保存、发布，服务端仍独立校验。新增空流程的首个节点带入该要求，继续添加节点时插入最终节点之前。配置只保存来源规则并显示“送审时确定”，不预先选择某张工单的人；切换类型清空无关字段。审批详情区分来源、送审确定人员和真实处理人，同时展示受审快照中的来源工单及当时负责人依据。人员失效不会自动改派，恢复原审批资格后继续。

业务关联人员的黑盒验收：用同一已发布流程分别提交两张负责人不同的工单任务，检查各自待办、详情和通知中的人员；只有当次确定的负责人可处理。核对最后节点改为角色／指定用户时的阻断，以及负责人无审批资格时的错误提示。上述扩展尚待黑盒与 UI 验收，按当前约定未新增正式测试集；现有测试夹具仅适配新契约。

BOM 编辑及审批证据明细仅显示物料、单位、单位用量和备注，不提供关键物料或记录批次开关。

## 任务产出清单与结案

正常生产在“生产执行完工”后进入待结案状态，工序报工量单独保留；提前结束仍先逐项收尾。任务页、生产执行记录和 Production 追溯提供“产出清单与结案”入口。`ProductionBatchTerminationDialog` 只处理收尾事项、物料实核和处理历史；`ProductionOutputDialog` 独立负责产出草稿、质检留存及批准清单，两者提供双向入口。正常生产也必须核对物料事实，有余料时在原退料管理办理，不能用最终成品差额推算退料。

产线管理员填写计划内产出、计划外产出及本次新增成品报废。计划内产出不超过计划；另外两项只按数量类型的非负整数上限校验，不以三项之和限制现场产出。计划缺口仅为计划量减计划内产出；历史工序报废只读展示，新增报废不重复包含历史数量或原材料损耗。工单汇总仅聚合有效批准清单，明确分别展示计划内、计划外和报废；未批准草稿另列，不计入审定产出。

质检人员在“质检记录”页签保存线下检验时间、当时申报数量快照、实检三项数量、结果说明和凭据参考。质检记录不可编辑覆盖，复检新增记录并关联前次记录，不直接改写产线草稿。产线管理员根据记录调整草稿并显式引用最新质检记录；送审要求三项申报数量与最新实检数量一致，不要求草稿版本与检验时版本相同。检验填写过程中申报依据变化时禁止提交，须重新核对。

送审使用当前版本和服务端核对指纹，最终由工单负责人审批。批准后形成不可变清单版本，清单支持查看关联审批与打印指定版本；历史清单明确标注不能用于入库。后续数量错误使用“发起清单更正”，保留旧批准版、新质检记录和后续审批；可显式取消未送审更正。已入库类别的批准数量不可改，更正期间入库资格仍以服务端为准。收齐本类别全部数量后仓管一次确认，清单批准本身不确认库存。

`useProductionOutput` 是详情、产出草稿、质检输入和命令意图的局部所有者；质检与批准版页签是纯展示组件。加载错误不转为空清单，关闭/切换任务后丢弃迟到响应；刷新不会覆盖未保存草稿，远端版本变化时提示重新加载。写操作有成功反馈，结果未知保留原命令和幂等键。后端独立区分产出管理与质检留存权限；前端状态控制不替代鉴权。此流程按约定等待黑盒和 UI 验收，未新增正式测试集。
