# apps/admin-web

Vue 3 管理端主线。视觉与交互遵守[视觉设计](docs/visual-design.md)：左侧菜单 + 顶部栏 + 内容区；列表优先；新增、编辑、分配、确认使用 Modal，不使用 Drawer。前端分层、候选数据所有权、竞态守卫和刷新时机遵守[管理端架构](docs/architecture.md)。

```text
src/
  app/
  api/
  components/
    data-table/
    query-form/
    modal-form/
    status-tag/
  composables/
  layouts/
  router/
  stores/
  styles/
  views/<module>/<feature>/
    components/
    composables/
    schemas/
    index.vue
```

页面负责组合，Modal 表单、查询模型、状态字典和 API schema 分离。当前共享组件仍由 admin-web 的
`src/components` 所有；只有出现第二个独立前端消费者且组件 API 已稳定时，才评审提取 workspace UI 包。

## 验证

`corepack pnpm --filter @company/admin-web typecheck` 检查应用源码和共享契约；`build` 在打包前执行同样的应用类型检查。`typecheck:test` 额外纳入测试文件，相邻测试由独立 `test` 入口执行。应用检查与构建通过不能替代测试类型检查和测试执行。

## 供应商配置

“采购管理 → 供应商配置”使用稳定路由 `procurement-suppliers` 和组件 `SuppliersPage`，提供名称搜索、服务端分页、新增及修改。用户只填写供应商名称，去首尾空白后必填且最多 100 字符；页面不提供联系人、备注、物料绑定、启停或删除。创建和修改由后端分别鉴权，菜单和路由以 `procurement:suppliers:view` 控制整页。

`useSuppliersList` 持有列表、筛选和分页，首次进入及返回缓存页刷新；`useSupplierEditor` 持有独立名称草稿及原始版本。切换标签保留草稿，关闭未保存修改须确认放弃。修改携带打开时的版本，已加载资料发生变化或服务端返回并发冲突时保留输入并禁止继续保存，须关闭后从最新列表重新选择；不会静默替换版本覆盖他人修改。名称重复与并发冲突分别按后端错误提示处理。

该页面通过 `src/api/procurement.ts` 调用供应商接口，普通创建／修改不发送幂等键。本页等待用户黑盒与 UI 验收，未新增正式测试集。

## 采购单与需求来源

“采购管理 → 采购单”使用稳定路由 `procurement-orders` 和组件 `PurchaseOrdersPage`，支持来源／状态／关键词分页查询。按需求和独立备料使用两个明确入口；草稿保存后在详情核对并正式下单，已下单记录冻结供应商、物料、数量与来源。页面可取消无到货整单、逐行人工结束或无到货取消，并从原行创建独立超量补单。关闭依据和补单原始来源在采购行展开区查看，原行的“相关补单”按全部状态分页核对并可跳转；质检达标与质量退回处置完成按服务端允许的关闭原因逐行选择，不合格补货从真实质量退回记录创建。

`usePurchaseOrderEditor` 拥有草稿与供应商远程候选，`PurchaseMaterialSelect` 拥有各行采购用途物料／版本候选。供应商、物料均使用关键词窗口加已选 ID 解析，采购版本允许停用并明确提示。需求弹窗以需求叶子分页，按工单和任务分组，跨页已选项独立保存，采用前显式解析全部已选资格；相同精确版本合并为一行，展开保留逐条需求，数量由采购独立填写整数。采购数量不分摊到需求，也不显示为需求已采购量。

`MaterialDemandOverviewDialog` 在真实任务需求入口批量读取 distinct 相关采购单数，相关记录可分页查看；跳转采购详情仍要求采购查看权限。采购页支持 `purchaseOrderId` 定位详情和 `demandId` 解析带入草稿，换单前处理未保存输入；未知提交结果阻止换单。`useProcurementCommand` 持有本次确认意图，全部订单写命令含草稿修改发送幂等键；网络不确定时冻结第一次内容并提供原操作重试，读取刷新不会覆盖未保存草稿或偷换版本。到货、来料检验和仓库放行入库接入同一来源链，正式测试集等待用户验收通知。


## 采购到货与来料检验

“仓储管理 → 采购到货”使用 `procurement-receipts`，通过专用分页收货采购候选选单，不要求采购页面权限。实收按现场数量填写整数，不按计划剩余量封顶；同一采购行可以按供应商批号拆成多个到货明细。到货不会产生库存，内部批号在首次实际确认入库时生成。`receiptId` 定位整单，`receiptLineId` 可独立解析并定位具体明细。

`ReceiptLineActionDialog` 与 `useReceiptLineAction` 持有原范围、行版本、修订和检验依据。实收更正逐范围调整，已入与已退事实锁定，同批原实收漏录量单独核实，并明确确认实物身份。更正后受影响范围进入复核；零量更正仍显示质检核实待办。实际退回每范围一次全部确认，交接时间与凭据必填；指定采购终止待退单独保留原因，不改写原质量结论。

“质量管理 → 来料检验”使用 `quality-inbound-inspections`，按未检真实范围与已有 case 分页。初检、主动复检和检验更正均先明确确认发起，指定数量立即显示复核中并暂停其入库／退回。全检与抽检记录真实整数数量，人员单独明确选择批准入库与后续处置，结论和凭据必填；检验追加事实，不覆盖旧结论。该页通过质量独立读取能力获取当前到货范围，不要求采购或仓库页面权限。

主详情只展示当前未处置范围、最近历史预览和所有未完成检验；`ReceiptHistoryDialog` 对实收修订、检验、供应商退回、实际入库、范围树分别分页，避免下载全部增长历史。质量退回历史提供“不合格补货”入口，创建新采购草稿并保存原退回证据。所有确认命令保留第一次请求以供未知结果重试，切换目标前保护未保存输入；不能通过自动刷新替换旧版本继续确认。上述页面等待用户黑盒与 UI 验收，尚未编写正式测试集。

## 审批试探手工验收路径

审批业务接入产品 BOM、生产需求更正和批次收尾，工单下达审批不在范围内。需求总览提供更正与追溯；收尾页逐项处理并登记产出后再送审。两个 Production 场景须分别配置并发布流程。站内通知使用顶部铃铛，每页 10 条、每 30 秒拉取未读角标；打开入口和显式刷新拉取列表，点击正文保存已读，点击“查看详情”保存后进入审批申请。后端完成迁移并准备至少一个启用角色后，可按以下路径验收：

1. 以具有 `approval:configure` 的账号进入“审批中心 → 审批流程配置”，打开“BOM 审批”，添加两个节点，第一级选角色，第二级选指定用户；切换类型时确认清空另一种选择。保存草稿后修改指定人，直接点击“发布流程”，确认发布的是刚修改的节点；指定用户必须具备审批权限。
2. 以具有产品 BOM 管理权限的账号进入“成品与物料”，为一个未送审成品配置并保存 BOM；重新打开 BOM，确认未保存修改时不能提交审批，保存后“提交 BOM 审批”可用。
3. 提交后确认 BOM 显示“审批中”且编辑控件被锁定；在“审批待办”打开该申请，核对成品编码、规格、BOM 明细、节点角色/指定用户、当前可处理人员和实际处理记录，候选人不再各自生成任务条目。
4. 使用节点角色下的合格账号明确点击“通过当前节点”，确认申请进入下一级；同一账号可继续处理下一级，但每一级都有独立记录。点击“驳回申请”必须填写原因。
5. 申请人从“我发起的”打开申请并撤回，确认申请结束、BOM 恢复可编辑；再次提交应生成新的申请并从第一级开始。全部节点通过后确认 BOM 显示“已批准”并永久锁定。
   驳回或撤回后返回已缓存的“成品与物料”标签，确认列表和此前打开的 BOM 弹窗都恢复草稿状态，无需浏览器刷新。审批通过后返回同一标签，确认弹窗同步为永久锁定。若本地仍有未保存修改且产品版本发生变化，应保留草稿并阻止保存，只有确认“重新加载 BOM”后才丢弃修改。
6. 在第一级尚未处理时加入新的合格角色成员，使用新成员账号刷新“待我处理”，应能看到并处理该旧申请，无需重新分派或历史通知；移除成员后刷新待办应消失，旧详情的迟到提交也应被拒绝。全部成员失效时申请人/管理员详情显示“暂无合格审批人”，补齐后自动恢复；指定用户节点不会因为角色新增其他成员而转给其他人。角色无人或指定用户失效时，发布、提交均应被拒绝。
7. 审批中心默认显示全部状态：普通用户范围为“与我相关”，配置管理员为“全部申请”。通过、驳回或撤回后，申请人和实际作出过通过/驳回决定的人可查看完整处理记录；仅曾是候选人、后加入角色或收到通知均不授予历史访问。“待我处理”只显示当前待办，不提供已结束状态筛选。从产品进入审批中心时也使用全部状态，不限定为本人发起。
8. 两个合格人员同时处理同一节点，只允许一次成功。保留旧详情后由另一人推进节点，旧页面再次提交不得误批下一节点。发布新流程后，已送审申请仍显示原节点配置。指定用户失效时恢复该账号资格即可继续，也可由申请人撤回后按新流程重新送审。

前端页面通过 `src/api/approval.ts` 使用审批公开契约，详情页以服务端返回的 `canApprove` 和 `canWithdraw` 决定操作入口，审批提交 `currentStepId + version`；页面按钮可见性不替代后端鉴权。组件及 API 测试覆盖角色/指定用户切换、候选刷新与失效、保存当前草稿后发布、节点命令和详情请求竞态。`typecheck:test` 检查这些测试的类型，应用构建不能替代；验证边界见[测试策略](../../docs/testing-strategy.md)。

流程配置支持第三种分派方式“业务关联人员”，具体来源与最终节点要求均由场景接口返回。批次收尾最终节点必须选择“业务关联人员 → 工单负责人”；页面提示最终放行要求，排序或删除导致要求不满足时阻止保存、发布，服务端仍独立校验。新增空流程的首个节点带入该要求，继续添加节点时插入最终节点之前。配置只保存来源规则并显示“送审时确定”，不预先选择某张工单的人；切换类型清空无关字段。审批详情区分来源、送审确定人员和真实处理人，同时展示受审快照中的来源工单及当时负责人依据。人员失效不会自动改派，恢复原审批资格后继续。

业务关联人员的黑盒验收：用同一已发布流程分别提交两张负责人不同的工单任务，检查各自待办、详情和通知中的人员；只有当次确定的负责人可处理。核对最后节点改为角色／指定用户时的阻断，以及负责人无审批资格时的错误提示。上述扩展尚待黑盒与 UI 验收，按当前约定未新增正式测试集；现有测试夹具仅适配新契约。

BOM 编辑及审批证据明细仅显示物料、单位、单位用量和备注，不提供关键物料或记录批次开关。

## 任务产出清单与结案

正常生产在“生产执行完工”后进入待结案状态，工序报工量单独保留；提前结束仍先逐项收尾。任务页、生产执行记录和 Production 追溯提供“产出清单与结案”入口。`ProductionBatchTerminationDialog` 只处理收尾事项、物料实核和处理历史；`ProductionOutputDialog` 独立负责产出草稿、质检留存及批准清单，两者提供双向入口。正常生产也必须核对物料事实，有余料时在原退料管理办理，不能用最终成品差额推算退料。

物料实核按原分配显示已领、退料占用、损耗占用及可退／可登记上限。正常和提前结束的初次结案，在 `closing` 且未送审期间可通过独立“登记损坏（不补料）”弹窗填写数量、原因；登记前再次确认永久占用可退额度，不生成需求、补料、补产或库存流水，审批驳回不会撤销损坏事实。弹窗保留打开时的版本、核对令牌和上限，依据变化后禁止沿用旧确认；提交结果未知保留原命令重试。成功后刷新物料依据并要求重新实核。物料表与逐笔损耗记录分别由独立展示组件承担，产出编辑器不增加损耗命令。

审批详情、批准清单及打印保留逐笔领料损耗记录，区分在产补料和结案不补料，展示来源需求／分配／库存批次、数量、原因、状态和登记／确认人员时间；材料损耗不计入成品报废。既有报废页统一展示两类记录及登记用途，“申报领料损耗”仍是原在产补料入口，不在本轮增加补料管理菜单。

产线管理员填写计划内产出、计划外产出及本次新增成品报废。计划内产出不超过计划；另外两项只按数量类型的非负整数上限校验，不以三项之和限制现场产出。计划缺口仅为计划量减计划内产出；历史工序报废只读展示，新增报废不重复包含历史数量或原材料损耗。工单汇总仅聚合有效批准清单，明确分别展示计划内、计划外和报废；未批准草稿另列，不计入审定产出。

质检人员在“质检记录”页签保存线下检验时间、当时申报数量快照、实检三项数量、结果说明和凭据参考。质检记录不可编辑覆盖，复检新增记录并关联前次记录，不直接改写产线草稿。产线管理员根据记录调整草稿并显式引用最新质检记录；送审要求三项申报数量与最新实检数量一致，不要求草稿版本与检验时版本相同。检验填写过程中申报依据变化时禁止提交，须重新核对。

检验结果说明及凭据编号／存放位置均必填，前端保存条件拒绝空白并与接口统一限制为 5000 字符。三项均为零时仍须由质检核实是否确无产出，留存真实结论与凭据，不豁免检验依据、不自动代填。全部报废据实登记新增成品报废，历史工序报废不重复填写；两类合格产出均为零时不办理成品入库。

送审使用当前版本和服务端核对指纹，最终由工单负责人审批。批准后形成不可变清单版本，清单支持查看关联审批与打印指定版本；历史清单明确标注不能用于入库。后续数量错误使用“发起清单更正”，保留旧批准版、新质检记录和后续审批；可显式取消未送审更正。已入库类别的批准数量不可改，更正期间入库资格仍以服务端为准。收齐本类别全部数量后仓管一次确认，清单批准本身不确认库存。

`useProductionOutput` 是详情、产出草稿、质检输入和命令意图的局部所有者；质检与批准版页签是纯展示组件。加载错误不转为空清单，关闭/切换任务后丢弃迟到响应；刷新不会覆盖未保存草稿，远端版本变化时提示重新加载。写操作有成功反馈，结果未知保留原命令和幂等键。后端独立区分产出管理与质检留存权限；前端状态控制不替代鉴权。此流程按约定等待黑盒和 UI 验收，未新增正式测试集。

## 成品入库与库存来源

入库管理仍使用 `warehouse-inbound` 路由，分为“外购物料入库”和“成品入库”两个页签。外购业务由 `PurchaseInboundPanel` 承担，成品业务由 `FinishedGoodsInboundPanel` 及其独立列表/编辑 composable 承担；页签切换保留未保存输入，隐藏非活动页签的弹窗，重新进入只刷新所属数据，不重建草稿。成品页提供“生产流转入库”和“额外产出入库”两个入口，分别选择已结案任务及当前批准清单；候选列表支持分页，不能把分页窗口未包含某项当作已失效。

仓管创建成品入库草稿时填写独立库存批次号和备注，数量由批准清单带入并只读显示，不提供拆分数量输入。每个任务的两种来源分别收齐全部批准数量后一次确认，形成不同库存批次及库存流水。待确认草稿可编辑、取消，确认成功后不能再次确认、修改或取消。批准清单更正送审期间冻结受影响类别的入库资格，旧草稿采用的批准版本失效时，详情同时显示原依据和当前批准依据；仓管明确核对数量变化后采用新版并保存，不能静默更新版本号后直接确认。新版本类别数量为零时取消旧草稿，不创建零数量入库。

成品入库详情在 `inbounds:view` 权限内展示实际采用的批准清单和质检依据，不需要任务管理权限。原审批链接仍由审批中心独立校验访问资格。确认按钮再次列出任务、批准版、完整数量和库存批次；实物不符时先线下核对，确需改清单则由产线管理员按更正流程处理，不让仓管覆盖审定数量。状态、业务来源使用共享常量；写操作由后端独立鉴权，成功反馈与未知结果的原命令重试均在当前弹窗处理。

库存查询继续提供“物料供需”和“库存批次”两种视图，只有库存批次视图纳入成品。列表可按物料/成品身份及业务来源筛选；成品展示成品编码名称、工单、任务、批准版本和同一账本的库存流水，物料继续展示精确版本。成品行的预留及可分配字段显示不适用，以账面可用量判断是否有库存，不把物料分配字段的零值误报为成品无库存。物料供需、物料分配和物料盘点仍限于物料。

库存详情的成品入库来源链接进入 `/warehouse/inbound-orders?inboundId=...`，成品入库详情的库存批次链接进入 `/warehouse/inventory?itemBatchId=...`，均复用现有稳定路由和权限边界，不为单次追溯新建菜单。该阶段等待黑盒和 UI 验收，未新增正式测试集。

跨路由定位另一张入库单前，统一确认是否放弃当前未保存草稿；取消定位保留原草稿并恢复原单据定位。提交中或结果未知时禁止换单，保留原命令的重试标识。离开页面只清除导航请求，不销毁缓存草稿，因此再次进入同一张单据也能正常定位。

工单创建表单不再手填工单号，保存成功后展示服务端生成的北京时间 `yyyy-MM-dd-N`；编辑不改号。创建结果未知时保留原请求和幂等键，提示先核对并按原意图重试，不能因修改表单自动重复建单。

## 应用与测试类型检查

常规 `build` 和 `typecheck` 只编译应用源码，不纳入相邻测试夹具；测试仍通过原 `test` 入口运行，测试代码的完整类型检查使用 `corepack pnpm --filter @company/admin-web typecheck:test`。用户确认黑盒与 UI 验收并进入正式测试阶段后，再迁移旧夹具并执行测试检查；应用构建通过不代表测试集通过。

## 工单物料版本配置与计划额度

工单列表的“物料版本配置”仅在 `mass_production` 且 `released/doing` 时出现，替换原批次管理按钮；生产任务仍由任务页管理。弹窗展示完整 BOM、精确版本及首个阻断任务，管理员填写配置原因后整份保存。失效版本保留已选编码并禁止提交；下拉展开、弹窗打开和页面激活刷新配置候选，未提交草稿不被覆盖，工单版本变化要求重新加载，保存结果未知时保留原请求重试。

批量任务需求确认只读继承工单配置，缺项或启用资格失效时提示返回工单管理；研发任务仍可拆分多个版本。配置修改不回写旧需求和物流记录，取消／提前结束须沿现有任务流程办理。

“已分配”主数排除已取消、已终止任务，存在终止历史时附注“已终止计划 N，不占额度”；收尾中和正常完工仍占用，页面激活刷新最新额度。终止任务已有审定产出继续在产出列累计，不从分配额度扣减。

新增任务选择工单后，通过同一工单候选响应展示计划、有效已分配、已终止计划、剩余额度、审定计划内／外产出与报废，并展示本次分配后的剩余量。打开、激活、展开及显式刷新均重读候选；刷新失败保留草稿和上次结果并阻止新建提交，核对新额度不会覆盖已输入的计划数量。

工单、任务及完工／关闭确认的最终数量均取当前有效批准清单；任务的 `finalOutput=null` 展示“尚无批准清单”，批准零产出正常显示零。可用合计只含计划内加计划外，报废单列；计划内累计超计划时显示“超出 N”。`lastStepReportedQuantity` 从报工事实派生，独立标为“末工序正常报工量”，不作为最终合格或入库数量；工序列表的正常量也不标为质检合格。更正草稿和历史批准版不重复计入；返回工单详情时重读当前批准结果。已确认入库类别的产出输入旁说明实际入库数量及锁定原因，未入库类别仍可更正。

## 追溯与报工记录展示

追溯页的任务概况和审定产出统一使用紧凑描述表，不在概况重复展示末工序报工量；报工数量仍可在“工序与报工”查看。审定区区分尚无批准清单与已批准零产出，展示可用合计、计划内／外产出、成品报废、计划内差额和批准版本。执行完工时间与正常结案时间分别标注，提前结束不伪造正常结案时间。

报工记录页采用相同的紧凑摘要风格；每道工序突出正常目标、已报正常、已报异常、剩余需报和当前可报，投入放行、普通报工累计与已激活补产投入在“数量依据”展开查看。有效报工条数只统计未冲销的普通报工，不包含冲销记录；明细保留原报工、更正和冲销关系。工序数量服务于执行核对，不替代质检后的批准产出，调整布局不改变原报工和补产限制。

两个页面通过 `usePageActivationRefresh` 首访立即加载一次，再次激活停留 150 ms 后自动刷新；离开或关闭标签取消待执行调度，手动刷新、查询和选任务仍立即执行。`useLatestReadRequest` 为列表、详情透传 AbortSignal，新读取替代旧读取，失活或卸载取消在途读取。响应还须通过请求代际和任务身份检查，取消不会提示为业务失败，也不取消写命令或丢失编辑草稿。

同一任务刷新保留表格直到新数据到达，切换任务先清空旧详情。报工刷新失败清空旧详情及完工依据，阻止沿用旧状态操作；追溯刷新失败保留原展示并提示错误。追溯的四个内层页签使用 `lazy`，首次点击才创建表格，之后保留。该行为的边界由[管理端架构](docs/architecture.md#6-生命周期与定向刷新)、[路由与标签页](docs/route-dialogs-and-tabs.md#3-联动流程)和[请求重试规则](docs/http-error-handling.md#4-基础请求与重试)共同说明，性能与竞态专项验收仍列在根路线图。
