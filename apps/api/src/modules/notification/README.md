# Notification

通用站内通知模块，拥有消息、固定收件集合和首次已读状态。Approval 是首个调用方；业务模块决定事件、具体用户与真实来源/目标，Notification 不重查角色、账号启停或业务资格。历史正文不因业务权限变化隐藏，详情和操作仍由目标模块鉴权。

## 公开能力

其他模块仅导入 `public.ts` 的 `NotificationService.publish(input, context)`。字段与规范化边界见[发布契约](application/notification-publish.ts)。不开放通用 HTTP 发送接口，也不提供公告管理页、删除、外部投递或自动补发。

- 事件键使用业务命名空间和稳定动作身份；不得用每次新生成的随机数、当前时间或原始 HTTP 幂等键代替。区分大小写的数据库唯一键最终防并发重复。
- 标题和正文作为纯文本保存和展示，不持久化 HTML、Markdown 链接、URL、完整单据或敏感详情。每条至多一个结构化目标；未知目标映射只显示正文，不猜地址。
- 来源表示触发动作，目标表示详情对象，可以不同或分别为空；每对类型/正整数 ID 同时传值或 null，类型在共享 constants 登记，业务事件仍遵守自身必填约束。
- 收件人去重，不排除操作者。用户存在性由外键保证；停用或软删除不丢失收件历史。
- 返回 `created/reused` 和通知 ID；新空事件返回 `no_recipients`、null，不写表或审计、不登记钩子。已有同键先比较全部规范化内容及收件集合，空集合不能绕过冲突。
- 同键内容不同返回 `NOTIFICATION_EVENT_CONFLICT`，不覆盖、补收件或重新调度。创建人和请求 ID 不参与事件内容比较，复用时保持原始审计。

## 事务与钩子

发布复用同一 pool 的活动事务；没有外层业务事务时，发布本身创建事务。消息、固定收件集合与发布审计原子保存。

提交后事件与端口见[发布契约](application/notification-publish.ts)。新消息登记、最外层提交后调度、失败隔离和 best-effort 限制统一由[通知提交后协议](../../../../../docs/notification-design.md#4-同事务落库与提交后钩子)维护。

## 接口及权限登记

前缀 `/api/notifications`。接口只读写登录用户自己的收件；不设置可撤销的业务权限条目，不往权限目录增加 `notification:*`。用户身份只取认证上下文，前端不能指定其他收件人。

| 接口 | 输入与结果 |
| --- | --- |
| `GET /` | 本人全部历史收件，公共分页；按收件 `created_at DESC,id DESC` 排序 |
| `GET /unread-count` | 返回 `{ count }`，只计算本人 `read_at IS NULL`，与审批待办数无关 |
| `POST /read-all` | 空对象 body；将本人全部未读收件标记已读，返回实际更新数量及确认前查询到的未读收件 ID |

消息列表提供纯文本、可选目标、创建时间及 `isUnread` 展示标记，不暴露阅读时间或并发版本。GET 不写阅读状态。全部已读在事务内按本人身份及 `read_at IS NULL` 执行一次集合更新，不受界面分页限制。首次更新保留数据库的版本及操作者约束，已有已读时间不覆盖；有实际更新时记录一条 `notification.read-all` 成功审计，与更新同事务提交，无变更不重复审计。

确认前查询到的未读 ID 仅用于本次面板的新消息提示，不限定更新范围，也不能据此推导实际更新数量或当前未读数。未启用 HTTP Idempotency-Key，不自动重试写请求；角标通过只读接口查询实际计数。

## 阅读与历史保留

用户打开通知面板即确认本人全部未读收件，包括尚未加载的分页；该确认不表示逐条阅读正文。普通刷新、滚动加载和角标轮询仅查询，不继续标记随后到达的消息。标记失败或结果未知时不能在前端清零，须查询实际状态；显式重试或再次打开重新执行全部已读。

阅读与目标是否可访问独立，详情导航不依赖标记成功。通知正文不因目标失效、停用或权限变化隐藏；详情和操作仍由目标模块实时鉴权，不把已读理解为业务完成，也不接入业务处理状态回调。

消息及收件长期保留，不提供用户删除、自动到期或年度清理任务。人工备份不等于可以清空；未来清理须另定恢复验证、跨期追溯和事件去重身份保留策略。纯系统通知可以无来源和目标，但仍由有身份的发布用例记录创建者，不预设定时作业或虚构操作者。

数据库定义见[数据库设计](docs/database.md)，跨模块事务及可靠性边界见[通知协议](../../../../../docs/notification-design.md)。前端拉取、会话隔离及导航约束见[管理端架构](../../../../admin-web/docs/architecture.md)，不在后端文档维护铃铛布局。

## 自动化验证

验证归属：后端相邻测试负责发布规范化、事件与引用校验及错误映射；审批适配器测试负责业务事件到发布契约的转换。真实 MySQL 用例位于根 `tests/integration/notification`，负责发布并发、全部已读、事务回滚、成功审计、HTTP 输入与本人访问和迁移保护；审批联动归 `tests/integration/approval`。数据库包测试负责通用提交后任务生命周期，管理端相邻测试负责轮询、会话隔离、全部已读、滚动加载与详情跳转。

执行命令及专用 MySQL 门禁见[测试策略](../../../../../docs/testing-strategy.md)。

契约验证范围还包括非审批形态与无来源／目标、成对空值、空收件、同键不同集合、HTTP 重放不调度、提交结果未知不触发、重试废弃事件、慢处理器和同步／异步异常隔离，以及权限变化后的历史阅读。公开契约验证不授权新增实际业务通知，也不证明外部可靠投递。
