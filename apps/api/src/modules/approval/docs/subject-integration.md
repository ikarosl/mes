# 审批场景接入与业务人员分派

当前场景由业务模块注册，Approval 负责流程与申请执行；表结构及状态见[数据库](database.md)，接口和查询权限见[模块入口](../README.md)。

## 模块与事务边界

Product、Production 通过代码注册场景及类型化 handler；场景目录与配置分离，规则见[Registry](database.md#31-代码-registry)。Approval 依赖 Identity、Notification，业务模块依赖 Approval 公开能力，Approval 不反向导入业务模块。

新增场景必须提供固定场景、独立鉴权的业务提交入口，声明支持的人员来源、必需节点规则及证据结构版本。复用通用申请和节点执行，不新增场景专属审批 SQL，不接受客户端任意指定场景、审批人或业务字段路径。

handler 负责锁定业务根、核验受审资格、生成快照和业务人员解析结果、绑定申请、恢复冻结以及最终业务生效。绑定后的业务版本以 handler 返回值保存，不假定所有模块都加一。审批详情由 Approval 解码证据，再由业务 handler 校验结构版本和补充当前显示引用；BOM 物料解析由 Product 所有，不在证据中复制名称主数据。

提交按以下顺序在同一事务完成：锁业务根并核验受审内容 → 固定已发布流程 → 解析全部节点实时资格 → 创建申请和节点（首级 pending，其余 waiting）→ 绑定业务对象 → 审计和通知。配置仓储与运行仓储的协作不向 application 暴露连接；人员资格仅经 Identity 公开能力读取。

后续决定／撤回先只读定位，再由 handler 锁业务根，核验当前申请引用和冻结版本，最后锁申请及节点。非末级通过只推进节点；末级通过与业务生效同事务，驳回／撤回恢复可编辑状态。单节点最多一个实际决定由唯一约束保护；成功审计及通知与核心变化一起提交，失败全部回滚。

提交后的证据、流程及实例人员不改写；实时资格、无人可审和历史访问规则见[运行契约](../README.md#配置与操作)。业务错误由 handler 映射到公开结果。

表约束见[数据库设计](database.md)，BOM 门禁见[Product](../../product/docs/product-rules.md)。当前证据联合区分 BOM 和需求更正；扩展联合只新增明确的场景类型及 owner 校验，不使用任意 JSON 代替类型边界。

## 业务关联人员

业务关联人员是独立于角色和指定用户的通用分派类型，来源由场景声明白名单，不接受任意字段路径、SQL、脚本或客户端临时指定审批人。当前 BOM 和需求更正场景均未声明此类来源。

已发布流程节点保存分派类型及来源代码；具体申请的业务来源节点保存送审事务中解析出的唯一用户 ID。来源规则引用不可变流程节点，解析依据由所属业务的受审证据保留。业务身份固定后，账号是否启用及审批权限仍由 Identity 公开能力实时校验；被解析为业务人员不自动获得审批权限。

场景必须通过 handler 声明支持的来源和必需节点规则。保存及发布时校验来源白名单和节点规则；送审时在业务根锁内解析具体人员、检查资格，并与受审快照、申请绑定、审计及通知整体提交。Approval 不直接读取业务模块的表，也不在模板中保存某个业务对象的当前人员。

待办、计数、详情、决定与通知使用本次解析人员及实时资格，不能从最新业务资料重新推断。新流程不改变在途申请；资格失效保持阻塞，不自动换人。重新送审建立新申请并重新解析，旧证据与决定保留。人员回避、代理和转交没有隐含规则。
