# 审批场景接入与业务人员分派

当前场景由业务模块注册，Approval 负责流程与申请执行；表结构及状态见[数据库](database.md)，接口和查询权限见[模块入口](../README.md)。

## 模块与事务边界

Product、Production 通过代码注册场景及类型化 handler；Registry 只装配能力，不保存 SQL、任意回调地址或前端组件路径。场景定义与数据库流程配置分开，未配置的代码场景仍可出现在管理查询。Approval 依赖 Identity、Notification，业务模块依赖 Approval 公开能力，Approval 不反向导入业务模块。

新增场景必须提供固定场景、独立鉴权的业务提交入口，声明支持的人员来源、必需节点规则及证据结构版本。复用通用申请和节点执行，不新增场景专属审批 SQL，不接受客户端任意指定场景、审批人或业务字段路径。

handler 负责锁定业务根、核验受审资格、生成快照和业务人员解析结果、绑定申请、恢复冻结以及最终业务生效。绑定后的业务版本以 handler 返回值保存，不假定所有模块都加一。审批详情由 Approval 解码证据，再由业务 handler 校验结构版本和补充当前显示引用；BOM 物料解析由 Product 所有，不在证据中复制名称主数据。

提交按以下顺序在同一事务完成：锁业务根并核验受审内容 → 固定已发布流程 → 解析全部节点实时资格 → 创建申请和节点（首级 pending，其余 waiting）→ 绑定业务对象 → 审计和通知。配置仓储与运行仓储的协作不向 application 暴露连接；人员资格仅经 Identity 公开能力读取。

后续决定／撤回先只读定位，再由 handler 锁业务根，核验当前申请引用和冻结版本，最后锁申请及节点。非末级通过只推进节点；末级通过与业务生效同事务，驳回／撤回恢复可编辑状态。单节点最多一个实际决定由唯一约束保护；成功审计及通知与核心变化一起提交，失败全部回滚。

提交后的证据、采用流程和实例解析人员不改写。无人可审只派生 blocked，不在 GET 中写表或重新分派；待办、计数、详情、决定及通知共用实时资格。新发布版本不改变在途实例。公开错误由 handler 映射，不泄漏业务 domain 类或 SQL 异常。

表约束见[数据库设计](database.md)，BOM 门禁见[Product](../../product/docs/product-rules.md)。当前证据联合区分 BOM、需求更正和任务收尾；扩展联合只新增明确的场景类型及 owner 校验，不使用任意 JSON 代替类型边界。

## 业务关联人员

### 流程规则与本次人员分开保存

- “业务关联人员”是独立于角色和指定用户的分派类型。来源由场景声明白名单，任务结案首个来源为“工单负责人”；来源代码由后端定义，不接受任意字段路径、SQL、脚本或客户端临时指定审批人。
- 已发布流程节点保存分派类型及人员来源代码，不保存某张工单的负责人 ID。同一版本应用于工单 A、B 时，可分别解析为甲、乙；只有节点或来源规则改变才需要发布新版本。
- 本次申请的业务来源节点保存送审时解析出的唯一用户 ID，并通过用户外键约束；来源规则仍引用不可变流程节点，来源工单及负责人的解析依据保留在本次受审证据中。此结果是本次分派事实，不是工单负责人第二份可变主数据；不修改模板的固定用户字段来适配单次申请，也不按人生成任务表。
- 原有角色和指定用户分派保持当前语义。业务来源节点固定本次身份，账号是否启用及 `approval:decide` 是否有效继续实时校验；被解析为负责人不自动赋予审批权限。

### 场景解析与事务

- 公开场景描述与 `ApprovalSubjectHandler` 适配契约要求：业务模块声明支持的人员来源及场景必需规则，并在送审事务内解析来源。Production 负责按任务找到所属工单、读取 `work_order_owner_id` 并校验归属；不得使用 `batch_owner_id`、申请人或请求体中的用户替代。Approval 继续决定流程版本与节点，由 Identity 公开能力校验人员资格，不直接读取 Production 表。
- 流程发布时，业务来源节点校验来源受该场景支持、解析能力已装配、场景必需节点规则成立；此时尚无具体任务，不要求预先指定某个负责人。角色／固定用户节点仍保留当前人员有效性校验。送审时在固定业务对象与流程版本的事务中解析具体人员、检查资格、保存解析结果，并与受审快照、申请绑定、审计及通知整体提交。
- 任务结案及清单更正的最终放行节点必须采用“工单负责人”来源；该约束在保存／发布和送审后端校验，不能靠界面默认值保证，不能配置为任意角色后绕过。最后一个节点为工单负责人即可满足本需求，不强制两级；若配置其他管理节点，工单负责人仍负责最终放行。新申请采用符合末级规则的发布版本；当前开发数据可清空重建，不保留旧版审批兼容逻辑，也不补造负责人批准。
- 送审缺少负责人、负责人账号无效或无审批权限时给出明确业务错误，不自动回退到申请人、管理员或同角色人员。工单草稿负责人可空且普通编辑仅限草稿，下达须有有效负责人，送审再检查实际审批资格。
- 当前不新增负责人转交能力。送审后不能因配置发布或人员变化静默换人，资格失效保持阻塞；恢复原人资格后可继续。以后若开放已下达工单负责人交接，须保留交接依据，并明确在审先撤回、交接后重新送审的边界，不用读取最新负责人来改写旧实例授权。


业务节点的待办、计数、详情、决定与通知使用实例解析人员及实时资格；不可从模板固定用户或当前工单负责人重新推断。详情区分来源规则、送审确定人员、实际处理人。更正是新申请，重新解析但保留前版关联；新发布版本不改变在途实例。

允许申请人自审及同人逐级处理，各级独立决定。人员回避、代理和转交没有隐含默认规则，新增能力须另行明确，不能靠动态分派改写在途授权。
