# 迁移安全

迁移运行器在专用连接上获取 MySQL 建议锁 `easy_mes_migration`，然后读取校验和或执行 SQL。锁在 `finally` 块中释放，即使迁移失败也不例外。每条迁移只有在 SQL 执行成功后才会被记录。

迁移始终为仅追加（append-only）。新鲜验证会对一个干净的 MySQL 8.4 数据库应用所有迁移，然后再次运行迁移命令以证明待处理状态处理的幂等性，若存在待处理或校验和不匹配的文件则状态验证失败。升级和并发迁移器集成测试仍是下一个必需的测试环境里程碑。

回滚验证须覆盖空库全量 up/down/up，并在物料版本需求迁移边界比较回滚前后的索引定义。删除外键不会自动删除其支撑索引；down 必须清理本迁移引入且不再被使用的索引，不能依靠后续删表掩盖残留。恢复旧外键所需的支撑索引后，才能删除替代它们的组合索引。

系统基础数据位于 `packages/database/seed`，由 `pnpm db:seed` 幂等写入；测试业务数据仍由各 integration fixture 自行创建和清理。`pnpm db:init` 统一编排 migration、seed 和管理员账号初始化，但不能替代 migration fresh、升级迁移或并发迁移器测试。权限目录与应用代码和接口版本绑定，继续由对应的不可变 migration 管理，不与账号或测试 fixture 混放。演示或联调样例数据不属于系统基础数据，置于独立的 `packages/database/demo` 目录，由显式命令 `pnpm db:seed:demo` 加载。命令要求 `ALLOW_DEMO_SEED=1` 和单独的 `DEMO_USER_PASSWORD`，按业务编码幂等更新 System 演示角色/账号与 Product 主数据和 Production 草稿工单；`db:init`、生产部署与 CI 均不得自动加载。

数据库运行器保留两类入口：开发与 CI 使用 `tsx src/*.ts`，避免每次修改后手工构建；对应的 `*:compiled` 脚本使用 `node dist/*.js`，只消费构建产物。两类公开包脚本都先交给 Turbo 构建 workspace 依赖，带 `:run` 后缀的内部任务只供 Turbo 调度。API 生产镜像通过 `pnpm --filter @company/api build` 预先构建 `@company/database`，并通过 deploy 产物携带 `dist`、`migrations` 和 `seed`，不安装或运行 `tsx`。CD 迁移阶段必须以同一不可变 API 镜像执行一次性命令 `node node_modules/@company/database/dist/migrate.js`；成功后才允许启动或更新 API 工作负载。

成品/物料拆表与工单类型迁移只接受空业务表，失败守卫位于结构变更之前；旧业务数据无需保留，可重建开发库。回滚同样仅限空业务表，不尝试恢复路线产品归属或推断历史工单类型。完整 schema 验证须覆盖 up/down/up 与 demo 重复加载；应用接入新结构的待办见[roadmap](../../../docs/roadmap.md)。

移除基础物料余额投影的迁移及回滚须暂停库存写入，避免 MySQL 非事务 DDL 替换触发器期间产生漏记。升级保留批次与精确版本余额及其维护，只删除冗余物料余额；回滚从库存流水和当前批次状态重建物料余额，并恢复相应触发器，不改写流水或其他余额，重建投影的版本计数从零开始。迁移锁只互斥迁移运行器，不代替业务写入暂停；若 DDL 中途失败，应保持写入暂停并检查、修复实际结构后再恢复服务。

库存版本余额触发器的局部字符变量显式使用业务 schema 的 `utf8mb4_0900_ai_ci`，不得继承部署连接的 `collation_connection`；否则连接排序规则不同时，库存流水写入会在批次状态比较处失败。替换该触发器同样要求暂停库存写入。

物料名称实时展示迁移删除需求基础、需求、库存批次和入库明细的四个名称快照列，不改编码、单位、版本、流水或余额。须暂停相关 API 写入并与新应用一起发布，避免旧写入器引用已删除字段。MySQL DDL 非事务性，中途失败需检查实际结构后恢复。回滚只允许四张表为空：当前名称无法重建原历史名称，down 在任何结构变更前检查并拒绝非空表；开发环境可按统一流程重置，不生成伪历史名称。

全工序报工迁移删除路线的报工开关与批次对应快照列，并移除员工单独完成工序权限及角色关联。升级前暂停相关 API；若存在旧免报工批次工序，迁移在 DDL 前拒绝，应按开发约定重置业务数据，不补造报工事实。回滚要求路线步骤及批次工序表为空，恢复权限目录但不重建旧角色授权。MySQL DDL 非事务性，中途失败须检查实际结构后恢复。

BOM 审批试探迁移 `202609100001` 先拒绝存在旧任务锁定 BOM 的开发数据，再创建七张审批表并为 products 增加状态、当前申请及并发版本；不伪造人工审批历史。升级前暂停 Product/Production 写入，与新 API 一并切换。开发库可重建；down 在任何修改前拒绝已有审批申请，不隐式丢弃决定证据。

BOM 标志移除迁移 `202609110001` 删除 Product BOM、Production 需求基础和需求中的两个标志列及对应 CHECK，保留 BOM 状态/软删除 CHECK。升级须暂停相关 API 写入并切换新应用；不改写已有审批 JSON 证据。down 在任何 DDL 前要求这三张表为空，不能凭默认值重建已丢失的标志；开发环境允许重置。

审批节点迁移 `202609120001` 将既有角色配置转为明确的 `role` 类型，增加指定用户外键及角色/用户二选一 CHECK；删除个人任务表与动作 task_id、分派轮次及持久化阻塞原因，将 blocked 节点恢复为 pending 并由实时资格派生提示。真实决定、操作者、时间与意见保留，新增单节点有效决定唯一约束，删除重新分派权限及授权。升级前暂停相关 API 并同步切换新契约，不能让旧应用继续写个人任务；MySQL DDL 非事务性，失败后先检查实际结构。down 在任何 DDL 前要求无审批申请且无指定用户配置，无法恢复已丢弃的个人任务，亦不能把用户配置猜测为角色；恢复旧权限目录但不补造角色授权。开发库可统一重建，无双写或影子表。

审批回滚以 `202609130001` 与 `202609120001` 为连续边界：先执行前者 down，再执行后者 down，期间保持相关写入暂停。MySQL 在含存储生成列的表重建时，不能直接收紧仍带外键的 `role_id`；追加的准备迁移先做相同的数据守卫，再分别移除角色外键、恢复非空列并重建同名外键，使不可修改的旧 down 可以继续。该准备状态不能单独作为可运行的应用版本；若准备后取消回滚，重新执行 `202609130001` up 恢复可空列后才能恢复服务。正常 up 保持当前角色/用户模型和所有外键，不改业务数据；不修改旧迁移，不关闭外键检查。

需求关闭／替代与逐项收尾迁移 `202609150001-production-demand-correction-and-closeout` 增加 Production 的更正申请、收尾主记录及不可变行动表，扩展需求 closed／在审与替代关系、批次 closing 和工序 terminated；需求事实和库存账本不复制。升级前暂停 Production 和相关审批写入，并切换新应用。首个永久 DDL 前拒绝旧批量关闭语义的 cancelled 需求（cancel_source 非 production_batch），开发数据可按统一约定重建，不能补造审批证据。

该迁移 down 在任何持久变更前拒绝已存在更正／收尾记录、closed／替代／在审需求、closing 批次、terminated 工序或新场景流程配置；不丢弃真实中间态和审批历史。只在未使用的新结构上允许回退，顺序先解除工序／需求引用，再删新表。MySQL DDL 不整体回滚，应用失败须保持写入暂停，核对实际结构；不改已成功执行文件，不关闭外键保护或建立兼容影子表。

审批业务人员迁移 `202609160001` 为模板追加来源代码与三选一约束，为实例追加解析人员外键与待办索引。暂停 Approval 及相关业务写入后迁移并同步部署；不改写已有配置、在途分派或受审证据，旧结案配置须发布新版本才能提交新申请。down 先拒绝任何业务来源配置或实例解析人员，避免丢失分派事实；未使用该能力时可回退。DDL 失败仍需检查实际结构后恢复，开发环境可统一重置。

统一产出清单迁移 `202609170001` 在首个永久 DDL 前拒绝旧收尾、终止、结案申请及已完成／终止／收尾批次，开发库先统一重建，不转换旧审批快照。迁移沿用收尾草稿，新增不可变质检和批准版本，删除旧终止事实表，不双写；批次执行完成时间与最终结案时间分开。down 先拒绝任何新草稿、质检、批准版及执行完成时间，解除根与不可变事实间的外键后删除新表、列和专用索引，恢复旧空结构。不可变事实不可通过 down 隐式丢弃；开发重置后可重新按全部 migration 恢复最新版。

成品入库迁移 `202609170002` 仅接受空库存批次、入库单据、流水及余额投影；暂停所有库存写入后通过开发重置切换，不推断旧成品身份。物料组合 FK 保留，成品追加 product_id 分支、互斥 CHECK、来源组合 FK 和同任务同类有效入库唯一键；替换余额触发器时仅物料分支维护精确版本桶，单一库存流水不变。down 同样要求空库存，在收紧物料非空约束前解除相关 FK，恢复原触发器并清理新索引。若任一 DDL 失败须检查实际结构后重建，不修改已经成功执行的文件。

分类重命名迁移 `202609170004` 将共用分类树直接改名为 `item_categories`，同时统一分类自身的索引、外键和检查约束名称；不复制数据、改写 ID 或创建兼容别名。产品、物料和分类父节点的引用随重命名保持一致。升级和 down 均须暂停 Product 写入并切换匹配应用；down 恢复完整原名，保证此前迁移仍可按序回滚。表重命名与后续 ALTER 不构成整体事务，失败时保持写入停止、核对实际表名和约束后恢复；开发库仍可通过重置重建。
