# 迁移安全

本页维护迁移的执行前提、失败恢复和特殊回滚条件。只在初始化、升级或回滚经过对应迁移时查阅其条目；历史中间结构不代表当前 schema，也不证明某个环境已经执行迁移。当前表结构由[业务所有者](../README.md#业务数据库设计)维护，待执行状态通过迁移运行器查询。

## 通用执行要求

- 迁移文件及顺序遵守[追加与注册规则](90-migration-order.md)。修正通过新迁移完成，不修改已执行文件，不关闭外键检查，不建立兼容双写或影子结构。
- 变更字段、外键、触发器或应用写入契约时，先暂停受影响的业务写入，再执行迁移并切换匹配版本的应用；经过多个边界时覆盖其全部写入方。新 schema 未就绪前不得启动匹配的新应用，旧应用也不得继续写入已变更的结构。当前部署脚本的停写责任缺口见 [CO-04](../../../docs/documentation-conflicts.md#co-04)。
- 运行器在专用连接取得 MySQL 建议锁 `easy_mes_migration` 后读取校验和及执行 SQL，在 `finally` 中释放锁；仅 SQL 成功后登记迁移。此锁只互斥迁移运行器，不会暂停 API 或其他业务写入。
- MySQL DDL 与迁移登记不能整体事务回滚。中断后保持相关写入暂停，核对实际表、列、索引、外键、触发器和登记状态，处理部分完成结构后才恢复；不能假设失败即还原，也不能通过改旧文件或伪造登记掩盖失败。
- 不可恢复或无法真实转换的业务事实应由迁移在永久 DDL 前拒绝；不猜测旧配置、检验、审批或名称快照。开发库可按[统一初始化流程](../../../ops/runbooks/database-initialization.md)重建，回滚守卫拒绝不等于可以强制删除事实。
- 回滚使用成对 down，并遵守具体依赖顺序。删除外键不自动删除支撑索引：清理本次引入且不再使用的索引；先恢复旧外键所需索引，再删除替代组合索引，不能依靠后续删表掩盖残留。

初始化、seed/demo 和本地命令见[数据库包](../README.md)、[系统种子](../seed/README.md)与[演示数据](../demo/README.md)；镜像构建、一次性迁移及部署切换见[发布手册](../../../ops/runbooks/compose-server-deployment.md)。这些使用说明不在本页重复维护。

## 特殊迁移边界

以下只列需要额外注意的守卫、依赖或恢复条件，不是完整迁移注册表。通用停写及匹配应用要求适用于每个结构切换；精确守卫和语句以对应 up/down SQL 为准。

### 202609040002：物料版本需求

回滚验证除全量 up/down/up 外，还须在此边界比较前后索引定义，确认旧外键支撑索引恢复、替代组合索引清理。后续删除整张表不能替代该检查。

### 202609070001：成品、物料与路线拆分

up/down 均只接受相关空业务表。回滚不能推断原路线产品归属或历史工单类型；保留 DDL 前守卫，开发数据通过重建处理。

### 202609080001：移除基础物料余额投影

替换投影触发器期间暂停库存写入，保留批次与精确版本余额。down 从库存流水和当前批次状态重建基础物料余额并恢复触发器，不改流水或其他余额；重建投影的版本计数从零开始。

### 202609080002：基础物料名称快照

应用须同步停止读写被删除的四个名称快照列。down 在结构变更前要求四张表为空：当前名称不能还原当时的名称快照，不允许用当前值伪造历史。编码、单位、精确版本及库存事实不随此转换。

### 202609080003：全工序报工

up 在 DDL 前拒绝旧免报工批次工序，不补造报工事实。down 要求路线步骤及批次工序表为空，恢复权限目录但不重建旧角色授权。

### 202609090001：版本余额触发器排序规则

暂停库存写入后替换触发器。局部字符变量显式采用业务 schema 的 `utf8mb4_0900_ai_ci`，不得继承部署连接的 `collation_connection`，避免批次状态比较因连接排序规则不同而失败。

### 202609100001：BOM 审批

up 拒绝存在旧任务锁定 BOM 的开发数据，不伪造人工审批历史；暂停 Product/Production 写入。down 在修改前拒绝已有审批申请，不能隐式丢弃决定证据。

### 202609110001：BOM 标志移除

不改写既有审批 JSON 证据。down 在 DDL 前要求 Product BOM、Production 需求基础和需求三张相关表为空，不能以默认值恢复已丢失的两个标志。

### 202609120001、202609130001：审批分派与连续回滚

`202609120001` 切换期间暂停相关 API，旧应用不得继续写个人任务。迁移保留真实决定、操作者、时间和意见；down 在 DDL 前拒绝已有审批申请或指定用户配置，不恢复已丢弃的个人任务、不猜测用户对应的角色，恢复旧权限目录但不补造角色授权。

回滚必须先执行 `202609130001` down，再连续执行 `202609120001` down，期间保持相关写入暂停。准备迁移先执行同样的数据守卫，再移除角色外键、收紧列并重建同名外键，以规避 MySQL 在存储生成列表重建时不能直接收紧外键列的问题。

**准备状态不能单独启动应用。** 若准备后取消回滚，须重新执行 `202609130001` up，将 `role_id` 恢复为可空后才能恢复服务。正常 up 不改变角色/用户模型、外键或业务数据。

### 202609150001：需求关闭替代与逐项收尾

up 在永久 DDL 前拒绝旧批量关闭语义的 cancelled 需求（`cancel_source` 非 `production_batch`），不补造审批依据。切换暂停 Production 和相关审批写入。

down 在修改前拒绝更正/收尾记录、closed/替代/在审需求、closing 批次、terminated 工序或新场景配置；只允许未使用的新结构回退，先解除工序/需求引用，再删新表，不能丢弃真实中间态和审批历史。

### 202609160001：审批业务关联人员

暂停 Approval 及相关业务写入。已有配置、在途分派和受审证据不改写；旧结案配置须按工单负责人末级要求发布新版本后，才能提交新的结案申请。down 拒绝已有业务来源配置或实例解析人员，仅在未使用该能力时允许回退。

### 202609170001：统一产出清单

up 在永久 DDL 前拒绝旧收尾、终止、结案申请及已完成/终止/收尾批次，不转换旧审批快照。down 拒绝新草稿、检验、批准版及执行完成时间；先解除根与不可变事实间外键，再删除新结构及专用索引，恢复旧空结构。

### 202609170002：成品入库身份

up/down 均要求库存批次、入库主从、流水和余额投影为空，并暂停所有库存写入，不推断旧成品身份。up 临时解除受可空性变更影响的物料外键，完成互斥分支后原名恢复；down 先解除成品引用和触发器，再收紧原物料非空列、清理新增索引，恢复原外键与投影触发器，并移除该迁移新增写权限。物料精确版本余额只由物料分支维护。

### 202609170004：分类表重命名

暂停 Product 写入并同步切换应用。表、索引、外键和 CHECK 名称同步改名，ID 和父子引用保留；down 恢复完整旧名，保证此前迁移可顺序回滚。重命名和后续 ALTER 非整体事务，中断后先确认实际名称和约束。

### 202609170008：移除批次完成计数

应用停止读写旧列，报工、检验、批准版和库存事实不改。down 仅对有执行完成时间的任务从末工序报工重建旧完成量，未使用质量列恢复零，不将批准产出伪造为旧质量事实。

### 202609190003：整数数量存储

25 个历史数量列从 `DECIMAL(12,4)` 改为 `INT`；原整数约束保证没有小数，不舍入回填。保留符号、空值、盘点差额生成表达式及八位业务范围，应用同步返回整数字符串。down 恢复原类型并删除新增范围 CHECK，现有范围内数值可无损恢复。

### 202609200003、202609200007：成品检验数量结构

两次 up/down 均在永久 DDL 前拒绝已有产出检验、批准版、结案审批或冻结证据。不推测旧检验方式、旧剔除量或实物范围，不将旧审批快照解释成新 schema。切换暂停 Quality/Production/相关 Approval 写入。

`202609200007` 对应应用使用审批证据 schema 6 和成品检验命令 v2 scope。该说明仅适用于这个发布边界；当前数量公式、字段与调用规则见 [Quality 成品检验](../../../apps/api/src/modules/quality/docs/finished-inspections.md)，不从历史迁移说明推导现行业务。

### 202609200004：领料损耗只记录事实

up/down 均要求相关损耗、需求、补料及结案审批证据为空，不转换自动补料的历史依据。工序报废补料不随本次切换移除。

### 202609200005：成品检验所有权切换

暂停 Quality/Production/Approval 写入。同一事实表改名及触发器/索引切换保留原引用，不复制记录、不改写批准证据；不把此中间表名当作最新结构。

### 202609210001、202609210002：统一检验与正式分配

up 顺序先统一 Quality，再切换正式分配；down 反向。上下行均在永久 DDL 前拒绝相关已有事实，不伪造无法转换的剔除量或历史依据。暂停相关 API 写入并同步切换应用；中间版本的 scope/分配结构不代表当前模型。

### 202609210003：质量补发依据

暂停 Procurement 写入。up 通过实际退回已有 `acceptance_line_id` 转换采购来源，不新增退回或质量事实。down 在永久 DDL 前拒绝已有质量处置来源引用，不能猜测一个实际退回 ID。

### 202609220001、202609230001：处理轮次与不可变分配

两次 up/down 均在永久 DDL 前拒绝相关来料业务事实，不推断历史轮次或授权，不改写成品检验和批准事实。前后端与 schema 同版切换，开发库通过统一入口重建。

`202609220001` 的人工拒收可空引用规则属于中间结构；`202609230001` 后实际入退直接引用不可变 allocation，scope 已移除。当前字段及资格见 [Procurement 数据库](../../../apps/api/src/modules/procurement/docs/database.md)与 [Inventory 数据库](../../../apps/api/src/modules/inventory/docs/database.md)。

### 202609240001、202609240002：统一分次入库及权限回滚准备

升级先执行 `202609240001` 的结构切换，再执行 `202609240002` 幂等核对当前成品入库确认权限路径、移除旧创建/取消草稿权限。切换期间暂停 Production、Quality、Procurement、Inventory 入库及库存写入。`202609240001` 在永久 DDL 前要求入库主从、批次、流水、到货、批准版、检查和结案根均为空；无法真实转换旧单批次或整类批准量，开发库应通过统一初始化入口重建。两次迁移均不恢复或伪造角色授权。

回滚必须保持停写，先执行 `202609240002.down`，紧接着执行 `202609240001.down`，期间不得单独启动旧版或新版应用。前一步仅在上述业务事实为空时恢复 `202609170002` 定义的旧创建、确认、取消权限元数据及路径，不恢复已删除的 `role_permissions`；此时权限目录与新版表结构暂不匹配，只是连续回滚的准备态。后一步恢复旧表、索引、约束与触发器。两步 down 的非空守卫拒绝丢弃任何真实业务事实；若中断，继续停写并核查实际结构及迁移登记，不修改已执行迁移或伪造旧角色授权。

### 202609290001：外购物料入库逐明细供应商

暂停 Procurement、Inventory 入库及库存写入，并同步切换读取入库来源的应用。up 将已确认外购入库主单 provider 原文转存到所属物料明细的 supplier_name_snapshot，随后删除主单字段；在永久 DDL 前拒绝非外购 provider、存在 provider 却没有承接物料明细的主单，以及已引用正式分配却没有旧供应商名称的外购明细，避免遗失或伪造历史文本。成品明细不回填该字段，现有来源、数量、目标批次和流水保持不变。

down 在永久 DDL 前拒绝同一外购入库单下不一致的供应商名称快照，或非外购明细中的供应商快照；不能选择其中一行冒充整单供应商。允许回退时才恢复主单字段、回填一致原文并移除明细字段。业务边界见 [ADR-0018](../../../docs/adr/0018-purchase-inbound-multiple-suppliers.md)，当前结构见 [Inventory 数据库](../../../apps/api/src/modules/inventory/docs/database/inventory-ledger-and-inbound.md)。

### 202610080001：成品检验只记录检查事实

暂停 Quality、Production 结案与相关 Approval 写入，迁移后同步切换应用。up/down 均在永久 DDL 前拒绝已有成品 case/record、批准版本、结案审批或根冻结快照；旧整批送检量与建议量不能伪装为新版检查事实，新版样本也不能用于回填旧整批量。开发库通过统一初始化入口重建，不改写不可变检验或审批证据。共享 `covered_quantity` 列保留，但新成品与来料结果均必须为 NULL；来源申报和来料定稿核实量不受影响。普通全检／抽检仅约束 G/F 与正数 N=G+F，成品零量核实继续要求 G=F=0 且明确放行。应用使用结案审批快照版本 8 与成品登记幂等 scope v3；需求更正审批版本及来料写入语义保持不变。

### 202610080002：共用入库查看权限

同步切换入库页面与后端读取接口，将 `production:inbounds:view` 原行改名为 `warehouse:inbound:view` 并归入仓储页面目录。up/down 保留权限 ID、启停／删除状态、既有角色授权和子权限引用，不修改业务表、不重建角色授权；写权限编码保持独立。up/down 均要求新旧编码合计恰好一条且目标父节点存在，缺失或并存时拒绝。若 SQL 已成功但运行器未完成登记，只有目标编码的元数据完全匹配本次迁移时才允许安全重跑，不插入第二条权限或猜测授权合并。

down 原位恢复旧编码及旧目录元数据，须同时回退应用。前后端与权限目录按同版切换；后端每次认证读取当前授权，管理端需刷新页面恢复最新会话权限。demo 的生产管理员授权显式包含新查看编码，不依赖 `production:%` 前缀。目录规则由 [Identity](../../../apps/api/src/modules/identity/docs/database.md#14-permissions)维护；角色验收与成对迁移正式覆盖见[路线图](../../../docs/roadmap.md#采购到入库与来料整批处理待验收)。

### 202610100001：返工完成双结果引用

暂停 Production 执行、异常和返工写入，迁移后同步切换应用及返工完成 v3 幂等结果。up 在首个永久 DDL 前核验来源及 approved/rework 处置同源，拒绝缺失、混合、被冲销、替代或不同源的 scalar 完成事实；已有纯正常或纯异常结果保留原报工、编号和数量，仅归入真实对应引用。未完成返工的两个引用为空合法，不要求清空其他业务数据；返工版本、操作者及原更新时间保留。

down 在永久 DDL 前拒绝存在正常与异常双子结果，或单侧结果缺失、失效、数量及归属不符的记录。只允许真实单侧结果还原旧 scalar，不合成混合报工、不删除任何结果或处置事实；同时恢复旧外键及其支撑索引，清理本次新增的两个唯一键、组合索引和引用。两次 ALTER 与引用移动无法整体事务回滚，失败后保持停写并核对实际结构和迁移登记，不修改已执行文件或伪造登记。

## 验证边界

- 空库 fresh 验证应用全量迁移后再次运行，核对无待执行或校验和冲突；`db:init` 不能替代迁移验证。
- up/down/up 验证另需检查边界索引、空/非空守卫和中间状态；升级及并发迁移器验证是独立覆盖项。
- 涉及成品、物料与路线拆分的完整 schema 验证还须覆盖 demo 重复加载，确认 Product/Production 只补缺失样例，不覆盖已有业务编辑或批准事实。
- 验证是否已完成、用户验收及正式测试排期由[测试策略](../../../docs/testing-strategy.md)和[路线图](../../../docs/roadmap.md)维护，不由本页的执行要求推断。

### 202609280001：业务日序号与库存批号唯一

暂停 Production、Procurement、Inventory、Approval 及演示写入。up/down 在永久 DDL 前要求所有相关编号业务表和 http_idempotency_records 为空；不转换旧编号、幂等快照或重建历史计数，开发数据使用统一初始化入口重建。up 创建平台 business_number_daily_sequence、为 item_batch.batch_code 增加全局唯一键并删除旧 work_order_daily_sequence；down 反向恢复空结构，工单编号不可变触发器始终保留。旧应用与新 schema 不混跑，回滚后须切回对应应用。全局批号唯一不限制 inbound_detail 对同一 batch_id 的多次引用。
