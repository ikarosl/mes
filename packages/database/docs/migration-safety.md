# 迁移安全

本页维护当前迁移的执行前提、中断处理和回退边界。当前结构由[业务所有者](../README.md#业务数据库设计)维护，初始化范围及旧链退役由[基线规则](90-migration-order.md#初始化基线)维护；不从历史迁移中间结构推导现行业务。

## 发布前提

- 变更字段、外键、触发器或写入契约前，暂停全部受影响写入，包括 API、后台作业、外部连接与人工操作。部署锁和 MySQL 建议锁不能代替业务停写。
- 发布采用不可变镜像 digest；备份必须记录与数据匹配的应用版本。已有库正常增量发布不运行管理员重置或 demo。
- 执行前确认备份已完整生成、有校验和且有恢复演练依据，并明确迁移失败时使用备份恢复还是已审核的前向修复。备份与恢复操作由[MySQL 运维手册](../../../ops/runbooks/mysql-backup-restore.md)维护。
- 新 schema 未就绪前不得启动新应用，旧应用不得继续写入已经变更的结构。应用启动失败不授权自动恢复旧镜像；必须先核对数据库兼容性，必要时恢复迁移前备份及对应应用。
- migration 不关闭外键检查、不建立兼容双写或影子结构，不猜测无法真实还原的业务事实。基线之前的开发库只支持按统一入口重建。

## 运行状态与中断

运行器在专用连接取得 `easy_mes_migration` 建议锁，核对文件身份、校验和、连续登记及未完成状态后才执行 SQL。每份文件执行前持久化 running，整份 SQL 成功后改为 applied；失败尽力改为 failed。进程崩溃、连接断开或登记结果未知时可能留下 running。两种未完成状态均阻止后续迁移和自动重跑，状态命令返回非零；具体字段由[登记表](../README.md#迁移登记表-_schema_migrations)维护。

MySQL 支持的单条原子 DDL 不等于整份 migration 可以事务回滚：前面成功的建表或改表可能已经提交，后面的失败不会还原它们。applied 只说明该文件执行和登记完成，也不证明实际 schema 未被人工更改。缺少成功记录不能解释为该文件没有执行过。

失败时按以下顺序处理：

1. 保持维护状态及所有相关写入暂停，保留候选／原应用 digest、备份位置、失败文件名和错误码；不启动不匹配的旧应用，不连续点击重试。
2. 使用 `db:migrate:status` 只读核对登记，并核对真实表、列、索引、外键、CHECK、触发器及数据；确认已完成与未完成部分。状态查询不代替实际结构核验。
3. 新基线初始化且没有业务数据时，可在新的空库重新初始化。已有业务库优先将迁移前备份恢复到新库，核验后切换数据库配置和匹配的旧应用；保留失败库用于诊断，不覆盖唯一原始数据。
4. 选择前向修复必须先审查精确的恢复 SQL 和目标结构，在隔离副本验证；只有实际结构、数据与整份迁移目标一致后才能人工校正登记。没有通用的“忽略失败”或自动标记成功入口，不能靠删除 running／failed、改 checksum 或重放整份 SQL 掩盖不确定状态。
5. 核对后续迁移、应用 readiness 及必要业务路径，通过后才按运维入口恢复写入。恢复数据后须处理客户端旧草稿、未知请求结果以及外部系统已执行而本库回退的事实。

备份只恢复到备份时点。恢复后若丢弃了备份之后的写入，需要单独核对和补偿；恢复文件成功不代表业务已完成核对，也不包括对象存储附件。

## down 与版本降级

- 成对 down 用于明确受支持的结构回退，不是整份 up 失败时可自动执行的补偿脚本。部分 up 可能尚未建立 down 假定的对象，直接执行 down 可造成二次破坏。
- 当前基线的阶段回退只支持独占的空业务库：先删除固定权限目录，再逆序移除触发器、外键和表。业务数据、角色与账号、审批或审计记录不会被脚本自动清理；已执行 system seed／管理员初始化的库不等于空业务库。
- 正式环境版本降级先判断旧应用与当前结构是否兼容。兼容时可在核验后切回旧应用；不兼容时使用验证过的 down 或恢复配套备份，不能只换镜像。业务事实已经使用的新能力，不能以回退结构为由丢弃真实记录。
- 后续每个增量 migration 明确自己的停写范围、数据守卫和可回退条件；不可无损逆转的改动应明确拒绝 down，并提供恢复边界。存在 down 文件不等于保证任意版本可降级。

## 验证边界

- 基线对照从源提交的完整旧链与新基线分别建立空库，比较字段、生成表达式、字符集／排序规则、索引、外键、CHECK、触发器正文／顺序／SQL 环境及权限目录。排除迁移运行元数据、环境 DEFINER 和时间游标，保留业务语义。
- 合并时的完整对照仅作为当次验证材料，不维护长期结构快照。日常验证范围由[迁移测试取舍](../../../docs/testing-strategy.md#migration-测试的范围与维护)维护，基线之后的数据转换按实际风险补充测试。
- fresh 验证还要覆盖重复运行、状态查询、旧登记拒绝、非空无登记拒绝和失败后的停止边界。完整 up/down/up、阶段非空守卫与部分执行后的失败记录分别验证，不能用正向通过推断回滚可用。
- 备份验证必须实际恢复到独立库，核对结构和数据；仅生成文件或通过 gzip 校验不代表可恢复。正式上线前还须完成部署环境的恢复演练、停写与人工恢复验收。
- 验证结果与仍待用户验收的能力只在交付说明及[路线图](../../../docs/roadmap.md)记录，不由上述规则推断已通过。

## 追踪卡实验分支

本分支按[ADR-0027](../../../docs/adr/0027-tracking-card-workbench-and-terminal-output.md)只初始化独立空库。20261109 的追踪卡、终检入库、路线简化、旧生产质检退役与旧执行退役迁移不提供业务历史转换；相关非空守卫拒绝误接原库。终检来源外键先切换，旧 Quality 引用再解除，最后移除旧 Production 表。不可逆 down 明确拒绝自动回退；失败库保留诊断，重新初始化另一个空库，不改登记校验和。通用采购和库存约束仍按各所有者设计执行。

`202611090060-tracking-abnormality-disposition` 将异常改为带影响数量的一次性结算，并让批量终检按剩余盘量生成产出。旧实验追踪数据无法补出真实影响数量及返修／报废分配，迁移仅接受空追踪数据，非空时拒绝；使用另一个独立空实验库，不在原库猜造或清除历史事实。部署切换必须同时使用匹配的新应用与新库，不能让新接口读取旧异常结构。

## 仓库简化实验分支

[ADR-0028](../../../docs/adr/0028-independent-warehouse-receipt-and-inspection.md)在追踪卡分支基础上只初始化另一个独立空库，不转换旧采购轮次、实收修订、定稿分配、真实退回或来料检验办理。采购／库存旧来源外键先解除，Quality 独立报告结构随后建立；每份破坏性迁移在 DDL 前检查受影响业务数据为空，已有数据拒绝。既有 migration 不变，破坏性迁移拒绝自动 down；回退使用匹配应用和数据库。交接凭据选填迁移保留已有文字；回退须停写，存在空凭据时拒绝恢复必填约束。报告、库存与补单分别办理，不为旧链路保留兼容写入、影子表或伪造历史授权。

`202611110060-incoming-report-json-table` 保留独立报告已有数据，将固定五列行转换为完整 JSON 表格；转换依据和核对项由 [Quality 数据库](../../../apps/api/src/modules/quality/docs/database.md#写入查询与迁移)维护。执行前暂停所有报告登记／更正及相关采购写入，并备份匹配旧应用的数据库。迁移在数据预检通过后短暂移除报告更新禁止触发器，转换后恢复触发器并增加完整表格 CHECK；中途失败即保持停写，核验实际列名、数据、CHECK 和更新／删除触发器，不能以重新运行迁移代替恢复。该转换不改旧报告批号或旧 HTTP 幂等结果；切换前结束旧客户端操作并刷新，不能把旧提交意图自动转入新 scope。动态表格不能无损降回固定五列，down 明确拒绝，降级使用匹配备份及应用。
