# Migration 顺序与注册规则

> [返回数据库基础设施包](../README.md)。业务表语义不在本文件维护。

## 事实来源

`packages/database/migrations/*.up.sql` 按完整文件名升序组成唯一 migration 注册表；同名
`.down.sql` 提供配对回滚 SQL。`src/migration-utils.ts` 负责读取、计算校验和及共用的已执行记录检查，`src/migrate.ts` 按注册顺序执行尚未登记的迁移，
`src/migrate-status.ts` 报告 pending／running／applied／failed；登记结构见[迁移登记表](../README.md#迁移登记表-_schema_migrations)，开发历史整合的检查例外见[下方规则](#开发模式下的历史整合)。运行器只执行 up，没有自动 down／rollback 或强制标记完成命令。

文档不重复枚举 migration 文件或完成状态，避免注册表演进后产生第二份过期清单。查看当前顺序使用：

```text
corepack pnpm db:migrate:status
```

## 初始化基线

当前初始化基线为 `20261102`，按模块保留完整结构与业务约束。文件按以下阶段全局排序，不能独立初始化某一个模块：

1. 各模块建表，包含最终字段、主键、索引、CHECK。
2. 各模块添加外键，处理相互引用及循环依赖。
3. 各模块创建触发器，保留同一事件的执行顺序和创建时 SQL／字符集环境。
4. 写入固定版本的权限目录；system seed、管理员初始化与可选 demo 继续使用原入口。

基线之前的 SQL 原文和回滚限制由 Git 历史保存，不进入当前运行链。基线用于空库初始化，不迁移旧业务数据；旧库的结构与登记须先满足当前运行器契约，开发模式也不会自动把旧库认定为新基线。另建空库使用与当前代码匹配的 `db:init`，是否重建及保留原数据仍遵守[数据保留约定](../../../AGENTS.md#数据库与交付约定)。

基线及之后的增量构成唯一活动注册表，按下方规则维护；已发布基线保持不可变。文件历史由 Git 保存，不维护额外的基线文件清单或摘要副本。运行器直接读取 migration 目录，并按数据库中的执行登记核对文件身份与校验和。

该边界也退出旧链完整 down 的支持；旧链曾有重复外键缺陷，不将其退役解释为缺陷已修复。当前基线 down 仅用于受控空业务库验证，正式环境恢复以[迁移安全](migration-safety.md)为准。

## 追加规则

1. 文件名使用 12 位数字时间序号加 kebab-case 目的名；完整迁移基名（时间序号与目的名）全局唯一，并同时添加 `.up.sql`、`.down.sql`。数字前缀可因多分支开发重复，不单独作为迁移身份；运行器以完整 `.up.sql` 文件名登记已执行记录。
2. 开发中同一次模块变更（包括同一表的字段与约束调整）合并为一对 migration，不按每次编辑拆文件。未发布且仅在开发环境使用的 SQL 可继续整改，包括已在开发库登记的文件，运行行为见[开发模式规则](#开发模式下的历史整合)。已发布迁移保持不可变，后续修正追加新文件；非开发环境不接受历史身份、内容或顺序变化。
3. 有先后依赖的 migration 必须确保完整文件名排序满足依赖。被引用表、唯一键和必要索引必须先创建；循环外键在两侧对象存在后通过后续 migration 追加。
4. 数据回填先于非空、唯一键、外键或收紧后的 `CHECK`；无法无损推导时应失败并要求人工处置，禁止猜测业务事实。
5. 破坏性 down migration 必须设置数据守卫。回滚会覆盖后续业务进度时，应明确拒绝回滚。
6. migration 的物理集中不改变表所有权；字段、约束、索引、关系或业务含义变化时，同步更新所属数据库设计及受影响的所有权登记，遵守[数据库文档要求](../../../docs/database-conventions.md#数据库设计文档)。

## 开发模式下的历史整合

`db:migrate` 与 `db:migrate:status` 仅在显式 `NODE_ENV=development` 时放宽已登记文件被移除、同名文件内容改变及合并引起的历史顺序差异；状态查询给出开发提示，不因此失败。运行器按现有环境加载方式读取进程环境及工作区 `.env`；未显式设置该值，或设为 test、production 等其他值时，均采用严格检查，不自动选择开发模式。无需额外命令入口。

原 `_schema_migrations` 行、校验和与执行时间保持不变。同名已登记文件不重放；未登记的新文件按当前文件名顺序正常执行。改名或产生新合并文件会形成新的迁移身份，不能将其当成已执行文件自动跳过。开发者须在整改时同步处理实际结构与数据差异；修改已执行 SQL 不会自动把修改部分应用到数据库，脚本也不推断差异、不自动合并 SQL 或比较 schema。

该例外只放宽历史文件检查，不删除或改写登记，不补造基线身份。running／failed、非法登记结构或状态、非空库没有登记等情况仍然失败；失败恢复遵守[迁移安全](migration-safety.md#运行状态与中断)。新增 migration 的失败同样会阻断继续执行。文件配对、业务所有权及开发环境的静态门禁边界见[迁移就绪门禁](migration-readiness.md)。

开发整改通过[迁移前副本与手动切库](migration-safety.md#开发迁移前副本与手动切库)回到本轮起点，再执行整理后的 SQL；副本保留原登记，切库不改变上述历史检查策略。
